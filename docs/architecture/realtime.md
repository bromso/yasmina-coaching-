# Realtime

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Realtime.** Signed-in pages get live updates from `apps/api` over Server-Sent Events relayed through the app's own origin, so browsers never call `apps/api` and the CSP stays `connect-src 'self'`. The seam is `apps/api/src/realtime/` (`Broadcaster`: `publish(channel, event)`, `subscribe(channel, onEvent)` → unsubscribe, `close()`), built at boot from the database dialect and overridable with `REALTIME_BUS`: `memory` on SQLite (in-process fan-out, correct for the one process SQLite implies) or `postgres` (its own client, never the pool: `new SQL(url, { max: 1 })` for the NOTIFYs plus the dedicated connection `sql.listen` opens — two connections — holding one `LISTEN realtime`, `publish` = `SELECT pg_notify('realtime', '<json>')`, so every replica's subscribers hear every replica's writes; after the `LISTEN` connection reconnects every local channel gets a `resync`, since notifications in the gap are lost; `close()` waits at most 2 s for `UNLISTEN`; a `publish` after `close()` is a no-op, matching the memory bus, rather than throwing, so `publishAfterCommit` racing shutdown never records a failure). Both refuse a `{ channel, event }` payload of 8000 bytes or more (`NOTIFY_PAYLOAD_LIMIT`), so nothing works on SQLite that fails on Postgres. Channels are per workspace (`workspaceChannel(id)` = `workspace:<id>`) and per user (`userChannel(id)` = `user:<id>`, Phase 13 A's `GET /events/me` — see **Notifications.**); events are `RealtimeEventSchema` in `@repo/api-contract` (`realtime.ts`, also the `@repo/api-contract/realtime` subpath, which imports only `./note` so the browser bundle never pulls in the whole contract): `note.created` `{ note }`, `note.deleted` `{ id }`, `presence` `{ replicaId, members: { userId, name, avatarUrl }[] }` (never an email) and `resync`. `notes.create` / `notes.delete` call `publishAfterCommit(context, channel, event)` once the write is durable (after `db.transaction` resolves, never inside it, so a rollback publishes nothing); it is fire-and-forget — never throws or fails the request, a failure goes to `recordFailure` — and an oversized `note.created` (a 10 000-character body) falls back to a `resync`. The stream is `GET /events/workspaces/:workspaceId` on `Bun.serve`, outside oRPC, behind the bearer guard and rate limiter plus `x-session-token`, with `content-type: text/event-stream`, `cache-control: no-store`, `x-accel-buffering: no`: `retry: 3000`, the presence snapshot and a `resync` on every connect (nothing replayed; `Last-Event-ID` is ignored), then each event with one `id:` (monotonic per process, the same on every stream), and a `: ping` every 25 s. Auth goes through the shared `resolveSession` / `findMembership` (`apps/api/src/access.ts`), the same rules as the procedures (an impersonation session may subscribe while its admin is still a superadmin, but never joins presence): `401` without a session, `404` for a non-member and an unknown workspace alike; both are re-checked every 60 s and a stream that fails is closed. A member a workspace's required two-step verification blocks gets `403` instead (plain text `two_factor_required`, no oRPC JSON shape — the relay drops bodies anyway), on connect and on that same 60 s recheck — see **Required two-step.**. Limits: 5 streams per session and 10 per user across sessions (`429`; an impersonation stream counts against the impersonating admin's cap, not the impersonated user's) — `/events/me` keeps its own pair of these counters apart from the workspace stream's (see **Notifications.**) — `REALTIME_MAX_STREAMS` per process (default 1000, `503`, shared by both kinds; a blank env value means the default); Bun's 10 s idle timeout is turned off before the stream is even set up — the guard, the rate limiter and the membership check all run first, and a database round trip there would otherwise read as idle — and restored to its configured value once the answer is known not to be a stream (`401`/`404`/`429`/`503`) or the handler throws, so a keep-alive socket from any of those still idles out; a slow reader is dropped once 256 KiB is queued past its 64 KiB buffer (errored, and its connection released within ~4 s). A server drop errors the stream with no error value (queued bytes discarded; Bun.serve prints a stack trace for any other value), a client drop closes it; shutdown closes every stream first without publishing presence; the dedicated jobs worker serves none. Presence is per replica: each process tracks who has a stream open per workspace (several tabs of one user are one person) and publishes a full snapshot with its random `replicaId` on every join and leave and again every 25 s; clients merge the latest snapshot per replica and drop one unseen for 60 s, so on several replicas a newcomer may take up to 25 s to see users on the others; names and avatars are read on connect, so a change shows on the next reconnect. The relay is `createEventsRoute()` in `@repo/session/events`, used by `apps/app`'s few-line `src/app/api/events/route.ts`: `401` without a user, the workspace from `?workspace=<id>` when given (not a positive integer → `404`; the api checks membership), else the cookie's — `503` when that lookup cannot reach the api, `404` without a workspace — then the upstream stream with the service token, the session token and, when the client ip is known, client id `events:<ip hash>` (without one, every browser behind that Next server shares its address bucket), unbuffered, `cache-control: no-store`, the browser's disconnect aborting the upstream request; an upstream `401` / `404` / `429` / `503` passes through, anything else is `502`. The client (`apps/app`'s `LiveNotes` over `new EventSource("/api/events?workspace=<rendered id>")`, the pure reducer `applyRealtimeEvent` and connection helpers in `src/lib/realtime.ts`, `HereNow`) imports values only from `@repo/api-contract/realtime`; it skips the first `resync` only when it arrives within 5 s of the page's server `renderedAt` (so a back/forward-cache restore refreshes) and calls `router.refresh()` on later ones; presence survives the list's re-seed after an action or refresh; "Reconnecting…" shows after 5 s in `CONNECTING`, and a `CLOSED` source (a non-OK answer: an api restart, a `429` sixth tab) is probed once with a plain `fetch` (`probeStream`, cancelling the body unread) to tell a permanent refusal apart from a transient one: a `401` (signed out) or `404` (workspace gone, or membership revoked) stops reconnecting for good and shows a translated message instead (cleared on the next successful open or a workspace switch); a 2xx reconnects at once, since the transient condition that caused the original error already cleared by the time the probe landed; anything else (`429`/`502`/`503`, or the probe itself failing) keeps the existing capped, jittered backoff — 5 s doubling to 60 s, ±20 %, reset on open (`reconnectDelay`, `refusalFor`, `decideAfterProbe` in `src/lib/realtime.ts`) — with "Reconnecting…" shown meanwhile; note dates print in UTC so server and client agree in any zone. Without JavaScript `/notes` is exactly the server render. Reverse proxies must not buffer `text/event-stream` (nginx `proxy_buffering off;`, Caddy `flush_interval -1`) and need idle timeouts above 25 s. Adding events, subscribing from a page, scaling and proxies: `docs/guides/realtime.md`. See `apps/api/README.md`, `apps/app/README.md` and `packages/session/README.md`.
