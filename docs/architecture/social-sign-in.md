# Social sign-in and magic link

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Social sign-in and magic link.** Google, GitHub and Apple sign-in run through `apps/auth`'s route handlers: a provider button links to `/oauth/<provider>/start`, which asks `auth.oauth.start` for the authorization URL, state and (Google) PKCE verifier, stores them in the `oauth` cookie and redirects to the provider; the provider returns to `/oauth/<provider>/callback`, which checks the state against the cookie before any api call, then `auth.oauth.callback` exchanges the code and issues a session, and the auth app sets the `session` cookie as password sign-in does. The provider secrets and the token exchange (Arctic, `apps/api/src/oauth/`) live only in `apps/api`; a provider is offered (`auth.providers`) only when all of its `OAUTH_*` vars are set. Linking: a known identity (`identities` table, keyed by provider and provider user id, migration `0005_identities`) signs in its owner; a signed-in caller connects an unclaimed identity, only on a session under 10 minutes old (`REAUTH_WINDOW_MS`; older is refused at `/oauth/<provider>/start` and again at the callback, sending the browser to `/login?reauth=1&next=…`), and gets its own session back, never a new one — see **Two-factor**; otherwise only a provider-verified email links to the account with that email or creates a passwordless, verified one, and an unverified email is refused (`FORBIDDEN`). Linking a verified provider email — or consuming a magic link — into an account whose email was never verified runs `purgeUnverifiedAccount` first (password cleared, sessions, identities, reset links, two-factor challenges and every pending email-change, cancel and revert link deleted, two-step verification turned off, email marked verified), so someone who pre-registered a victim's address with their own password is locked out. Passwordless accounts (`password_hash` NULL) fail password sign-in exactly like a wrong password; `User.hasPassword` tells `apps/account`'s Security page to offer **Set a password** (`account.setPassword`) instead of the change form, and `account.identities.disconnect` refuses to remove a passwordless account's last identity — unless the account also holds a passkey, which counts as a way in too (see **Passkeys**). "Email me a sign-in link" on `/login` calls `auth.magicLink.request` (always silent, 3 per email per 15 minutes); the mailed `${AUTH_URL}/magic?token=…` link is valid 15 minutes, once, and is consumed only by the page's **Continue** button (a server action calling `auth.magicLink.consume`), never by loading the page, so mail scanners cannot burn it; an address with no account gets a passwordless, verified one on consume. The `oauth` cookie is host-only on the auth app, HttpOnly, `Secure; SameSite=None; Path=/oauth`, 10 minutes, single use: `SameSite=None` because Apple returns with a cross-site `form_post` POST that would not carry a Lax cookie; Chromium and Firefox treat `*.localhost` as a secure context, so it works over http in dev (Safari does not resolve `*.localhost`). Setting up each provider — console, redirect URIs (`${AUTH_URL}/oauth/<provider>/callback`), scopes, Apple's `.p8` key — is in `docs/guides/oauth-providers.md`. See `apps/api/README.md`, `apps/auth/README.md` and `apps/account/README.md`.
