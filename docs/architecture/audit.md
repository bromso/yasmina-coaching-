# Audit retention and export

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Audit retention and export.** Two env-driven stages, nightly, keep `audit_log` from growing forever: `AUDIT_PII_RETENTION_DAYS` (default 90, integer ≥ 1, strictly less than `AUDIT_RETENTION_DAYS`) strips `ip`/`user_agent` first; `AUDIT_RETENTION_DAYS` (default 365, bounded 180–1095 — CNIL's general case to its internal-control maximum — or up to 3650 with `AUDIT_RETENTION_JUSTIFIED=true`, which also logs one startup warning asking the operator to document the legal obligation or DPIA that justifies going past 1095) deletes whole rows later. The schedule is `audit.prune` (`45 3 * * *`; see **Jobs**): each run deletes first, then strips only rows between the two cutoffs (so a row about to be deleted is never stripped first), in batches of 1000 keyed on the last id (`queries/audit.ts`'s `deleteBefore`/`stripNetworkBetween`, linear in the table; no migration). It keeps the default 60 s job `timeoutMs` (so the worker's shared batch lock is unchanged) and its own time budget is 80 % of that, 48 s: once the budget passes it stops between batches, logs a partial run with its counts and returns normally — no failed attempt, no dead job — so a large backlog drains over several nights; a row exactly at either cutoff is kept (strict `<`); idempotent. Apart from the privacy purge nulling user ids, `audit.prune` is the only code that updates or deletes an `audit_log` row — every writer stays append-only, and `reason`/`metadata` stay on a row until it is deleted. `admin.audit.list`'s `retention: { piiDays, rowDays }` reports the limits in effect, and `/admin/audit` shows them: "Network details (IP, browser) are kept 90 days; entries are kept 365 days." Since Phase 12 A, the superadmin's `targetType=workspace&targetId=N` filter (`admin.audit.list`, the workspace detail page, `admin.audit.export`) also matches `workspace_id = N`, not only `target_type`/`target_id` — a workspace's activity rows now target the member, key or endpoint changed, not the workspace itself, and without this they would drop out of `/admin/workspaces/<id>`'s own audit view (see **Activity log.**).

`admin.audit.export({ from, to, format, actorId?, targetType?, targetId? })` is a synchronous download, superadmin only like every `admin.*` procedure (`NOT_FOUND` to anyone else, impersonation included). `from`/`to` are `YYYY-MM-DD`, inclusive whole UTC days (`auditExportRange`: `from`'s own midnight through the midnight after `to`'s), `from` ≤ `to`, at most 366 days apart, and `to` may not be later than tomorrow's UTC date (`isToWithinBounds`, checked before the rate limiter — a stale admin clock a day ahead of UTC can still pick today). Rows come back oldest first, capped at `AUDIT_EXPORT_MAX_ROWS` (100 000, test-overridable): the handler selects with `limit: cap + 1` and throws `CONFLICT` (`auditExportCapMessage`) the moment that single select returns more than the cap, rather than a separate count-then-select that could race and silently truncate. Columns, in order: `id, at, actor_id, actor_email, impersonated_id, impersonated_email, action, target_type, target_id, reason, ip, user_agent, metadata`; emails are as of the export, null for a purged actor. CSV is RFC 4180 (every field quoted, CRLF line ends, a UTF-8 BOM, a header row) with OWASP's CSV-injection guard — a cell whose first character is `=`, `+`, `-`, `@`, a tab or a CR gets a leading `'`; JSON Lines is one object per line with real `null`s, `metadata` parsed back to an object when it is valid JSON else kept as the stored string. The result is a `File` named `audit-<from>-<to>.<format>` (`text/csv; charset=utf-8` / `application/x-ndjson`). After the file is built — never before, and never inside the file it describes — the handler writes `audit.exported` (metadata `{ from, to, format, rows, actorId?, targetType?, targetId? }`); a refused export writes nothing. Limited `audit-export:<adminId>` 10/hour.

`apps/auth`'s `POST /admin/audit/export` route sits behind `assertSameOrigin` and is gated by `admin.audit.export`'s own `NOT_FOUND` (the `(gated)` layout does not wrap route handlers), answers every response — the file, a `404`, a redirect — with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, and streams the file with `Content-Disposition: attachment; filename="<file.name>"`, setting `Content-Type` itself from the posted `format` — never from the returned `File`'s own `.type`, which Bun's `Response.formData()` decode drops on a multipart part. A refusal (`BAD_REQUEST`/`CONFLICT`/`TOO_MANY_REQUESTS`) redirects to `/admin/audit?exportError=<code>` with the page's filters kept, and an api 5xx or an unreachable api to `exportError=unavailable` ("The export is unavailable right now. Try again shortly."); the notice shows in the Export card, which sits above the table and says "Uses the filters above.", and From/To carry server-computed `min` (today − `AUDIT_RETENTION_DAYS`) and `max` (tomorrow, UTC) (English only, like the rest of `/admin`).

Restoring an older backup brings pruned rows back — the next `audit.prune` removes them again — so effective retention is the configured period plus however long `BACKUP_RETENTION_DAYS` keeps that backup around. The legal basis for the bounds: CJEU C-582/14 *Breyer* (an IP address is personal data where the operator has legal means to identify the person), GDPR Art. 5(1)(c)/(e)/(f), 5(2) and 32, and CNIL Délibération n° 2021-122 (six months to a year generally, up to three years for documented internal control, longer only for a specific legal obligation or DPIA). **Tamper evidence is a known, documented gap**: rows are deleted, not archived, with no hash chain or WORM storage. See `docs/guides/operations.md`, `apps/api/README.md` and `apps/auth/README.md`.
