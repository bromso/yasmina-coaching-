# Content

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Content.** `apps/blog` is MDX posts compiled at build time: fumadocs-mdx (`source.config.ts`, which imports the schema by relative path rather than `@repo/content/schema` — it bundles that file with esbuild and leaves packages external, so a package import would make Node load the schema's `.ts` source at runtime) plus fumadocs-core, headless (no `fumadocs-ui`). `@repo/content` is the pure-TypeScript engine, by subpath like `@repo/telemetry`: `schema` (the strict frontmatter Zod schema — `postFrontmatterSchema` for the blog, `docFrontmatterSchema` for the docs app), `posts` (`createBlog` and `ContentError`, which lists every problem at once rather than stopping at the first), `feeds` (RSS 2.0, Atom, JSON Feed 1.1, full content), `links` (root-relative link checking), `seo` (BlogPosting JSON-LD) and `checks` (`extractLinks`, `extractImages`, `imageProblems`, `headingProblems` — raw-MDX content checks shared by the blog and the docs app; `headingProblems`'s `titleOwner` names what owns the page's one `<h1>` in its message, `"post"` for the blog, the default `"page"` for the docs app). `@repo/ui/components/mdx` is the component map a post's body can use (headings with "#" anchors, a copyable code block, callouts, tabs — stacked, with no JavaScript, before hydration — steps, images with required dimensions) plus `components/mdx/static`, a server-safe twin with zero Client Components in its graph (guarded by its own test) for rendering feeds outside Next's page pipeline; the blog blocks (`post-card`, `post-header`, `toc`, `prev-next`) compose them, and `toc-active` (`TocActive`, a client wrapper both the blog and the docs put around `Toc`) marks the section in view `aria-current="location"` once hydrated, the server-rendered list unchanged. Frontmatter: `title`, `description`, `date`, `updated?`, `author` (a key of `content/authors.ts`), `tags` (lowercase kebab-case ASCII; each language's display labels in `apps/blog/src/content/ui.ts`'s `TAG_LABELS`), `cover?`, `draft?`, an optional `type` (defaults to `"Blog Post"`, reserved for a later Open Knowledge Format export), `locale` (`sv` or `en`, defaulting to `en` so docs, help, jobs and any one-language blog never set it) and `translationOf?` (the slug of the original this post translates). The blog is Swedish at the root and English under `/en`: `createBlog`'s `rootLocale: "sv"` serves `<slug>.mdx` (`locale: sv`) at `/<slug>` and `en-<rest>.mdx` (`locale: en`) at `/en/<rest>`, fails the build on a misnamed file, a `translationOf` naming no post or a post in the same language, or a second translation of one original, and `sv` / `en` join the reserved slugs (as does a reserved word after `en-`). `Blog.inLocale(locale)` narrows every list, tag, author and neighbour to one language and `translation(slug)` finds the published counterpart either way; every list, tag, author and feed route exists once per language, each language has its own root layout (route groups `(sv)`, `(en)`) for `<html lang>`, and an unmatched URL renders `src/app/global-not-found.tsx`. A post links to another app of the site as `www:/<path>`, resolved to `siteUrl("www")` + the path at build time (page and feeds) because a post cannot know the production domain; `siteLinkProblems` refuses one without a `/` path, one pointing at the blog itself or an app id not in lowercase, for every post, drafts included. `draft: true` and a future-dated post both preview under `next dev` only — scheduling is just a date in the frontmatter, and "publishing" a scheduled post is merging the PR and redeploying, nothing else; a draft/future post never appears in a feed or the sitemap either, nor is its own links or images checked (see below). The build gate runs in two stages: fumadocs-mdx validates each post's frontmatter against the strict schema (and measures a local Markdown image's dimensions) while *compiling* it, one post at a time, in fumadocs' own wording (a missing required field, a bad `date`, a `cover` with no `alt`, an unknown key, or a missing local image, each its own failure, before `apps/blog/src/lib/blog.ts` ever runs); once every post compiles, `assembleBlog` (`apps/blog/src/lib/blog-core.ts`, blog-specific: it also owns `knownPaths` and `nestingProblems`) loads and validates them *together*, collecting every problem it can find — an unknown author, a malformed, reserved or duplicate slug, a malformed tag, a post not directly in `content/posts/`, a body `# h1` (the post's own title is already the page's one `<h1>`, checked by `@repo/content/checks`'s `headingProblems`), and, for the posts that would publish, a broken or non-root-relative internal link, a link naming an app `@repo/sites` doesn't know, an unparseable link, a link to `localhost`/`*.localhost` or a loopback/`0.0.0.0` address outside a `.localhost` site, and a missing JSX image or `cover.src` under `public/` (`@repo/content/checks`'s `extractLinks`/`extractImages`/`imageProblems`) — into one thrown `ContentError`, even when `createBlog` itself throws over an unrelated post elsewhere (a bad tag on one post never hides a broken link on another). A **remote** image is fetched over the network at build time to measure it, so a slow or unreachable host slows down — or fails — the whole build. `/tags/<tag>` and `/authors/<author>` are unpaginated (every matching post on one page); the index and `/page/<n>` show 12 posts per page. Routes, each also under `/en/` for English: `/`, `/page/[n]`, `/[slug]` (with OG/Twitter images, BlogPosting JSON-LD with `inLanguage`, and hreflang links to its translation), `/tags/[tag]`, `/authors/[author]`, and `/rss.xml` / `/atom.xml` / `/feed.json` (per language, naming it) (rendered through `mdxStaticComponents` with `react-dom/server.edge`'s `renderToReadableStream` — see the comment in `feed-render.ts` on why that works on `next@16.2.12` — with every relative URL made absolute). `pageAlternates(canonical, locale, languages?)` advertises that language's three feeds (and the hreflang pair, when the page exists in both languages) from every page; the sitemap derives each entry's `lastModified` from the posts, tags and authors it covers. Like every static app, there is no runtime dependency on `apps/api` beyond the shared telemetry/analytics routes. `@repo/content` is shared, not blog-specific: `apps/docs` runs on the same engine and is just as static, its only runtime calls the same shared telemetry/analytics routes. `defineDocs` (fumadocs-mdx) reads `content/docs` plus a `meta.json` per folder, validated against `docFrontmatterSchema` (strict: `title`, `description` required, `icon?`, `updated?` a date, `tags` default `[]`, `type` defaults to `"Documentation"`, the same Open Knowledge Format readiness as the blog's `type`); `apps/docs/source.config.ts` imports that schema by the same relative path as the blog, for the same bundling reason. A `meta.json`'s `pages` orders the sidebar with fumadocs' own tokens: `---Name---` (optionally `---[icon]Name---`) separators, `...` / `z...a` for "every remaining page, in order or reversed", `[Text](url)` link entries (`external:` and a leading `[icon]` allowed), `!name` to hide an entry and `...name` to inline a folder's children (a folder only) — an entry naming neither a page nor a folder, or a `...name` naming a page, is reported, not silently dropped; the separator is fumadocs' own regex, copied verbatim, so the check classifies an entry exactly as fumadocs does. The build gate (`assembleDocs` in `apps/docs/src/lib/docs-core.ts`, one `ContentError` like the blog's) fails on a `meta.yaml` / `meta.yml` (only `meta.json` is checked), a `meta.json` entry matching no page or folder, a body `#` h1, a broken/non-root-relative/local-host link, a missing image under `public/` (the same `@repo/content/checks` and `links` the blog uses) and a page under a reserved top-level name — `all`, `og`, `api`, `opengraph-image`, `twitter-image`, `manifest.webmanifest`, `sitemap.xml` or `robots.txt` — that its own built-in route would shadow; frontmatter shape errors come from fumadocs at compile, exactly as the blog's do. Routes: `[[...slug]]` (`/` is `content/docs/index.mdx`), `/all` (every page, in sidebar order, the search control's no-JavaScript fallback), per-page OG/Twitter images at `/og/<path>/image.png` (a route handler, `cache-control: public, max-age=3600, s-maxage=86400` — Next 16.2 refuses an `opengraph-image` route under a catch-all), a sitemap (`lastModified` only when `updated` is set) and `/api/search` — `force-static`, built by `createFromSource` on fumadocs-core's bundled zbsearch engine (no `@orama/*` install), downloaded once by the ⌘K/Ctrl K dialog (`staticClient`) and searched in the browser from then on. The layout is three columns on `lg` (sidebar, article, table of contents — absent for a page with no headings; wrapped in `TocActive`) and a closed `<details>` "Menu" on narrower screens; breadcrumbs start with "Docs", the article footer shows "Last updated" and, only when the build-time `CONTENT_REPO_URL` is set, "Edit on GitHub" (`editUrlFor`, the page's file path appended), and `PrevNext` is labelled "Previous"/"Next" with `aria-label="Docs pages"`. The `@repo/ui` blocks stay plain, serialisable props, no fumadocs import: `docs-sidebar` (folders as `<details>` with a 28px toggle, `aria-current` on the current page), `breadcrumbs`, `docs-search` (a link to `/all` before hydration, then the dialog: a "Type to search the docs" hint, "No results", an "unavailable" state linking to `/all`, closing on navigate) and the `Cards`/`Card` MDX components (in both the interactive and the static-rendering component maps); `CommandDialog` took its title inside `DialogContent` and a `commandProps` passthrough (`shouldFilter={false}`) to carry this. See `docs/guides/content.md`, `apps/blog/README.md`, `apps/docs/README.md` and `packages/content/README.md`.
