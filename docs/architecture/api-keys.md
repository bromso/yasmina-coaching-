# API keys and /v1

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**API keys and /v1.** Phase 11 A: a workspace admin or owner can connect outside tools and scripts without sharing anyone's sign-in. Migration `0027_api_keys` adds `api_keys` (`workspace_id` `ON DELETE CASCADE`, `name` 1–60, `prefix` 8 base62 chars unique, `secret_hash` the SHA-256 hex of the whole key, `scopes` a JSON array, `created_by` nullable with no FK — like `audit_log.actor_user_id` — `created_at`, `expires_at` nullable (no expiry), `last_used_at`, `revoked_at`) and a nullable `notes.api_key_id` (no FK; a revoked or deleted key leaves the note it wrote). A key is `bb_live_<8-char base62 prefix>_<43-char base64url secret>` (`generateApiKey` in `apps/api/src/api-keys.ts`; the secret is 32 random bytes, the prefix a separate uniform draw sharing none of the secret's entropy), shown exactly once at creation; only its SHA-256 hash is stored, looked up by `prefix` and compared with `crypto.timingSafeEqual`. Scopes are `API_SCOPES = ["workspace:read", "members:read", "notes:read", "notes:write"]` (`@repo/api-contract/api-keys-limits`, a Zod-free subpath); a key needs at least one. `api` is the second entry in `FEATURES` (Pro and Team; Free sees an upsell in place of the create form, `FEATURE_MESSAGES.api` "Upgrade to use the API"; only `create` needs the feature — `list` and `revoke` work on every plan, so a workspace that drops to Free still lists its keys, paused (`401` on `/v1` until it upgrades again), each revocable). Expiry is chosen at creation — 30, 90 (default) or 365 days, or none (the UI warns that a key with no expiry keeps working until revoked). A workspace holds at most `MAX_API_KEYS` (20) live keys: the count and the insert run in one transaction after `workspaces.lockForOwnership`, so two concurrent creates at 19 can never both land a 20th (`CONFLICT` `API_KEY_LIMIT_MESSAGE`). `workspaces.apiKeys.list` / `create` / `revoke` (⚑, `member("admin")`) manage keys from `apps/account`'s Workspace page; `create` needs the `api` feature and is refused while impersonating, like `revoke` (`list` stays readable); every create and revoke writes an audit row (`workspace.api_key_created` / `workspace.api_key_revoked`), never the key or its hash, and revoking an already-revoked key is a silent no-op. `/v1/*` is the one surface these keys authenticate: no service token, no session. `createApiKeyGuard` (`apps/api/src/v1/guard.ts`) runs, in order: parse the `Authorization: Bearer bb_live_…` header → look up by prefix and compare the hash (a miss compares against `DUMMY_KEY_HASH`, so hit and miss take the same work) → refuse a revoked key (its use recorded through `recordFailure`, ids only, never key material, at most once a minute per key with the uses in between counted into the next report) or an expired one → the workspace still exists → the plan still has `api` → the per-key limiter `api-key:<id>` (600/minute, default) → write `last_used_at` (throttled to once a minute per key, so it is approximate — up to a minute stale, and can step back across replicas). Every refusal (no key, malformed, unknown, revoked, expired, workspace gone, feature lost) is `401 unauthorized`, with no oracle for which, except once a caller's address exhausts `apiAnonLimiter` (60/minute by default, keyed `v1-anon:<hash of the socket address>` — behind a proxy that is the proxy's address, so all refused traffic behind it shares one budget), when it becomes `429` instead. Every /v1 error is one shape, `{"error":{"code","message"}}`: `unauthorized` (401), `forbidden_scope` (403, names the missing scope — checked before input validation, so a wrong-scope key never also learns its body was invalid), `not_found` (404 — an unknown path with no key is `401` instead, since the guard runs first), `validation_failed` (400 — its message always `Input validation failed`, never naming the field — or 413 for an oversized `POST` body), `rate_limited` (429, with `Retry-After`) and `internal` (500, or 503 past `REQUEST_TIMEOUT_MS`, both still in the /v1 shape even for a guard database failure or a timeout). Routes, from `@repo/public-api-contract`: `GET /v1/workspace` (`workspace:read`) → `{id,name,slug,plan}`; `GET /v1/members?cursor&limit` (`members:read`) → members by user id, never an email; `GET /v1/notes?cursor&limit` and `GET /v1/notes/{id}` (`notes:read`); `POST /v1/notes` and `DELETE /v1/notes/{id}` (`notes:write`, reusing the internal note queries, limits, `publishAfterCommit` and the `note_created` event with no user id); `GET /v1/openapi.json` and `GET /v1/docs` (Scalar) are open. Every query is scoped to the key's own workspace in SQL, so another workspace's id is `404`; the members cursor stays filter-only (a cursor is a keyset position, not a reference, so it never answers differently for another workspace's id — paging must survive a member leaving). `notes.api_key_id` and the internal `Note.apiKey: {id,name} | null` (set wherever a `Note` is built: `list`, `find`, `create`, the realtime event) mean a key-authored note's `authorId` is `null` but it is not "Deleted user": `apps/app`'s `/notes` shows "via API key `<name>`" instead, even after the key is revoked. A repo-specific Gitleaks rule, `bb-live-api-key` (`.gitleaks.toml`, keyword `bb_live_`), flags a leaked key — proven against 200 generated keys (`apps/api/src/api-keys.test.ts`) and a fixture (`scripts/security/gitleaks-rules.test.ts`). Basis: OWASP's REST Security, Multi-Tenant Security and Secrets Management cheat sheets (revocable, SHA-256 hashed, least-privilege scopes, never logged) and GDPR Art. 25(2) (no emails in `/v1`, no scope preselected). `@repo/public-api-contract`'s own rule: `/v1` only ever gains a field, an output, a route or an error message — anything that could break a caller is `/v2`, served alongside `/v1` until it is retired.
