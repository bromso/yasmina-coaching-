# Privacy

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Privacy.** Migration `0019_privacy` adds `users.deletion_scheduled_at` (null = no deletion scheduled) and `data_exports` (`user_id`, `status` one of `pending` / `ready` / `expired`, `storage_key`, `created_at`, `ready_at`, `expires_at`). Two groups of procedures, every one ⚑: `account.export.*` (`request`, `get`, `download`) and `account.delete` / `account.cancelDeletion`; all but `account.export.get` are refused while impersonating (`get` only shows the status). `account.export.request` is throttled to one request per `EXPORT_REQUEST_INTERVAL_MS` (24 h, whatever became of the last one; `CONFLICT` naming when the next is allowed) and enqueues `privacy.export`, which collects the account's data (profile, avatar URL, sign-in methods, sessions, workspaces, invitations sent, notes, the audit rows naming the user as actor, as the impersonated user or as the target (an admin's impersonation, session revocation or 2FA reset, with its reason) — an admin-written row's ip/user agent left out, and `metadata` cut to a per-action key allowlist (`EXPORTED_AUDIT_METADATA`, so no admin id such as `impersonatedBy`) — notifications (type, created, read, data; see **Notifications.**), analytics events and pageviews, read with explicit column lists so no password hash, TOTP secret, recovery code, session, token or invitation-token hash ever rides along), writes it as one JSON file through the storage seam and mails `dataExportReady`; `account.export.get` reports the latest row's status (a row still `pending` `EXPORT_REQUEST_INTERVAL_MS` after its request — its job died — reads as `expired`, so the page offers a new request), and `account.export.download` streams the file to its owner only while `ready` and unexpired (`NOT_FOUND` otherwise). `apps/account`'s `/data-privacy/export` route (the only one) sets `Content-Disposition: attachment`, so the browser saves rather than opens it. A `ready` export expires after `EXPORT_TTL_MS` (7 days); the nightly `privacy.export.prune` schedule (`40 3 * * *`) turns it `expired` and queues its file for `storage.delete`, and marks every export still `pending` a day after its request `expired` (see **Jobs**). `account.delete` (`DeleteAccountSchema`: the account's own email, typed, case-insensitively) schedules the purge `DELETION_GRACE_MS` (7 days) ahead, refuses a session past the re-authentication window (`FORBIDDEN`, `data.reason: "reauth"`) and a sole owner of a workspace with other members (`CONFLICT`, naming them — the purge re-checks this itself, since an invitation can be accepted in between), then ends every session (this browser included) and mails `accountDeletionScheduled` with a link to `${AUTH_URL}/login`; a repeat call while one is already scheduled is a no-op — the same date comes back, with no second mail and no second sign-out. The browser is redirected to `${AUTH_URL}/login?deleted=1`, whose notice reads "Your account is scheduled for deletion. Sign in to cancel." — signing in during the grace period, then **Cancel deletion** on the red `DeletionBanner` (`@repo/ui`, shown by the `app` and `account` layouts whenever `me.user.deletionScheduledAt` is set) calling `account.cancelDeletion`, is how it is stopped; any live session may cancel, not only the one that scheduled it, and it is a no-op once nothing is scheduled. The hourly `privacy.purge` schedule (`25 * * * *`) pages through every user whose schedule has passed (keyset on date then id, so a page that skips one still reaches the ones behind it), each purged in its own transaction, after first cancelling — outside that transaction — the live subscription of every workspace the user alone belongs to (a failed cancel skips the user for the next run, deleting nothing); inside the transaction it re-locks the user row, re-checks the schedule and the sole-owner block, deletes every workspace the user is the sole member of, runs `users.purge`, then **re-counts the owners of every shared workspace the user co-owned** and rolls the whole purge back — leaving the user scheduled for the next run — rather than leave one ownerless (a safety net: the purge locks every co-owned workspace up front, right after the user row, so a racing leave waits and the re-count sees it); a skip after subscriptions were already cancelled names them in the recorded failure, for an operator to restore. `users.purge` deletes the user's sessions, tokens, identities, memberships, two-factor recovery codes, data-export rows and notifications outright (see **Notifications.**); sets `invitations.invited_by`, `workspaces.created_by`, `audit_log.actor_user_id`, `audit_log.impersonated_user_id`, `analytics_pageviews.user_id` and `analytics_events.user_id` to `NULL` (the audit trail's `target_id`, `metadata`, `ip` and `user_agent` are kept — only the ids linking rows back to the deleted account are cleared) and `billing_customers.email` to `NULL` where it held the user's own address; deletes accepted invitations to the user's address (pending ones stay valid); leaves `notes.user_id` pointing at the now-gone id, so `Note.authorId` comes back `null` and `apps/app` renders "Deleted user" in its place; queues the avatar and every export file for `storage.delete`; mails `accountDeleted`; and writes a `user.deleted` audit row (actor `null`: the system) naming the workspaces it deleted. Waitlist rows are deliberately kept — a marketing address, not the account, with its own lifecycle. A sign-in identity left pointing at a purged user (one linked, then the account purged before its next sign-in) is treated as unknown and deleted on the next attempt through that provider, rather than blocking it forever. See `apps/api/README.md`'s **Privacy** section, `apps/account/README.md` and `apps/auth/README.md`.
