# Required two-step

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Required two-step.** Phase 12 B: a workspace owner can require every member to have two-step verification (TOTP) or at least one passkey — blocked, never removed, the Slack/Google-Workspace model: a member without it stays a member but every workspace page and procedure refuses them until they set one up. Migration `0030_workspace_require_two_factor` adds `workspaces.require_two_factor INTEGER NOT NULL DEFAULT 0 CHECK (require_two_factor IN (0, 1))`, the repo's usual boolean pattern (`requiresTwoFactor`, like `webhook_endpoints.enabled`). `satisfiesTwoFactor(user, passkeyCount)` (`apps/api/src/access.ts`) is the one rule — `two_factor_enabled_at` not null, or `passkeyCount > 0` — judged fresh from the row and the passkey count this request just read, never from how the session signed in; `blockedByTwoFactor(db, workspace, user)` wraps it, reading the passkey count only when the workspace requires it and two-step is off. The router's `member(min, { twoFactorExempt? })` middleware applies it after the membership and role checks — a viewer refused on an admin procedure still sees "Requires the admin role" first, since the caller is a member either way and nothing leaks — throwing `FORBIDDEN` with `data: { reason: "two_factor_required" }` and `apiMessage(context, "workspaceTwoFactorRequired", { workspace })` ("Turn on two-step verification to access {workspace}." en + sv). Exempt, so a blocked member can always fix it or leave: `workspaces.list`, `workspaces.create`, `workspaces.leave` (`twoFactorExempt: true`; its last-owner rule is unchanged), `invitations.preview` / `accept` / `acceptById`, and every `account.*` / `auth.*` procedure — none of these use `member`. Every other `member` procedure is blocked: notes, workspace get/update/delete/transferOwnership, members, invitations, logo, API keys, webhooks, activity, billing. Impersonation follows the member: an impersonation session of a blocked member is blocked too, even when the impersonating admin's own account satisfies it — no support bypass. Realtime: `GET /events/workspaces/:id`'s `authorize` returns `403` with the plain-text body `two_factor_required` (`cache-control: no-store`; no oRPC JSON shape, since the relay drops bodies anyway) under the same rule, checked on connect and on the existing 60 s recheck, so turning two-step off, removing the last passkey or the requirement turning on all close an open stream; a non-member still gets `404`. `@repo/session`'s relay (`createEventsRoute`) adds `403` to `PASSTHROUGH_STATUSES` and passes it through unread. `apps/app`'s `LiveNotes` treats a `403` as a permanent refusal (`refusalFor` → `"twoFactorRequired"`), stopping reconnection and showing a translated notice instead of retrying. `/api/chat`'s `chatEntitlementGate` checks `workspace.requireTwoFactor && user.twoFactorSatisfied !== true` before the plan check (fails closed on a caller that doesn't say), answering `403` "Turn on two-step verification to use chat in this workspace" (en + sv) — closing the gap the exempt `workspaces.list` would otherwise leave open to a direct `/api/chat` call. `/v1` (API keys) and outgoing webhooks are unaffected: machine credentials whose creation already needed an admin. `workspaces.security.get({ workspaceId })` (`member("admin")`, every plan) returns `{ requireTwoFactor, membersWithoutTwoFactor }`; `workspaces.security.set({ workspaceId, requireTwoFactor })` (`member("owner")`, every plan, refused while impersonating) turns it on or off. Turning it on while the owner does not satisfy it themselves is `FORBIDDEN` `data: { reason: "owner_two_factor" }` ("Turn on two-step verification for your own account first."); a no-op (already that value) writes nothing. A real change is one transaction: a conditional `UPDATE … WHERE require_two_factor <> v` (so of concurrent identical changes only one writes), `auditWorkspace` as `workspace.two_factor_requirement_changed` (`metadata: { enabled }` — see **Activity log.**), then, only when turning on, a `workspaceTwoFactorRequired` mail (`@repo/email`, en + sv, saved locale else English, naming only the workspace, link to `${ACCOUNT_URL}/security`), alongside a `workspace.two_factor_required` notification (Phase 13 A, see **Notifications.**), to every member who does not satisfy it, excluding the caller — all in the same transaction, so a failed enqueue rolls the change back. `members.list` gains `twoFactor: boolean | null` per member, `null` below `admin` (the same rule as email); `invitations.preview` gains `requireTwoFactor`, shown on the invitation landing page as "This workspace requires two-step verification." `apps/account`'s Workspace page gets a **Security** card (`WorkspaceSecurityCard`) directly above API keys: owner, a checkbox and **Save security setting**; turning it on is a two-click, no-JavaScript confirmation naming how many members would be blocked (read fresh from `security.get`) with **Turn on requirement** and **Keep it off** (named apart from the API keys/webhooks rows' armed **Cancel**, which can be on screen at the same time); admin, the state and count read-only ("Only the owner can change this."); below admin, the state only; impersonating owner, read-only. The members list shows a "No two-step" badge for admin and up, `null` (hidden) below it. The Security page warns, before the action — which stays allowed either way — when turning two-step off or removing the last passkey would leave the account unable to satisfy a workspace that requires it (`requirementWarnings`, naming those workspaces). `@repo/ui/blocks/two-factor-required-notice` (`TwoFactorRequiredNotice`, props only, no client hooks) replaces the page — `apps/app`'s `/notes` and `/chat`, `apps/account`'s `/workspace` and `/payments` — for a blocked member, rendered server-side from `blockedByTwoFactor(workspace, user)` (`@repo/session`): a link to set up two-step, the app's own **Switch workspace** (or **Create another workspace**) and **Leave workspace** controls, and no redirect — after setting it up, the member reloads the page themselves. Accepted race: the owner's self-satisfaction check runs outside a lock, so a concurrent self-disable of the owner's own two-step can still let the requirement turn on; the owner is then blocked like anyone else and recovers through the exempt `account.*` procedures (turning two-step back on, or registering a passkey). Likewise `security.set` does not re-read the caller's role inside its transaction, so a concurrent `transferOwnership` can let the former owner (now an admin) flip the setting once; the change is audited like any other. Basis (checked 2026-10-20): OWASP's Zero Trust Architecture and MFA Cheat Sheets ("MFA for everyone"; a lost-factor recovery that must exist without becoming a bypass); NIS2 (Directive (EU) 2022/2555) Art. 21(2)(j) (multi-factor authentication among the measures essential/important entities must take); the Dutch DPA's z2018-02009 (single-factor authentication to sensitive personal data insufficient under GDPR Art. 32) and Art. 5(1)(c) (the members-list status is yes/no only, never the factor, device or recovery state); research on mandatory vs. optional MFA uptake and risk communication (Kamar et al., *Crime & Delinquency* 2026; Das et al. 2021).
