# Passkeys

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Passkeys.** WebAuthn sign-in (`@simplewebauthn/server` in `apps/api`, `@simplewebauthn/browser` in `apps/auth` and `apps/account`, both `catalog:`): a passkey signs in on its own and counts as **both** factors, so `auth.passkey.verify` never returns a two-factor challenge, even for an account with two-step verification on. Migration `0024_passkeys` adds `passkeys` (`id`, `user_id` — no FK, like every other user-owned table here — `credential_id` TEXT UNIQUE base64url, `public_key` TEXT base64url COSE, `counter`, `transports` JSON text or null, `name`, `created_at`, `last_used_at`, indexed on `user_id`) and gives `tokens` a `passkey_challenge` purpose (the same CHECK-constraint rebuild `0013` used) plus a nullable `ceremony` column (`register` | `authenticate`, every other purpose leaves it null) so one purpose value can back two ceremonies that can never redeem each other's challenge. **Relying party.** `PASSKEY_RP_ID` (env; unset → `SITE_DOMAIN`, else `brand.localhost`) is the registrable domain shared by every subdomain app, and the api refuses to start unless it equals, or is a parent domain of, both the `AUTH_URL` and `ACCOUNT_URL` hosts (a mismatch would otherwise fail every ceremony in the browser exactly like a cancelled prompt; Compose's api passes `${PASSKEY_RP_ID:-${SITE_DOMAIN:-localhost}}` for its plain-localhost defaults); `PASSKEY_RP_NAME` (unset → `BRAND_NAME`) is what the browser's prompt shows; the expected origins are only the `AUTH_URL` and `ACCOUNT_URL` origins, deduplicated — a wrong origin or RP ID is refused, never a 500. User verification is `required` (tightened from the library's `preferred` default once its v13 behaviour was checked — a security key with no PIN is refused, since a passkey must stand in for both factors), attestation `none`, resident key `required` (discoverable: `auth.passkey.options` names no user, the credential itself does, so sign-in needs no `allowCredentials`). **The challenge.** `challengeId` is the WebAuthn challenge itself (32 random bytes, base64url); only its hash is stored, in a single-use `tokens` row, 5 minutes (`PASSKEY_CHALLENGE_TTL_MS`) — `register` bound to the caller's `user_id`, `authenticate` unbound. `tokens.consume` spends it atomically before anything else is checked, so a replayed or concurrently-raced assertion can win at most once. **The counter.** `counterAdvances(stored, next)`: an authenticator that keeps a counter (either side non-zero) must report one strictly greater than last time, or the attempt is refused and recorded (`recordFailure("passkey counter did not increase", …)`) — a cloned authenticator's tell; both sides zero (a passkey that keeps none) is accepted. **Sign-in.** `auth.passkey.verify` applies everything `auth.signIn` applies after its password check except the code step: a deletion-scheduled account signs in (to cancel), impersonation never originates here, and it shares the `passkey:<x-api-client-id>` limiter (10 per 15 minutes) plus the general per-client cap — there is no api-wide sign-in cap to join, since `auth.signIn` itself has only a per-email one (a signature cannot be brute-forced, so this was judged an acceptable gap, documented rather than closed with a new global limiter). Once the signature verifies, recording the use and issuing the session share one transaction that locks the user row first — the same order `admin.users.removePasskeys` takes — so a concurrent admin removal either commits first (and the `recordUse` update, matching the row by id, then finds it gone) or waits for this commit and deletes the session it just made: no session outlives a removal racing it on either engine. **Registering** needs the same fresh-credential gate two-step setup uses (`requireFreshCredential`, shared by both): the current password on an account that has one, else a session under `REAUTH_WINDOW_MS` on a passwordless one — `FORBIDDEN` `data.reason: "reauth"` / `UNAUTHORIZED` `data.reason: "password"` — and is refused outright while impersonating (`account.passkeys.registerOptions`, `register`, `rename` and `delete` all throw `FORBIDDEN` "Not available while impersonating"; `list` stays readable). **The cap.** An account may hold at most `MAX_PASSKEYS` (10) passkeys: `registerOptions` checks the count first, before the password/reauth check, so a full account spends no password attempt on a doomed request (`CONFLICT` `PASSKEY_LIMIT_MESSAGE`, "You can have up to 10 passkeys. Remove one to add another."); `register` re-checks it, race-safe, inside the same transaction that locks the user row and inserts (the lock order every writer below uses), so two concurrent registers at 9 can never both land a 10th row — the second counts the first's committed insert. `PasskeysCard` shows the explanation in place of **Add a passkey** once the list reaches the cap. **The last way in.** `account.passkeys.delete` refuses (`CONFLICT` `PASSKEY_LAST_WAY_IN_MESSAGE`) to remove a passwordless, provider-less account's only remaining passkey — decided inside a transaction that locks the user row first, so two concurrent deletes of the account's last two passkeys cannot both pass. `account.identities.disconnect` applies the mirror rule: disconnecting a passwordless account's last provider is refused (`FORBIDDEN` `lastSignInMethod`) only when it also has zero passkeys — a passkey counts as a way in there too — decided under the same user-row lock `account.passkeys.delete` takes, so disconnecting the last provider and deleting the last passkey at the same moment cannot both succeed. An admin's `admin.users.removePasskeys` carries no last-way-in rule: it strips every passkey unconditionally (superadmin only, never self or another superadmin, reason 3–200, limited `removepasskeys:<adminId>` 10/hour), because removing all of them never locks the account out — a password or a magic link to its verified email still gets it back in — it just ends the shortcut. It does so in one transaction, the user row locked first (the same order sign-in's own transaction above takes): lock, delete every passkey, void any outstanding register challenge, then end every session (stamping `sessions_revoked_at`) in the same transaction — so a sign-in racing the removal never keeps a session past it — and audits `user.passkeys_removed`. **Squatter passkeys.** Two rulings close the pre-account-hijack hole a passkey would otherwise leave open: `purgeUnverifiedAccount` (provider linking and magic-link consume into an unverified account) now also deletes the user's passkeys and voids their open `passkey_challenge` tokens — in a transaction that locks the user row first, like every writer above, so a passkey sign-in racing it either commits first (and the purge deletes its new session) or waits and finds no passkey — and `auth.resetPassword` does the same, inside the reset's own transaction, when the account's email is still unverified (a reset proves the mailbox, like a magic link) — a verified account's passkeys are untouched by either path. **Mail.** Three templates: `passkeyAdded` and `passkeyRemoved` (self-service, naming the passkey) and `passkeysRemoved` (admin removal — plural, since it always removes every one and ends every session, so it needs no name to interpolate) — en and sv, tested, with Storybook stories. **Privacy.** The data export lists each passkey's `name`, `createdAt` and `lastUsedAt` only, never the credential id or public key; `users.purge` deletes them outright. `User.passkeys` (a count) flows into every place a `User` is built, for the UI badge. **UI.** `apps/auth`'s `/login` gets `PasskeySignIn`, a client component absent without JavaScript (the page is otherwise unchanged): a **Sign in with a passkey** button, plus a quiet conditional-mediation (autofill) ceremony on mount where the browser supports it; the email input gets `autocomplete="username webauthn"`; a cancelled ceremony shows a neutral status, any other failure the same `passkeyFailed` sentence the api itself uses. `apps/account`'s Security page gets a **Passkeys** card: list, rename inline, a two-click **Remove** (arm, then confirm), and **Add a passkey** (absent without JavaScript, gated by the same password/reauth prompt as two-step setup) — read-only while impersonating. A successful removal moves focus to the card's title (`SettingsCard`'s optional `titleId` prop gives it `id` + `tabIndex={-1}`, focusable from script but never a tab stop) rather than leaving it on a now-removed row's button; a refusal leaves focus where it was. `apps/auth`'s `/admin/users/<id>` always shows a **Passkeys** card (the count, even at zero) with **Remove passkeys** (a reason) once there is at least one. **Testing.** `apps/api`'s test suite drives a software WebCrypto authenticator (real `attestationObject`/`authenticatorData`/`clientDataJSON`, `none` attestation) through register and sign-in, including wrong origin/RP ID, replayed/expired/wrong-ceremony challenges, the counter rule, the last-passkey rule, impersonation, a 2FA account's passkey sign-in skipping its code step, limiters, purge and export; `apps/e2e/tests/passkeys.spec.ts` drives Playwright's Chromium virtual authenticator over CDP (`WebAuthn.addVirtualAuthenticator`) through add → rename → remove and a full sign-out/sign-in-by-passkey journey on a two-step-enabled account. See `docs/guides/passkeys.md`, `apps/api/README.md`, `apps/auth/README.md` and `apps/account/README.md`.
