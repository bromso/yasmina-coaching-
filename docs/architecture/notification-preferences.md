# Notification preferences

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Notification preferences.** Phase 13 B: which notification types also reach a person by email — the in-app inbox above always receives every type regardless. Migration `0033_notification_preferences` adds one table, `notification_preferences` (`user_id`, `type`, `email_enabled` INTEGER 0/1 CHECK, `updated_at`; PRIMARY KEY `(user_id, type)`) — no FK, no `CHECK` on `type` (the procedures only ever write an optional type) and **no row for a user and type means that type's default**, so a new account and a new optional type both need no backfill. `NOTIFICATION_EMAIL` (`@repo/api-contract`'s Zod-free `./notifications` subpath, alongside `NOTIFICATION_TYPES`) splits the seven types into `locked` — `invitation.received`, `workspace.two_factor_required`, `export.ready`, `webhook.disabled`; mailed exactly as they always were, never opt-out-able, since each keeps an account or its workspaces working — and `optional` — `member.role_changed`, `member.removed`, `plan.changed`; `NOTIFICATION_EMAIL_DEFAULT` is `true` for all three. `account.notificationPreferences.get()` (⚑) returns every type, optional ones first (each the stored row else the default) then the locked ones (always `{ email: true, locked: true }`); `.set({ type, email })` (⚑, `SetNotificationPreferenceSchema` typing `type` to `z.enum(NOTIFICATION_EMAIL.optional)` so a locked type never parses) writes inside a transaction — an UPDATE only when the stored value differs, else an `INSERT … ON CONFLICT DO NOTHING` only for a non-default value, so a no-op write and a race between two identical concurrent sets each audit `user.notification_email_changed` `{ type, email, via: "settings" | "link" }` exactly once — refused while impersonating. `notifyUser` (see **Notifications.**) gains one step for an optional type: inside the same transaction that inserts the in-app row, `enqueueNotificationEmail` reads the recipient's preference (default on), and **only when it is on and the recipient's own email is verified** — an address nobody has proven to own is never mailed anything it did not ask for, even an opt-out-able one — reads their name and saved locale (else English) and enqueues a `mail.send` job for one of three new `@repo/email` templates, `roleChanged` (`workspaceName`, `role`), `removedFromWorkspace` (`workspaceName`) or `planChanged` (`workspaceName`, `plan`); each shares `NotificationFooter` (an inbox button, a visible `List-Unsubscribe` link and "Turn off these emails") and carries no other member's address. A rolled-back change therefore enqueues no mail, exactly like the in-app row. The mail seam's `Message` (`apps/api/src/mail/mailer.ts`) gained `headers?: Record<string, string>`, passed through as-is by `smtp` (Nodemailer's own `headers` option) and `resend` (its `headers` field, not an HTTP header) and recorded verbatim by `log` and `file`; every other mail passes none. Only an optional-type mail carries `List-Unsubscribe: <${AUTH_URL}/email/unsubscribe/one-click?token=…>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) — a locked mail (and every other template) carries neither header. **The token** (`apps/api/src/notification-email.ts`): `base64url(payload).base64url(mac)`, `payload` = `<userId>.<type>.1` (the trailing `1` a version), `mac` = HMAC-SHA256(payload) under a key derived from `TWO_FACTOR_ENCRYPTION_KEY` with `hkdfSync("sha256", key, <empty salt>, "notification-unsubscribe-v1", 32)` — HKDF, not a raw or re-hashed key, and under its own fixed `info` label, so the TOTP-encryption key is never reused for anything else and no new env var is needed (RFC 5869 §3.1 allows the empty salt because the input key is already uniformly random). `verifyUnsubscribeToken` rejects anything not strict, canonical base64url (so a re-padded or alternately-encoded twin of a real token fails), compares the mac with `timingSafeEqual` on equal-length buffers, and only then parses the payload — **never expires** (it works until the key rotates) and names exactly one user and one optional type; a correctly signed token for a locked type, another version or a malformed payload is invalid. `auth.notificationEmail.peek({ token })` (anonymous, read-only) answers `{ type } | null` — null for a bad token or one whose user was purged, the same shape either way, so loading the confirm page unsubscribes nobody and tells a scanner nothing. `auth.notificationEmail.unsubscribe({ token })` (anonymous) sets that type off in a transaction for a valid token and **always answers `{ ok: true }`**, for a bad token too, so the outcome is never an oracle. Both verify the token first (one HMAC, constant time): a forged token answers at once — `{ ok: true }` or `null`, exactly as a good one would — spends no budget and changes nothing; only a token that verifies spends the two limits, `notification-email:<clientId>` (default 60/10 min) then api-wide `notification-email:global` (default 1000/10 min) — `TOO_MANY_REQUESTS` on either. `apps/auth`'s `POST /email/unsubscribe/one-click?token=…` is the RFC 8058 endpoint a mail client posts to: it never reads the body (any body, or none, works — only the query's token matters), keys its client id on `unsubscribeTokenClientId(token)` (`@repo/session/client`: `unsub:` + the first 32 hex of `sha256(token)`) rather than the poster's ip, because Gmail/Yahoo/etc. post one-clicks from shared provider egress addresses where a per-ip bucket would refuse real unsubscribes at scale — since the api spends a budget only on a token that verifies, that is one bucket per real link (an invented token spends nothing), and the api-wide cap bounds the total across real links. It maps the api's answer to: a good token or a `BAD_REQUEST` (malformed/unknown) both to a blank `200` (so the response is never an oracle either), `TOO_MANY_REQUESTS` to `429` (honest; RFC 8058 senders may retry), and an unreachable api or missing env to `503` — never a redirect, since RFC 8058 clients do not follow one. It sits deliberately **outside `assertSameOrigin`**: a mail provider posts cross-site with no cookie and no Origin to check, and this is safe to leave open because the only effect is turning one optional type off for the one user the signed token names — idempotent, never a sign-in, never a locked type. `GET` on the same path is a `303` to the confirm page with the same token, making no api call. The confirm page, `/email/unsubscribe?token=…` (`unsubscribeClientId(ip)`, a person's browser), calls `peek` on load and renders one of three states — `valid` (the type named in a sentence, then **Turn off these emails**, a server action, so the link itself never unsubscribes anyone), `invalid` (a neutral "isn't valid any more" note with a sign-in link), or a distinct **`unavailable`** state (rate-limited, the api down, or env missing: a short "couldn't load this right now, try again" note, no button, nothing about the token) — because `peek` shares the same limits as `unsubscribe` (for a token that verifies), and an outage must never be shown as if the link were dead. `apps/account`'s `/notifications` page gets an **Email** card: one checkbox per optional type (`NOTIFICATION_EMAIL.optional` order, works with no JavaScript — a hidden `type` field per type plus a hidden `wasEmail` for whichever were on at render, so the action sends only the types that changed), **Save email settings** (the action `refresh()`es whatever the outcome, so a failed or partial save never leaves stale boxes), a "Verify your email address to get these emails." note linking to Personal info when the address is unverified, and the four locked types listed read-only underneath ("Always emailed — needed to keep your account and workspaces working."); disabled while impersonating like every other settings control. The privacy export lists `notificationPreferences: [{ type, email, changedAt }]` for the optional types only (a locked type is always on, so it is left out); `users.purge` deletes a user's rows outright. **Limitations, documented rather than fixed:** an unverified address gets no optional email at all (only a verified mailbox is trusted with an opt-out-able notice); `plan.changed` mail depends on the billing provider — the billing mirror never mails the actor, so with the mock provider an in-app plan change never mails anyone (a workspace has exactly one `owner`, the only one who may change the plan, and that owner is the actor), while with `BILLING_PROVIDER=stripe` every change, an in-app checkout included, arrives through the provider's webhook, whose actor is `{}`, so every owner is mailed, the one who just paid included; and forged tokens cost one HMAC each and spend nothing, while real tokens are bounded per link (60/10 min) and api-wide (`notification-email:global`, shared by `peek` and `unsubscribe`), so a burst of genuine one-clicks past 1000 in 10 minutes is answered `429` until the window passes. Basis (checked 2026-10-21): Context7 `/websites/resend` and `/websites/nodemailer` (RFC 8058's header pair, honouring a one-click request within 48 hours, keeping a visible unsubscribe link in the body) and Directive 2002/58/EC (ePrivacy) Art. 13 (an opt-out on a service notification about the recipient's own account is a courtesy and a deliverability measure, not a consent requirement, and locking essential mail is lawful).
