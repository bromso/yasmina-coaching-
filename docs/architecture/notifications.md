# Notifications

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Notifications.** Phase 13 A: a per-user in-app inbox for the things that happened *to* the signed-in person — never "someone joined" noise, that stays the activity log's job; calm by design, a badge and an inbox, no toasts, pop-ups or sounds. Migration `0032_notifications` adds one table, `notifications` (`id`, `user_id` NOT NULL, `workspace_id` nullable, `type`, `data` JSON text, `created_at`, `read_at` nullable) — neither id column a foreign key, like every other user-owned table here — with three indexes: `notifications_user_created` `(user_id, created_at)` (the list, newest first), `notifications_user_read` `(user_id, read_at)` (the unread count) and `notifications_created_at` `(created_at)` (the nightly prune's range scan). `type` carries no `CHECK`: a later type is then a code change, not a table rebuild on SQLite, since `notifyUser` validates every type and its `data` against the contract before it writes. `NOTIFICATION_TYPES` (`@repo/api-contract`'s Zod-free `./notifications` subpath, so a client bundle never pulls in zod or the contract for the type list alone) names seven: `invitation.received`, `member.role_changed`, `member.removed`, `workspace.two_factor_required`, `export.ready`, `webhook.disabled`, `plan.changed` — each with its own strict schema in `notifications-schema.ts`, and every one holds ids and display names only (a workspace name, a role, a plan, an endpoint's host) — **never an email address, a token or a secret**. `notifyUser(ctx, userId, type, data, { tx?, workspaceId? })` (`apps/api/src/notifications.ts`) parses `data` against that schema, inserts the row — on `tx` when given, so a rolled-back change creates nothing — and registers `db.afterCommit(() => publishAfterCommit(ctx, userChannel(userId), { type: "notification.created", id }))` (`Queries.afterCommit`, `db.ts`: queues on the outermost `db.transaction`, runs once `sql.begin` resolves, drops on rollback; on the pool it runs at once), so the announcement only fires once the row is durable and is fire-and-forget like every other `publishAfterCommit` call — a failed publish never fails the change. An after-commit callback that throws is caught and logged ("db: an after-commit callback threw") rather than left to roll back a transaction that already committed, and the remaining callbacks still run. `isActor(context, userId)` — the session's own user, or, on an impersonation session, the impersonating admin — is how every emitter below skips telling someone about their own action, including on an impersonator's behalf. Emitters, each inside the change's own transaction, one notification per recipient: `invitations.create` (and a re-invite) tells the account already holding the invited address `invitation.received` **only once that account's email is verified** — the same rule `workspaces.list`'s pending invitations already use, so whoever pre-registered someone else's address unverified never learns what it is being invited to — and nothing when no account holds the address. `members.setRole` tells the target `member.role_changed` (unless the target is the actor, or the change is a no-op); `workspaces.transferOwnership` tells the new owner the same way (`from` their previous role, `to: "owner"`) since the former owner made the change, including their own demotion, and so gets nothing. `members.remove` tells the removed member `member.removed`, never on a leave or a self-removal. `workspaces.security.set` turning a workspace's two-step requirement on tells `workspace.two_factor_required` to every member who does not yet satisfy it, alongside the existing `workspaceTwoFactorRequired` mail (see **Required two-step.**) — never the caller, and never an impersonator acting for them. The `privacy.export` job tells `export.ready` on success, inside the transaction that marks the export ready. A webhook endpoint's auto-disable (`failures` or `gone`) tells every owner `webhook.disabled` with the host and the reason. The billing mirror (mock and Stripe alike) tells every owner but the one who made the change `plan.changed` with the new plan; a provider webhook carries no actor, so it tells every owner — **a real Stripe checkout therefore produces a self-notification to the owner who checked out**, a known, accepted gap (the mock and the in-app change both skip the actor correctly); a cancellation right before the workspace is deleted (`actor === null`) tells nobody, like the activity log. `notifications.list({ cursor?, limit? 1–50 default 20, unreadOnly? })` (⚑) returns the caller's own rows only, newest first, keyset on `(created_at, id)`; `workspaceId` comes back only while the caller is still a member of that workspace, else `null`, so a notification about a workspace the user has since left never links back into it. `notifications.unreadCount()` (⚑) counts through a capped subquery (`NOTIFICATION_UNREAD_CAP` (99) + 1), so the UI shows `99+` without the api ever counting an unbounded backlog. `notifications.markRead({ ids: 1–100 } | { all: true })` (⚑) marks only the caller's own rows (another user's ids are silently ignored, never an oracle) and is refused while impersonating (`FORBIDDEN` "Not available while impersonating"), so support can never clear a user's badge; idempotent either way. Reads stay open while impersonating — the admin sees what the user would see — only marking is blocked. `notifications.prune` (`5 4 * * *`, see **Jobs**) deletes every read notification older than `NOTIFICATION_READ_RETENTION_DAYS` (30) days and every notification, read or not, older than `NOTIFICATION_RETENTION_DAYS` (90) days, in one range over the `notifications_created_at` index. The privacy export's `notifications` list (type, created, read, data) is read with the same explicit-column discipline as every other export section (see **Privacy**); `users.purge` deletes a user's rows outright. Three of these seven types — `member.role_changed`, `member.removed`, `plan.changed` — can also arrive by email, on by default and switched off per type; see **Notification preferences.** below. `userChannel(id)` = `user:<id>` is a new channel on the same `Broadcaster` every workspace channel uses; `GET /events/me` shares `createStreamHandler`'s `openStream` helper with `/events/workspaces/:id` (the guard, the limiter, session resolution, idle-timeout handling, the ping, the 60 s re-check, a `resync` on connect) but **keeps its own per-session (5) and per-user (10) counters**, apart from the workspace stream's — counting the two kinds together would halve how many `/notes` tabs fit in one session, since each tab then opens two streams — while the process-wide `REALTIME_MAX_STREAMS` cap stays shared by both kinds (see **Realtime**). It sends no presence. An impersonation session hears the impersonated user's own channel, never the admin's, and counts against the admin's caps; stopping the impersonation ends the stream. `@repo/session`'s `createUserEventsRoute` relays `apps/api`'s `GET /events/me` exactly as `createEventsRoute` relays the workspace stream (service token, session token, an `events:<ip hash>` client id, the request id, the browser's disconnect aborting upstream, the body streamed through unread) but with no workspace involved, and **passes an upstream `401`/`403`/`404`/`429`/`503` through with that exact status** rather than remapping any of them to `502` — the same set `createEventsRoute` relays, so a client stops for good on `401`/`403`/`404` either way; `apps/app`'s `src/app/api/events/me/route.ts` is the few lines over it. `createAuth(...)`'s `unreadNotificationCount()` is the header bell's count, read once per request (`cache`-wrapped), a plain `fetch` with no `x-locale` (a bare number needs none, nor would resolving one be worth its cost): `null` when signed out, when the api refuses (an expired session reads as the ordinary signed-out case, unlogged), fails, or does not answer within `UNREAD_COUNT_TIMEOUT_MS` (2 s, logged in every other failure case) — **it never throws**, so a layout always renders the bell, just without a badge, rather than breaking the page, on every signed-in page including one a workspace's two-step requirement blocks. `@repo/ui`'s `NotificationBell({ count, href, label, liveLabel? })` is a server component with no client hooks: a link with an inline SVG icon, an `aria-hidden` badge (`notificationBadge(count)`, `99+` above the cap, nothing at all for `null` or zero) and a sibling `role="status"` sr-only span (`liveLabel ?? label`, an ICU-plural accessible name such as "3 unread notifications" / "No unread notifications") that announces a changed count politely rather than interrupting — a later re-render (`router.refresh()`, a server action's `refresh()`) is how the badge and the live region update; rendered by `app`, `auth` and `account` in `SiteHeader`'s `end` slot next to `UserMenu`. `apps/app`'s `LiveNotificationRefresh` (root layout, signed-in only) is the one live wrapper: it follows `new EventSource("/api/events/me")` and calls `router.refresh()` — debounced 1 s, so a burst of notifications re-renders the server layout once — on `notification.created`, and on a reconnect's `resync` except the one right after mount, stopping for good on `401`/`403`/`404` like `LiveNotes`; it renders nothing and never shows a toast. `apps/auth` and `apps/account` render the same bell but do not stream: **their count refreshes on a full load and after a server action's `refresh()` (e.g. marking a notification read), not on every client `<Link>` navigation**, since their layouts persist across one. `apps/account`'s `/notifications` page (second in the sidebar, after Home) is the inbox itself: a translated sentence per type built from its own `data`, a link to its target (the workspace page, `/data-privacy`, `/payments`, `/security`, or, for an invitation, `${APP_URL}/workspaces/new` — the notification carries no token, since pending invitations are listed and accepted there) or a `switchTo` form button when the row's workspace is not the current one, unread rows marked, **Mark all as read**, a per-row **Mark as read**, an **Unread only** filter and **Older**/**Newest** paging — the filter and paging plain GET forms and links, **Mark as read**, **Mark all as read** and the cross-workspace open plain POST forms to server actions — so the whole page works without JavaScript; en + sv, the i18n guard, every label unique. Known limitations: on SQLite a dedicated worker builds its own in-process broadcaster, so a job's `export.ready` or `webhook.disabled` publish (`src/worker.ts`) reaches no api process and shows on the signed-in person's next page load rather than live — on Postgres the `NOTIFY` reaches every replica, api and worker alike; the Stripe self-notification above is accepted, not fixed. Basis (checked 2026-10-21): Ohly et al., *J. Occup. Health* 2023 (notifications disrupt task focus; reducing them helps) and Iqbal & Horvitz 2010 (people value notifications for passive awareness, not as a trigger to switch tasks) — hence a passive badge and inbox, never an interrupting toast; the W3C ARIA Authoring Practices (a polite live region announces a changed value without interrupting).
