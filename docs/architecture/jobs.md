# Jobs

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Jobs.** `apps/api` has a durable job queue in its own database, on both engines (migration `0015_jobs`, table `jobs`: `name`, JSON `payload`, `status` one of `queued` / `running` / `succeeded` / `dead`, `attempts` / `max_attempts`, `run_at`, `locked_until`, `last_error` truncated to 2000 characters, `dedupe_key`, a unique index on `dedupe_key` among `queued` / `running` rows only). A job is `defineJob({ name, payload: <Zod schema>, maxAttempts? = 5, timeoutMs? = 60 000, run(payload, ctx) })` in `src/jobs/`, listed in `JOBS` in `src/jobs/registry.ts` like a migration; `ctx` carries `db`, `mailer`, `storage`, `telemetry`, `log`, `recordFailure`, an `AbortSignal` that fires at the timeout, `attempt` and the worker's `now()`. `context.enqueue(def, payload, { tx?, dedupeKey?, runAt? })` validates the payload at enqueue (a bad one throws in the caller) and again at run; `tx` writes the job in the caller's transaction, so the data and its job commit together or not at all; a `dedupeKey` held by a live job makes the enqueue a no-op returning that id (with `dedupeAnyStatus: true`, a row of any status holding it does). Built-in callers enqueue in the transaction where there is one and otherwise await the enqueue right after the committed write, so a failed job insert answers `500` though the write stands (durability over silent loss) — except a failed `storage.delete` enqueue, which is only recorded (the sweep catches it). A throw or a timeout retries at `min(30 s × 2^(attempt−1), 1 h) ± 20 %` and only logs; after `maxAttempts` the job is `dead`, `last_error` kept and the failure recorded through `recordFailure` (log plus a telemetry `server` row); an unknown name or a payload failing the schema at run goes straight to `dead`. Delivery is **at least once**: a claimed batch is locked for the longest registered timeout up to 5 minutes (`LONG_JOB_MS`) plus 30 s, and a crashed worker's `running` rows are reclaimed after it, (that lock is shared by the batch, so raising one job's `timeoutMs` up to 5 minutes delays every crashed job's reclaim; a job longer than that — `backup.run`, 30 minutes — sets no shared lock and has its own row's lock extended to its timeout plus 30 s right after the claim; it is written with the claimer's clock, so keep workers on NTP; a timeout frees the slot but a run ignoring its `signal` keeps going), so built-in jobs are idempotent where it matters (the one-time-link mails — verify, reset, magic link — carry an idempotency key that reaches the mailer and doubles as the dedupe key; `telemetry.forward` sends a deterministic Sentry `event_id`); the other mails (password-changed, two-factor notices, account reset, invitation, waitlist welcome) carry none and may be sent twice after a worker crash or a timeout — the accepted worst case of at-least-once. Success replaces the payload with `{}`; a dead job keeps it for **Retry**, so a `mail.send` payload can hold a live one-time link until the job succeeds or `jobs.prune` deletes the dead row after 30 days (the token itself expires sooner, 15 minutes to 7 days); payloads are never returned by any procedure. The worker (`src/jobs/worker.ts`) runs inside every api process unless `JOBS_WORKER=false`; `src/worker.ts` (bundled as `dist/worker.js`; `bun --filter @repo/api dev:worker` / `start:worker`) runs only the worker and scheduler, migrates on boot and serves `/health` on `HOST:PORT` (default 3007, like the api — give it its own port), for a dedicated container; Compose has it as `api-worker` under the `worker` profile (`JOBS_WORKER=false docker compose --profile worker up -d --build`, see **Docker**). Every `JOBS_POLL_MS` (default 1000) it claims up to `JOBS_CONCURRENCY` (default 4) minus jobs in flight in one `UPDATE … WHERE id IN (SELECT … ORDER BY run_at LIMIT n)` — `FOR UPDATE SKIP LOCKED` on Postgres; on SQLite one statement and one writer per file make the plain form atomic — so two workers never run one job. On SQLite `createDb` holds other statements back while a transaction is open (Bun runs `sql.begin` on the one connection, so they would otherwise run inside it and roll back with it), through a gate in `src/db.ts` (`serialiseSqlite`): a transaction asks for its exclusive lock on the next macrotask rather than synchronously, so a statement already started just before `db.transaction` runs first, outside it, instead of queuing behind it; `sql.transaction` is gated the same way as `begin`, and `file`, `reserve`, `beginDistributed` and `distributed` throw — none of them goes through the gate. What remains — a statement queued behind an open transaction that then runs no statement for `SQLITE_GATE_WAIT_MS` (30 s) — fails with a "waited … behind an open SQLite transaction" error and the transaction rolls back; the clock resets on every statement the transaction runs, and is never armed behind the startup pragmas or a transaction still in `BEGIN IMMEDIATE`, so a slow but progressing transaction, or one blocked at `BEGIN IMMEDIATE` behind another process, never trips it. A pragma failure is logged (an error line, `SQLite pragmas failed`) rather than thrown, so the statements behind it fall back to Bun's defaults (no busy timeout, no WAL). A file database opens in WAL mode with `busy_timeout` 5000 and `BEGIN IMMEDIATE` transactions, so the api and a dedicated worker can share one file; a waiting writer blocks its event loop, so use Postgres for several replicas; an enqueue in the same process wakes it at once, except one inside a `tx`, which the next poll picks up (within `JOBS_POLL_MS`). Shutdown stops claiming the moment it begins (the lifecycle's `onShutdown`) and drains jobs alongside HTTP within `drainMs`; what is still running is reclaimed once its lock passes. A worker that claims a name it does not know kills it as `unknown job`, so in a rolling deploy ship workers with or after the code that defines a new job. The scheduler runs in every worker on each minute boundary and enqueues due `defineSchedule({ name, cron, job, payload })` entries (5-field UTC cron: `*`, lists, ranges, steps, day of week 0/7; parsed at import) with dedupe key `schedule:<name>:<YYYY-MM-DDTHH:MM>` and `dedupeAnyStatus` (a finished run still holds its minute), so any number of schedulers enqueue a run once. Built-in: `tokens.prune` `0 * * * *` (used or expired one-time tokens, replacing the request-path prunes), `telemetry.prune` `5 * * * *` (replacing the prune on ingest), `jobs.prune` `15 3 * * *` (`succeeded` after 7 days, `dead` after 30), `storage.sweep` `30 3 * * *` (avatars, logos and ready-export files no row references, older than 24 h, through `Storage.list`; one lookup per 100 keys; stops when its signal aborts; paused by `STORAGE_SWEEP_ENABLED=false`), `analytics.rollup` `10 0 * * *` (rebuilds `analytics_daily` for yesterday and the day before, so an event that landed after its day's first rollup is picked up the next night; a `{ day }` payload rebuilds that day only), `analytics.prune` `20 0 * * *` (raw analytics rows past `ANALYTICS_RETENTION_DAYS`, floored at the oldest day `analytics.rollup` still rebuilds, salts before today), `privacy.export.prune` `40 3 * * *` (every `ready` export past its 7-day `expires_at` to `expired`, queuing its file for `storage.delete`, and every export still `pending` a day after its request — its job died — to `expired`), `privacy.purge` `25 * * * *` (purges every user whose requested deletion's 7-day grace period has passed; see **Privacy**) and `applications.prune` `50 3 * * *` (deletes every job application past its 6-month `delete_after` and queues its CV for `storage.delete`, in one transaction per row; see **Hiring**), `audit.prune` `45 3 * * *` (deletes rows past `AUDIT_RETENTION_DAYS`, then strips `ip`/`user_agent` past `AUDIT_PII_RETENTION_DAYS`, both keyset-batched by id, the default 60 s `timeoutMs` with a 48 s budget; see **Audit retention and export**), `webhooks.prune` `55 3 * * *` (deletes `webhook_deliveries` rows older than 30 days; see **Webhooks**), `notifications.prune` `5 4 * * *` (deletes every read notification older than 30 days and every notification, read or not, older than 90 days; see **Notifications.**) and `backup.run` `0 2 * * *` (off unless `BACKUP_ENABLED=true`, checked on every tick: dumps the whole database to the storage seam under `backups/<date>/<engine>-<time>.jsonl.gz`, then deletes its own objects there past `BACKUP_RETENTION_DAYS`; sets `backup_last_success_timestamp_seconds` on success — see **Operations** and `docs/guides/operations.md`). The sweep deletes what *its own* database does not reference, so **one bucket per environment**: staging and production (or a local `dev:worker` with production credentials) sharing a bucket delete each other's files — keys carry no environment prefix. On the queue: every mail (`mail.send`), every storage delete (`storage.delete`), every outgoing webhook delivery (`webhook.deliver`, see **Webhooks**), Sentry forwarding (`telemetry.forward`, only when the provider is not `store`), every product event (`analytics.event`, enqueued by `recordEvent`), analytics forwarding (`analytics.forward`, only when `ANALYTICS_PROVIDER` is not `store`), the analytics rollup and the prunes. `detach()` remains only for the two silent mail enqueues (`auth.requestPasswordReset`, `auth.magicLink.request`, equal timing) and for telemetry's own `recordServerError` (never awaited on the caller's path). Superadmins see the **Background jobs** card on `apps/auth`'s `/admin`: `queued` / `running` / `dead` counts and the 20 most recently dead jobs (name, attempts, last error, when) with **Retry** (back to `queued`, `attempts` 0, `run_at` now; `CONFLICT` "A newer copy of this job is already queued" when a newer live job holds its dedupe key) and **Discard** (delete) — `admin.jobs.list` / `retry` / `discard`, `NOT_FOUND` to anyone else, the writes audited `job.retried` / `job.discarded`. Tests run with the worker off and call `drain()` (`src/test-server.ts`); `apps/e2e`'s api runs the in-process worker. The worker also takes per-name caps (`nameLimits`, `{ [jobName]: limit }`): each capped name is claimed in its own statement up to what its cap leaves, then every other name for the remaining slots, each claim still one atomic statement — today only `webhook.deliver`, at `WEBHOOK_CONCURRENCY` (see **Webhooks**). Out of scope: exactly-once, priorities, chains, a hosted runner. Defining jobs, schedules, a dedicated worker and dead jobs: `docs/guides/background-jobs.md`. See `apps/api/README.md` and `apps/auth/README.md`.
