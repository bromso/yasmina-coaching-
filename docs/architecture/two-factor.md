# Two-factor

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Two-factor.** Two-step verification is an authenticator app (TOTP: RFC 6238, SHA-1, 6 digits, 30 s, through `@oslojs/otp`) plus ten single-use recovery codes, for every sign-in method: once a user turns it on, `auth.signIn`, `auth.magicLink.consume` and `auth.oauth.callback` answer `{ twoFactor: { challenge, expiresAt } }` instead of `{ user, session }` (`SignInResultSchema` in `@repo/api-contract`, with `isTwoFactorChallenge`), after everything they already did (password check, unverified-account purge, provider linking, limiters). Sign-up and admin impersonation never challenge. The challenge is a one-time `tokens` row (purpose `two_factor_challenge`, hashed, 5 minutes, bound to the user only); only `auth.twoFactor.verify({ challenge, code, client })` turns it into a session (the session's client info comes from `verify`'s own input), with a TOTP code or a recovery code (`xxxxx-xxxxx`). A wrong code is `UNAUTHORIZED` "That code didn't work. Check your authenticator app and try again."; an unknown, expired or used challenge is `BAD_REQUEST` "Your sign-in timed out. Sign in again.", and the fifth wrong code burns it. Codes are accepted in a ±1-step window, and a step not greater than the last accepted one (`users.two_factor_last_step`) is refused, so no code works twice. `verify` resolves the challenge, the user row's lock, a recovery code and the new session in one transaction — the user row first, the same order `users.revokeSessions` takes, so the two can never deadlock — so only the request that wins the challenge spends a recovery code; a recovery code a concurrent request already spent rolls that transaction back, and the attempt is answered as an ordinary wrong code (`UNAUTHORIZED`), the challenge still live. `users.sessions_revoked_at` (migration `0018_sessions_revoked_at`) is stamped by every path that ends *all* of a user's sessions — `users.revokeSessions` (full: `auth.resetPassword`, `account.changePassword`, **Sign out everywhere else** (`account.sessions.revokeOthers`), `admin.users.revokeSessions` and `admin.users.resetTwoFactor`) or the stamp-only `stampSessionsRevoked` (`account.setPassword`, which ends no session of its own, and the unverified-account purge, which deletes them in its own transaction); ending one session or stopping an impersonation stamps nothing — and `verify` refuses a challenge issued before the caller's current stamp, so a challenge outstanding across any of them can never become a session. In `apps/auth` the password action, the magic link's **Continue** and the provider callback store the challenge in the `two_factor` cookie (host-only on auth, HttpOnly, `SameSite=Lax`, `Path=/`, `Secure` over https, 5 minutes) and redirect to `/login/verify?next=…`: a 6-digit code, or with `?recovery=1` (a link, no JavaScript) a recovery code; a wrong code stays on the page with the cookie, a dead challenge clears it and goes to `/login?error=two_factor_expired`, and success sets the `session` cookie as password sign-in does. `apps/account`'s Security page has the **Two-step verification** card (`account.twoFactor.get/setup/enable/disable/regenerateRecoveryCodes`). Turning it on needs a verified email: `setup` and `enable` answer `FORBIDDEN` "Verify your email to turn on two-step verification" otherwise (whoever proves the mailbox takes an unverified account over, so its 2FA would protect nothing), and the card shows "Verify your email first" instead of **Turn on**. `setup` also re-checks who is asking before minting a secret: the current password, on an account that has one — a wrong one is `UNAUTHORIZED` with `data.reason: "password"` — or, on a passwordless account (nothing to re-verify with), a session under 10 minutes old (`REAUTH_WINDOW_MS`); a stale one is `FORBIDDEN` with `data.reason: "reauth"`, and the card then shows the message with a **Go to sign-in** link to `${AUTH_URL}/login?reauth=1&next=<account>/security`. Three gates share that window, each `FORBIDDEN` with `data.reason: "reauth"` on a session at or past it: `setup` itself (above); `account.setPassword` (passwordless accounts only) — "Sign in again to set a password." (`SET_PASSWORD_REAUTH_MESSAGE`), the Security page's set-password form showing the same link — so an old session cannot set a password and then pass setup's password check; and connecting a provider while signed in, for every account — "Sign in again to connect a sign-in provider." (`CONNECT_REAUTH_MESSAGE`), refused by `auth.oauth.start` when `apps/auth`'s `/oauth/<provider>/start` forwards the browser's session (so the browser is never sent to the provider for nothing; it goes to `/login?reauth=1&next=<next>` instead) and again by `auth.oauth.callback` before anything is written (the session can age past the window during the round trip; same redirect) — so an old session cannot attach its holder's own identity and sign in with that for good. A signed-out provider sign-in is unaffected, and an impersonation session stays refused by the callback. A connect that passes answers with the caller's own session (same token, `created_at` and expiry), never a fresh one, so `apps/auth`'s callback keeps the browser's cookie and no path restarts the window short of signing in again. The `?reauth=1` form's own provider buttons carry `reauth=1` into the `oauth` cookie, so from there a signed-in browser signs in afresh (anonymously, a new session replacing the old) rather than connecting. **Turn on** shows a QR rendered server-side with `uqr` (no third-party QR service) and the key in groups of four, a first code turns it on (`setup` alone never does, so an abandoned setup locks nobody out), and the ten recovery codes show once; **Regenerate recovery codes** and **Turn off** each need a current code; turning it on or off ends no session; read-only while impersonating (the api refuses the four writes, a `FORBIDDEN` each declares). Lost phone: a recovery code, or with none left a superadmin's **Reset two-step verification** on `apps/auth`'s `/admin/users/<id>` (`admin.users.resetTwoFactor`, reason 3–200 chars, never yourself or another superadmin — "A superadmin's two-step verification cannot be reset"; turns it off, ends the user's sessions, audited `user.two_factor_reset`, mails them) — there is no email bypass, and a password reset leaves 2FA on. The secret is stored AES-256-GCM-encrypted (`v1:<iv>:<ciphertext>`) under `TWO_FACTOR_ENCRYPTION_KEY` (32 bytes, base64; required in production, where the api also refuses the public dev key; not derived from `API_SERVICE_TOKEN`, whose rotation would lock every 2FA user out); recovery codes are SHA-256 hashes in `two_factor_recovery_codes`. Migration `0013_two_factor` (the three `users` columns, that table, the token purpose). Limiters, in memory (`FailureLimiter` in `@repo/service-kit`): every code or setup-password check reserves an attempt first (`hit`, so a parallel burst cannot all pass) and gives it back (`refund`) when it is right, so only a wrong code or password stays counted: `2fa:verify:<id>`, 10 wrong codes per 15 minutes against `auth.twoFactor.verify`'s sign-in challenge, and `2fa:manage:<id>`, 10 wrong codes (or setup passwords) per 15 minutes shared by `enable`, `disable`, `regenerateRecoveryCodes` and `setup`'s password check — kept apart so a stolen session cannot spend a sign-in's budget, or the reverse; plus `2fa:challenge:<hash>`, 5 wrong codes per challenge, and `reset2fa:<adminId>`, 10 resets per hour. Enabling, disabling and an admin reset mail the user (`twoFactorEnabled`, `twoFactorDisabled`, `twoFactorReset` in `@repo/email`). A workspace's owner can also require it (or a passkey) of every member — see **Required two-step.**. See `apps/api/README.md`, `apps/auth/README.md` and `apps/account/README.md`.
