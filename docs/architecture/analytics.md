# Analytics

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Analytics.** First-party visitors, pages and the product events that matter (sign-ups, verifications, workspaces, invitations, notes, plan changes), in the api's own database, shown on a superadmin dashboard, with an optional seam to forward the same data to PostHog or Plausible. Product events come only from `apps/api` (authoritative, not blockable, not forgeable, via `recordEvent(context, name, ids, props)` in `src/analytics/record.ts`); pageviews and the one UI-only event come from the browser. The vocabulary is `ANALYTICS_EVENTS` in `@repo/api-contract` (`analytics.ts`): `signed_up` (`method`), `email_verified`, `workspace_created`, `member_invited` (`role`), `invitation_accepted`, `note_created`, `plan_changed` (`plan`, `interval`), `two_factor_enabled`, `lead_submitted` (`audience`, `need`, `timeline` — the contact form's three fixed answers, recorded by `leads.create` with no user or workspace id; see **Leads.**) — all api-only; `email_verified` is recorded wherever an email becomes verified, once per account: `auth.verifyEmail` (its `markEmailVerified` is the one atomic check-and-set — `UPDATE … WHERE email_verified_at IS NULL RETURNING id` — so two concurrent verifications of one account can never both report success, and only the one that does records the event), OAuth and magic-link account creation (created verified) and `purgeUnverifiedAccount` (inside its transaction) — and `pricing_viewed`, the one `client: true` event a browser may send; `analytics.ingest` refuses any other name from a client and any prop not in that event's allowlist (props capped at 1 KB). Visitors are cookieless: `visitor_id` is the first 16 hex chars of `sha256(daily salt + ":" + app + ":" + ip + ":" + user agent)`, the salt random per UTC day (`analytics_daily_salts`, created on first use, deleted the day after by the prune), so a visitor is countable per day and app but never followable across either, and the ip and user agent themselves are never stored. With the `consent` cookie `all` a pageview or client event also carries the signed-in user's id and current workspace id; an impersonation session sends neither (`analyticsIdentity` in `@repo/session`). Storage is migration `0016_analytics`: `analytics_pageviews` (app, collapsed path, referrer host or null — ingest drops one of our own hosts, the `SITE_DOMAIN` parent domain or any `*.<domain>` via `siteDomain()` from `@repo/sites`, so www → app is no referral — visitor id, user/workspace id, day), `analytics_events` (name, source — `api` or the app id — user/workspace id, props, visitor id for a client event, day) and `analytics_daily_salts`, kept `ANALYTICS_RETENTION_DAYS` (default 90); `analytics_daily` (one row per day/kind/app/key, plus a per-app `"*"` key for the days chart's summed-across-apps visitor count) is rebuilt nightly by `analytics.rollup` (`10 0 * * *`: yesterday and the day before, each idempotent, a day with no raw rows left skipped rather than wiped) and kept indefinitely; `analytics.prune` (`20 0 * * *`) deletes only the raw tables' old rows and past salts, never past the oldest day `rollupDays` still rebuilds (yesterday and the day before), so a short `ANALYTICS_RETENTION_DAYS` can never delete a day the nightly rollup has not rebuilt yet (see **Jobs**). `recordEvent` enqueues an `analytics.event` job after the write commits (inside the caller's `tx` when there is one), so a product event never slows or fails the request it rides on; the job inserts the row and, when a provider is configured, enqueues `analytics.forward`. On an impersonation session (`context.impersonating`) `recordEvent` records nothing, for every caller. Event counts are at least once (the queue is): a worker crash after the insert can count a row twice, but the funnel counts distinct users and is unaffected. The browser side is `@repo/telemetry/analytics`'s `sendPageview` / `track(name, props?)`, both `sendBeacon`-ing to the app's own `POST /api/analytics` (`createAnalyticsRoute({ app, identity? })` from `@repo/telemetry/server`, a three-line route like `/api/telemetry`'s); `<Analytics />` (`@repo/ui/components/analytics`, next to `WebVitals` in every Next app's root layout) sends one pageview per `usePathname()` change, the first carrying `document.referrer`'s host (never a client navigation's own history) and skipped entirely in development and under Do Not Track. The route refuses a cross-site write like `/api/telemetry` and, unlike it, drops bots (a bot user agent, before the body is read), cuts the user agent to the 500 characters ingest accepts, resolves ids only when consent is `all` (the signed-in apps' `identity` calls `getMeFromRequest` + `analyticsIdentity`), and forwards with a per-browser `analytics:<ip hash>` client id (none when the request carries no ip) — that key and the visitor hash are only as trustworthy as `x-forwarded-for`, the same best-effort as telemetry — rate-limited per client (`ANALYTICS_RATE_LIMIT`, default 120 a minute) and per app (6000 a minute, the backstop). The provider seam (`ANALYTICS_PROVIDER=store|posthog|plausible`, `apps/api/src/analytics/providers/`) always writes the tables first: `posthog` sends `$ip: null` and `$geoip_disable: true` with a `distinct_id` of `user:<id>`, else `workspace:<id>`, else `visitor:<visitorId>`, else `"anonymous"` with `$process_person_profile: false`, and a `uuid` fixed at enqueue time for its own dedup; `plausible` has no dedup key (a retried forward can double-count there; the first-party tables are the source of truth) and sends the api's own honest user agent, `boilerplate-bun analytics`, which Plausible may bot-filter and drop silently — both accepted limitations, documented in `plausible.ts`. `POSTHOG_HOST` / `PLAUSIBLE_HOST` must be URLs; a chosen provider missing its other vars (`POSTHOG_KEY`, or `PLAUSIBLE_DOMAIN`) stops the api at startup. The dashboard is `apps/auth`'s `/admin/analytics` (an `AdminNav` link, superadmin only, `NOT_FOUND` to anyone else including impersonation), backed by `admin.analytics.summary({ days: 7 | 30 | 90 })`: a days chart of visitors and pageviews (visitors distinct per `(day, app)` then summed across apps, so the same person on two apps counts twice — the rollup's `"*"` row is exactly this), top pages, top referrer hosts, a per-`(day, name)` events table (merged across every source), and a fixed funnel (`signed_up` → `email_verified` → `workspace_created` → `invitation_accepted` or `note_created`) as nested sets within the range, each step's percentage of `signed_up`. Every past day reads `analytics_daily`; a past day the nightly rollup never reached falls back to the same live aggregation today always uses. The funnel and top referrers read raw rows, so with `ANALYTICS_RETENTION_DAYS` shorter than the range they cover only the retained days: the summary returns `retentionDays` and the page notes it. `docs/guides/analytics.md` covers adding a product event, the client event, PostHog/Plausible setup and the privacy text; the legal app's privacy page (`apps/legal/content/pages/integritet.mdx`, `en-privacy.mdx`: visitor statistics, account events, cookies) states what is collected without consent (product events linked to the account whatever the visitor chose), what `all` adds (ids on pageviews and browser events), that a configured provider receives the account-linked data, and what is never collected.
