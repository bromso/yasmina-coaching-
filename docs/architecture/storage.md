# Storage

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Storage.** `apps/api` keeps user files behind one seam, `apps/api/src/storage/` (`Storage`: `put`, `get`, `delete` — a missing key is not an error — and `list(prefix)` for the `storage.sweep` job), picked at boot by `createStorage(env)` from `STORAGE_PROVIDER`: `local` (the default; keyless, files on disk under `STORAGE_DIR`, `.data/storage` from the api's working directory, the content type from the key's validated extension, no sidecar; with `NODE_ENV=production` the api warns at startup — fine for one node with a volume, wrong for several) or `s3` (Bun's built-in `S3Client`, no SDK; `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, or the api exits at startup naming the missing ones, and an optional `S3_ENDPOINT` for R2, MinIO, SeaweedFS or any S3-compatible bucket). `s3`'s `get` is one request (`bytes()`, no existence check first): a missing key (`NoSuchKey`) returns null like `local`'s, and so does a 403 (a bucket without `s3:ListBucket` answers that instead of 404 for a missing key; wrong credentials answer it for every key) — both read as "not found" to the image route, which answers `404` — but every 403 is also reported through `onForbidden` (`recordFailure("storage read forbidden", …)`), since one on every object is a configuration problem, not a missing file; the content type comes from the key's own extension (`contentTypeForKey`), not the bucket's stored header. Two examples use it, one per owner in the tenant model: a user's profile photo and a workspace's logo. Migration `0014_files` adds a nullable `users.avatar_key` and `workspaces.logo_key` (indexed: every image request looks them up) and no `files` table — one image per owner needs none. Keys are `avatars/<userId>/<random>.<ext>` and `logos/<workspaceId>/<random>.<ext>` (`<random>` 16 random bytes base64url, `<ext>` `png` / `jpg` / `webp`; `FILE_KEY_PATTERN` in `@repo/api-contract`) and never reused: a replace validates the file, writes a new object, commits its key to the row, then enqueues a `storage.delete` job for the old object (deduped `storage.delete:<key>`; a failed enqueue is logged and recorded as a telemetry `server` row, never shown, and the nightly `storage.sweep` catches the orphan); a failed commit queues the object just written for deletion instead. Procedures (multipart `File` input): `account.avatar.set({ file })` → `{ avatarUrl }` and `account.avatar.remove()` (⚑), `workspaces.logo.set({ workspaceId, file })` → `{ logoUrl }` and `workspaces.logo.remove({ workspaceId })` (⚑, `member("admin")`); a remove with no image is a no-op success, and `workspaces.delete` enqueues the logo's `storage.delete` in the same transaction as the row delete. Validation, in `apps/api/src/storage/image.ts` with no image library: the type by magic bytes only (PNG, JPEG or WebP; the declared type and file name are ignored, SVG and GIF refused), at most 2 MB (`MAX_IMAGE_BYTES`, checked before the image is parsed), dimensions from the header at most 4096 × 4096 (`MAX_IMAGE_DIMENSION`, so a decompression bomb is refused), a header that cannot be parsed or a truncated file refused — all `BAD_REQUEST` `IMAGE_UPLOAD_MESSAGE` "Upload a PNG, JPEG or WebP image up to 2 MB.". Metadata is stripped from the stored bytes so a phone photo does not publish its GPS position: every format is allowlisted, not denylisted. PNG keeps only `IHDR` (required first — and, since any later occurrence fails that same check, only once), `PLTE`, `tRNS`, `IDAT`, `IEND`, `gAMA`, `cHRM`, `sRGB`, `iCCP`, `sBIT`, `bKGD`, `pHYs`, `acTL`, `fcTL` and `fdAT` (APNG frames survive), plus the PNG 3rd edition's `cICP`, `mDCv` and `cLLi` (colour space and HDR levels); every other chunk — text (`tEXt` / `iTXt` / `zTXt`), `eXIf`, `tIME`, C2PA (`caBX`), vendor/private — is dropped. WebP keeps `VP8 `, `VP8L`, `VP8X`, `ALPH`, `ANIM`, `ANMF` and `ICCP`, with `VP8X`'s EXIF/XMP flag bits cleared since those two chunks never survive (its ICC, alpha and animation flags stay, since those chunks do). JPEG by allowlist too — the structural segments (SOFn, DHT, DAC, DQT, DNL, DRI, DHP, EXP, SOS) plus APP0 JFIF (cut to its 16-byte core: thumbnail size 0 × 0, the embedded thumbnail gone), APP2 ICC_PROFILE and APP14 Adobe, each matched by its own signature, are kept; every other APPn (EXIF, XMP, MPF, Photoshop/IPTC, APP0 JFXX, vendor data) and COM is dropped, the file is cut at the first real EOI (appended trailers and secondary images go), and a length-less or reserved marker where a segment should start refuses the file. No resizing: the UI sizes with CSS. A storage provider that fails the write (a bucket down, bad credentials, a full disk) answers the declared `SERVICE_UNAVAILABLE` (503) `STORAGE_UNAVAILABLE_MESSAGE` "File storage is unavailable, try again later" — for both image uploads and `jobs.apply`'s CV — and is recorded through `recordFailure`; nothing is committed. The two `set` procedures share the limiter `upload:<userId>`, 20 upload attempts per hour (`TOO_MANY_REQUESTS` "Too many uploads, try again later"), checked before the image is processed — the multipart body is already parsed by then, and a refused file counts. Allowed while impersonating and then audited like profile and workspace writes (`user.avatar_set`, `user.avatar_removed`, `workspace.logo_set`, `workspace.logo_removed`); ordinary uploads write no audit row. The contract carries `User.avatarUrl`, `WorkspaceSummary.logoUrl` and the admin views' `AdminUser.avatarUrl` / `AdminWorkspace.logoUrl` (`string | null`), resolved by the api to `/files/<key>` — relative, each app serves it on its own origin — or to `${STORAGE_PUBLIC_URL}/<key>` when that is set (a public bucket or a CDN in front of one; the route is then unused, and a removed image lingers until the CDN expires it). Browsers never call `apps/api`: `app`, `auth` and `account` each have `src/app/files/[...key]/route.ts`, two lines over `createFileRoute()` from `@repo/session/files`, which checks the key against `FILE_KEY_PATTERN`, calls `files.get({ key })` (`GET /files/{+key}`, service token only, no session) with a per-browser client id `files:<ip hash>` (so one browser cannot exhaust a bucket shared by every visitor), and streams the bytes with the stored `Content-Type`, `Cache-Control: public, max-age=31536000, immutable` (keys never change), `X-Content-Type-Options: nosniff`, `Content-Disposition: inline` and `Content-Security-Policy: sandbox; default-src 'none'`; `404` for an unknown key, `502` when the api cannot be asked, both `no-store`. The apps' proxy matcher skips image extensions, so those headers are the route's own. `files.get` serves only a key a `users.avatar_key` or `workspaces.logo_key` currently holds, `NOT_FOUND` for any other well-formed key, so a replaced or removed image stops being served at once; the key is the capability (unguessable, low-sensitivity images, cacheable), with no per-request access check. Body size: the api's `maxRequestBodySize` is `max(API_MAX_BODY_BYTES, UPLOAD_MAX_BODY_BYTES, CV_MAX_BODY_BYTES)` (6 MB); the two image uploads get `UPLOAD_MAX_BODY_BYTES` (3 MB) and `jobs.apply` `CV_MAX_BODY_BYTES` (6 MB) through the `content-length` check, every other request `API_MAX_BODY_BYTES`; a chunked body without `content-length` on any path is bounded only by the 6 MB server cap. `apps/account` sets `experimental.serverActions.bodySizeLimit: "10mb"`, above the 2 MB rule on purpose: its actions check the size themselves and answer `IMAGE_UPLOAD_MESSAGE`, so a 5 MB photo gets the form's message rather than Next's error page, and the api never receives more than 2 MB from it. The limit is app-wide — every server action in `apps/account` accepts a 10 MB body, signed in or not — an accepted trade-off. The UI (every form works without JavaScript): `apps/account`'s **Profile photo** card on Personal info and **Logo** card on Workspace (admin and up; read-only below), a file input (`accept` `IMAGE_ACCEPT`), **Upload**, **Remove**, a local preview once hydrated; `UserMenu` shows the avatar and each workspace's logo, initials as the fallback, and `apps/auth`'s admin views show both — plain `<img>` with `width` / `height` and `alt=""` next to a visible name, never `next/image`; in `UserMenu` and the account cards `useImageFallback` (`@repo/ui/components/image-fallback`) falls back to initials when a stale URL 404s, even before hydration. `docker-compose.yml` points the api at SeaweedFS (see **Docker**); `storage.test.ts` runs its contract suite against `local`, against `s3` through a fake endpoint, and against a real bucket when `S3_TEST_ENDPOINT` is set (not in CI). Choosing a provider, AWS S3 with a minimal IAM policy, Cloudflare R2, MinIO or SeaweedFS, a public bucket or CDN, and why no bucket CORS is needed: `docs/guides/storage.md`. One bucket per environment: the nightly `storage.sweep` job deletes every object its own database does not reference (see **Jobs**). See `apps/api/README.md`, `packages/session/README.md` and `apps/account/README.md`.
