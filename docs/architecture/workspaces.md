# Workspaces

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Workspaces.** The tenant (migration `0008_workspaces`): `workspaces` (name, a slug derived from it that never changes on rename), `memberships` (one row per user and workspace, with a role) and `invitations`; `0009_notes_workspace` gives `notes` a `workspace_id` (backfilling one workspace per existing note owner) and keeps `user_id` as the author. A user exists without a workspace; creating one needs a verified email and makes the creator `owner`. Roles are one ordered list, `ROLES = ["viewer", "member", "admin", "owner"]` in `@repo/api-contract`, compared with `roleAtLeast(role, min)`; invitations and `members.setRole` name only `ASSIGNABLE_ROLES` (no `owner` — that comes only from `workspaces.transferOwnership`, which makes the caller an `admin`). Every scoped procedure takes an explicit `workspaceId` and runs behind the router's `member(min)` middleware, which loads the caller's membership: a non-member gets `NOT_FOUND` "Workspace not found" whether or not the workspace exists (no existence oracle), a lower role `FORBIDDEN` "Requires the <role> role"; a note id from another workspace is `NOT_FOUND` too. Every workspace keeps an owner: `assertNotLastOwner` runs inside the transaction of every leave, removal and demotion, and `assertOwnerRemains` re-counts owners after the write in the same transaction (`CONFLICT` "Transfer ownership before leaving."), and every such writer first locks the workspace row (`workspaces.lockForOwnership`; the user row before workspaces, workspaces in ascending id), so concurrent demotions and leaves serialise and the second sees the first's result — on Postgres too, where READ COMMITTED would otherwise let two overlapping ones both pass; the re-count stays as a safety net. Members' emails are `null` below `admin`. Invitations are a hashed, single-use token (`newToken()`, stored as `tokenHash()`), valid 7 days (`INVITE_TTL_MS`), mailed as `${APP_URL}/invitations/<token>` (hence `APP_URL` for the api) and bound to the invited address: `invitations.accept` needs a signed-in user whose verified email is that address — an address mismatch is `FORBIDDEN` naming the masked address, an unverified caller `FORBIDDEN` "Verify your email to accept this invitation". `invitations.preview` is anonymous, masks the address and never consumes the token; `invitations.acceptById` accepts from the caller's pending list (`workspaces.list` returns `pendingInvitations` only for a verified email) and answers `NOT_FOUND` for a row addressed to someone else; re-inviting an address replaces its pending row and link; `workspaces.invitations.create` is limited to 20 per workspace per hour (`invite:<workspaceId>`, in memory). An owner may also limit invitations (create, re-invite, accept and acceptById alike) to the workspace's own email domains — see **Invitation domains.**. `workspaces.delete` (and the privacy purge's sole-member delete, through `deleteWorkspaceInTx`) now locks the workspace row before deleting its invitations, the same order an accept takes, closing a Postgres deadlock between the two. In the Next apps the current workspace is the `workspace` cookie (`WORKSPACE_COOKIE`, the id; HttpOnly, `SameSite=Lax`, on `COOKIE_DOMAIN`, a year), a hint re-checked against `workspaces.list` on every request. `requireWorkspace()` from `createAuth` (after `requireUser()`) has three outcomes: the cookie's workspace when the user is a member of it; the user's only workspace when the cookie is missing or stale; otherwise a redirect to `${APP_URL}/workspaces/new`. It never writes the cookie (a server component cannot); only server actions do, through `setCurrentWorkspace(id)` (refuses a non-membership) and `clearCurrentWorkspace()`. Pages need no role beyond membership: the api refuses a privileged call and the form shows its message. `app`, `auth` and `account` pass `UserMenu` a `workspaces` prop (`items`, `currentId`, `switchTo` — each app's `switchWorkspace` action — `pendingInvitations`, `newUrl`, `manageUrl`, `canManage` for admin and up); without it the menu is unchanged. The UI: `apps/app`'s `/workspaces/new` (create, or accept a pending invitation) and `/invitations/[token]` (the link's landing page; only its **Accept** button consumes the token), and `apps/account`'s `/workspace` (members, roles, invitations, rename, transfer, delete). See `apps/api/README.md`, `packages/session/README.md`, `apps/app/README.md` and `apps/account/README.md`.
