# Email change

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Email change.** `account.email.{get,requestChange,confirmChange}` (⚑) and `auth.emailChange.{cancel,revert}` (anonymous, button-consumed, never on load) let a signed-in user change the address they sign in with, from `apps/account`'s Personal info. Migration `0025_email_change` adds three `tokens` purposes and no new table — `tokens.email` already holds one address per row: `email_change` (the new address, 24 h), `email_change_cancel` (no address, 24 h — the request-time cancel link) and `email_change_revert` (the old address, 7 days, carrying the nullable `requested_at` the rollback below reads). `requestChange({ newEmail, password?, code? })` re-authenticates like two-step setup (the current password on an account that has one, `data.reason: "password"`; else a session under `REAUTH_WINDOW_MS`, `data.reason: "reauth"`) and, when two-step is on, also a current TOTP or recovery code (`data.reason: "code"`, the shared `2fa:manage:<id>` budget); it is limited to `email-change:<userId>` 3 per 15 minutes and refused while impersonating. A new request voids a pending one. A `newEmail` already held by another account runs every step and gets the identical answer and pending state as a free one — only the confirm mail to the taken address is withheld — so `account.email.get` cannot be used to probe whether an address exists; `confirmChange` on that stored token still answers `CONFLICT`. On a free address it mails `emailChangeConfirm` to the new one (`${ACCOUNT_URL}/email/confirm?token=…`, itself the address's verification) and `emailChangeRequested` to the current one (the masked new address, a 24 h `${AUTH_URL}/email/cancel?token=…` cancel link) — both enqueued inside the transaction that stores the tokens, so a failed job insert rolls the request back rather than leave a confirm link nobody was warned about. `confirmChange({ token })` (the token's own account only, else `BAD_REQUEST` naming the mismatch) sets the address and `email_verified_at` in one transaction (this is the reset-and-reverify an email change needs, in place of the generic note the **Email** paragraph above used to carry), voids the account's other reset/verify/magic-link/change tokens, ends every session but the caller's, issues the `email_change_revert` token, follows `billing_customers.email` to the new address (the provider is not told, so its next customer event writes the old one back — same accepted limitation as the privacy purge's handling), audits `user.email_changed`, and mails `emailChanged` to the old address with a 7-day "This wasn't me" revert link. `auth.emailChange.cancel({ token })` voids the pending change and ends *every* session of the account, including whichever one requested it, and audits `user.email_change_cancelled`. `auth.emailChange.revert({ token })` restores the old address (re-verified; `CONFLICT` `EMAIL_CHANGE_REVERT_TAKEN_MESSAGE` "contact support" if a *verified* account now holds it, nothing else changing and the link left usable — an *unverified* holder, typically a sign-up on the freed address made to defeat the undo, is displaced instead: the link proves that mailbox, so inside the revert's transaction the holder's row is locked after the reverting user's (ascending id), re-checked, refused with `CONFLICT` if it belongs to any workspace, deleted with `users.purge` and audited `user.displaced_by_revert` (actor `null`, the address masked); a sign-up racing the revert loses on the unique index, a clean `CONFLICT` for whichever comes second) and locks the account down: ends every session, deletes every passkey, voids every other one-time token, and — stamped from the *request* time (`requested_at`), not the confirm — rolls back whatever changed since: an identity linked since is deleted, two-step turned on since is turned off (one already on before the request stays; a superadmin's reset is the way to remove that), a deletion requested since is cancelled. When the account had a password it is cleared and a fresh `resetPassword` link mailed to the restored address (whoever changed the email may know it). A revert voids only revert tokens issued *after* the one just used (`tokens.invalidateForUserAfter`), not every other one — so after a second change the newest link always dies but an older link to an address the account held before stays live up to its own 7 days, the accepted cost of making the oldest link always win over a later one made by whoever is squatting the account. `emailChangeReverted` lists exactly what was undone and always asks the owner to review their connected providers and two-step verification; audits `user.email_change_reverted`. Every mail to the account's own current or old address (`emailChangeRequested`, `emailChanged`, `emailChangeReverted`) uses the saved locale, else English — never the request's, since a hijacker's request locale should not decide what the victim's mailbox reads — while `emailChangeConfirm` (self-initiated, to the address the user is trying to prove) uses the usual saved-else-request-else-English rule. No confirmation is required from the old mailbox before a change takes effect — a deliberate, documented departure from the OWASP Authentication Cheat Sheet's stricter option, since a user who has lost the old mailbox must still be able to change it; the before/after notices and the 7-day undo link are the mitigation. The reverse squat is closed too: when an owner proves an address someone pre-registered unverified (magic link or a provider's verified email), `purgeUnverifiedAccount` voids the account's `email_change`, `email_change_cancel` and `email_change_revert` links with everything else, so a change the squatter requested to their own mailbox cannot be confirmed by a tricked owner afterwards. Known, accepted races: a password sign-in can land a session after a concurrent confirm/revert ended the others (only a 2FA challenge checks `sessions_revoked_at`), and a two-step enable already in flight can still stamp a factor after a revert commits (it needs the session the revert just ended).
