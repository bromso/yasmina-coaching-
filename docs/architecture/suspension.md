# Suspension

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Suspension.** Migration `0026_suspensions` adds four nullable columns to `users`: `suspended_at` (null = not suspended), `suspended_until` (null = indefinite), `suspension_reason` (internal, never shown to the suspended user or exported) and `suspended_by` (the admin's id, no FK — set `NULL`, not cascaded, when that admin is purged, the same pattern `audit_log.actor_user_id` uses). One rule, `isSuspended(user, now)`: `suspended_at` set and (`suspended_until` null or later than `now`), computed fresh on every read from `Context.now()` (the same injected clock the job worker and `enqueue` already use — and the admin side too: `suspend`'s `until` check and its `suspended_at` stamp, and the `active` flag and `suspended=true` filter of `admin.users.list` / `get`, all read it, so a moved clock moves them together) — **expiry is never written back by a job**; an `until` in the past simply reads as not-suspended, the columns sitting there until an admin clears them with **Lift suspension** (`unsuspend`). Enforcement sits at every point a path would otherwise issue a session or a two-step challenge, always *after* that path's own credential check, so a wrong credential still answers exactly as before and the suspended message is never an existence oracle: password sign-in, magic-link consume, the OAuth callback (sign-in and connect), `auth.twoFactor.verify` (re-read under the user-row lock right after `consume`, so a challenge issued before the suspension is already dead — `revokeSessionsInTransaction` deleted it — and one minted by a sign-in that raced the suspension is refused here; the throw rolls back the challenge consume and a recovery code's spend, but a TOTP code's step was already advanced by `setLastStep` outside the transaction, so that code stays spent) and `auth.passkey.verify` (same re-read-under-lock pattern, the throw rolling back the counter and `last_used_at`); `admin.users.impersonate` refuses a suspended target with its own `SUSPENDED_TARGET_MESSAGE` ("A suspended account cannot be impersonated") before the limiter. Provider sign-in and magic-link consume may still link an identity, purge an unverified pre-registration or mark the email verified before refusing a suspended account — the existing linking rules, which need provider or mailbox proof — harmless, since no session is issued. `refuseSuspended(context, user)` throws `FORBIDDEN` `apiMessage(context, "accountSuspended")` (`ACCOUNT_SUSPENDED_MESSAGE` = "This account is suspended. Contact support.", en + sv) — declared once per procedure, since oRPC allows one default per error code (`auth.oauth.callback` already declares `FORBIDDEN` for `providerEmailUnverified` and still answers `accountSuspended` on this path; a comment notes it). `resolveSession` takes the same clock: a suspended user's session (impersonation sessions of them included) resolves to null and is **deleted on sight** — suspending already ends every session in its own transaction, so the only rows left are ones a sign-in that raced the suspension created: one presented while the suspension holds is deleted, while one never presented until a timed suspension has run out works again, as a fresh sign-in by the same credential holder would; every ⚑ procedure, the realtime stream's connect and 60 s recheck, and `support.create`'s optional session link all see the same refusal.

`admin.users.suspend({ userId, reason, until? })` / `unsuspend({ userId, reason })`: superadmin only (`NOT_FOUND` to anyone else, impersonation sessions included — the same `superadmin` middleware every `admin.*` procedure sits behind), never yourself or another superadmin (`SELF_SUSPEND_MESSAGE` / `SUPERADMIN_SUSPEND_MESSAGE`), `reason` 3–200 characters, `until` (suspend only) strictly in the future and at most `SUSPEND_UNTIL_MAX_DAYS` (365) days ahead (`BAD_REQUEST` `SUSPEND_UNTIL_INVALID_MESSAGE`, checked before the limiter); one shared limiter, `suspend:<adminId>` 20/hour, for both procedures (`TOO_MANY_REQUESTS` `SUSPEND_RATE_MESSAGE`). Both lock the user row first (`lockForSession`, the same order `resetTwoFactor`/`removePasskeys` take) inside one transaction: `suspend` writes all four columns (`suspended_at` always bumps to "now", even on a reason-only edit of an already-suspended account — it means "when the current terms took effect", not "when first suspended"), stores `until` normalised (`new Date(until).toISOString()`, so the filter's string comparison and the "end date changed" check see one form per instant), ends every session and stamps `sessions_revoked_at` (so an outstanding two-step challenge can't become a session), then enqueues `accountSuspended` in that same transaction — but only when no suspension was in force (`isSuspended` on the row re-read under the lock: never suspended, or expired) or the end date actually changed, never twice for a reason-only edit; a target purged between the lookup and the lock answers `NOT_FOUND` with no mail and no audit row, for both procedures; `unsuspend` is a true no-op (no limiter hit, no audit, no mail) only when `suspended_at` is already null — an expired-but-uncleared suspension still gets cleared, audited and mailed exactly like lifting a live one — otherwise it clears all four columns and enqueues `accountUnsuspended` in the same transaction. Both mail the account's saved locale, else English, and never the reason or the admin's identity — there is no such prop on either template. Audited after the transaction, the admin's `reason` riding in the audit row's own `reason` field (same as `resetTwoFactor`/`removePasskeys`, never exported — see below): `user.suspended` (no suspension in force — first time, or over an expired record) or `user.suspension_updated` (re-suspending one still in force, with a changed reason or end date) for suspend, `user.unsuspended` for unsuspend. Unaffected: workspaces, memberships, billing, invitations, scheduled deletion (the purge still runs) and pending one-time tokens all keep working for everyone else — a sole owner who is suspended keeps owning, and transferring ownership needs them signed in, so it waits for an unsuspend.

The privacy export's `profile.suspended` carries `{ at, until } | null` only — `suspension_reason` and `suspended_by` are simply never selected — and `REASON_REDACTED_ACTIONS` nulls the `reason` the export's `auditLog` section would otherwise forward for `user.suspended` / `user.suspension_updated` / `user.unsuspended` rows (that section surfaces an admin's own `reason` for other actions, like a 2FA reset, by design — suspension needed its own carve-out to not regress that). `AdminUser.suspended` (`list` and `get` alike) is `{ at, until, active, reason, by }` or `null`: present whenever the record exists, expired or not, since nothing but **Lift suspension** (`unsuspend`) clears it; `active` is `isSuspended`'s own answer at read time, so a client never re-derives it from `until`, and `admin.users.list({ suspended: "true" })` filters on that same `active` test, not raw presence — an expired-but-uncleared row stays visible unfiltered but drops out of the filtered view. `apps/auth`'s `/admin/users/<id>` gets a **Suspension** card (status Not suspended/Active/Expired, reason, until, by — "Unknown (account purged)" once `by` is null) with one form that renders as **Lift suspension** whenever a record exists, active or expired (lifting is what clears an expired record, so suspending again after expiry means lifting first), and **Suspend account** only when there is none, disabled for yourself and a superadmin like every other admin card; `/admin/users` gets a "Suspended" badge (`active` only, so an expired-uncleared row shows none) and a `suspended=true` filter checkbox. Every sign-in page that can answer the suspended `FORBIDDEN` shows it verbatim, since the api already answers in the caller's locale — the one exception is the OAuth callback's redirect, which cannot carry the api's own message across a 303: `apps/auth` tells the suspended refusal apart from the callback's other declared `FORBIDDEN` (`providerEmailUnverified`) by comparing the thrown message against its own `common.accountSuspended` catalog entry in every locale, pinned equal to the api's `accountSuspended` string by a dedicated test, rather than trusting the English constant alone — the api can genuinely answer in Swedish here, before any sign-in has happened.
