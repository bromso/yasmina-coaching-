# Email

Full reference; `CLAUDE.md` keeps the summary and the index. A bold name such as **Jobs** refers to its entry there, whose link leads to the sibling file here.

**Email.** `apps/api` sends every email through one seam, `apps/api/src/mail/` (`Message` / `Mailer`, picked at boot by `createMailer(env)`): `MAIL_PROVIDER=log` (the default; keyless, logs one `mail` line per message: masked `to`, `subject` and the whole text body as `text`), `smtp` (Nodemailer, `SMTP_URL`), `resend` (Resend's HTTP API via `fetch`, `RESEND_API_KEY`) or `file` (keyless, writes each message as a JSON file to `MAIL_DIR`, required iff `file`). The `log` and `file` providers both expose the text body, links included, so verify, reset and magic-link tokens are readable — fine in dev and for `apps/e2e` (which reads the mailbox directory for its one-time links, `fixtures/mail.ts`), never in production (the api warns at startup on either). In `docker-compose.yml` the api sends over SMTP to Mailpit, whose inbox is at `localhost:8025`; `docker-compose.dev.yml` runs Mailpit too but leaves the api on `log`. Templates live in `packages/email` (`@repo/email`), previewed in Storybook under `apps/story/stories/email/`; a new email = template + test + story. Every send is a `mail.send` job (see **Jobs**): the procedure enqueues the template name, address and props — in its own transaction for invitations and the unverified-account purge; sign-up and resend verify, password-changed, the two-factor notices and the waitlist welcome are enqueued (awaited) right after the write, so a failed enqueue answers `500` though the write committed — and the worker renders and sends, retrying with backoff, so a slow or failing provider changes neither the response nor its timing and a lost send is retried, not dropped (durability over silent loss). Success logs `mail sent <template key> to <masked address>` (`mail sent verifyEmail to a***@example.com`). The two silent anonymous requests (`auth.requestPasswordReset`, `auth.magicLink.request`) enqueue through `detach()` after the response, so a known and an unknown email keep equal timing. Verification is soft: `auth.signUp` mails a link to `${AUTH_URL}/verify-email?token=…` (24 h), `auth.verifyEmail` confirms it, `account.resendVerification` sends another (3 per 15 minutes per user), and `User.emailVerified` drives `apps/account`'s badge and notice — no user action is gated on it, but social sign-in and magic link read it to decide whether an account may be purged on linking (see below). One-time tokens share the `tokens` table, told apart by `purpose` (`password_reset`, `email_verify` from migration `0004_email_verification`; `magic_link` from `0005_identities`); a new one-time purpose is a value there, not a table. Invitations are the exception: they carry a workspace, a role and an address, so they have their own `invitations` table (see **Workspaces** below), hashed the same way. Changing the sign-in address does reset `email_verified_at` and send a new verify link — the confirm link an email change mails to the new address *is* that reset-and-reverify, handled by `account.email.confirmChange`; see **Email change** below. `Message` also carries an optional `headers?: Record<string, string>` (Phase 13 B), passed through as-is by `smtp` and `resend` and recorded verbatim by `log` and `file` — used only by the three optional notification templates (`roleChanged`, `removedFromWorkspace`, `planChanged`; see **Notification preferences.** below) to carry their RFC 8058 `List-Unsubscribe` pair; every other template leaves it unset. See `apps/api/README.md` and `packages/email/README.md`.
