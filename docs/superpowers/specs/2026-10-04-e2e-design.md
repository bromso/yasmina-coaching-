# Browser end-to-end tests for the Next apps (Phase 5)

**Status:** implemented
**Date:** 2026-10-04
**Origin:** `docs/ROADMAP.md` Phase 5 — "Browser end-to-end tests for the Next apps"
**Builds on:** every app and service shipped through Phase 6; the api's `Mailer` seam
(`log | smtp | resend`); the CI planner (`scripts/ci-plan.ts`); Playwright already used by
`apps/story`'s browser tests.

## Intent

Unit and api tests cover each piece; nothing covers the journeys that cross apps and break
silently — a session cookie that stops flowing between subdomains, a mailed link that points at the
wrong host, a server action that no longer redirects, a paid feature that stays locked after
checkout. This phase adds a small, deterministic Playwright suite over those journeys, run against
production builds on the real `*.brand.localhost` hosts, as a PR gate that the CI planner triggers
only when an app or a shared package changed.

## Decisions

- **PR gate over critical journeys**, ~12 tests, < 8 minutes in CI including builds.
- **Production builds** (`next build` / `next start`, `bun` for api and ai) launched by Playwright's
  `webServer`, real hostnames and ports, a throwaway SQLite database. No dev servers, no Docker.
- **A `file` mail provider** in `apps/api` (`MAIL_PROVIDER=file`, `MAIL_DIR`): each message is a JSON
  file the tests read for one-time links. The api stores only token hashes, so the mailbox is the
  only source of the links.
- **Chromium only, serial** (`workers: 1`): the journeys share one database and the api's in-memory
  limiters; serial keeps them deterministic.
- Out of scope: Firefox/WebKit, visual regression, axe scans, OAuth providers, Stripe (mock only),
  `docs` / `help` / `jobs`, Docker images, Postgres for e2e, load testing.

## Components

### `apps/api` — the `file` mail provider

- `MAIL_PROVIDER` gains `file`; `MAIL_DIR` is required iff `file` (at any `NODE_ENV`; `loadEnv`
  throws `MAIL_PROVIDER=file needs MAIL_DIR`). `apps/api/src/mail/file.ts`: `fileMailer(dir)` →
  `Mailer` with `kind: "file"`; `send(message)` creates the directory if needed and writes
  `<dir>/<Date.now()>-<random 6 hex>.json` containing `{ to, subject, text, html, sentAt }`.
- `createMailer(env)` picks it; startup warns in production as for `log`: "MAIL_PROVIDER=file writes
  mail to disk instead of sending it".
- Unit test in `mail.test.ts`: a send writes one parseable file with the fields; a missing `MAIL_DIR`
  fails `loadEnv`.

### `apps/e2e` (`@repo/e2e`, private workspace)

- `package.json`: `@playwright/test` (root catalog entry, same version as `apps/story`'s
  `playwright`), `@types/node`; scripts `e2e` (build the four apps, then `playwright test`),
  `test:ci` (`playwright test` — CI builds first), `typecheck`.
- `playwright.config.ts`: `testDir: "tests"`, Chromium project only, `workers: 1`,
  `fullyParallel: false`, `retries: process.env.CI ? 1 : 0`, `use: { trace: "retain-on-failure",
  screenshot: "only-on-failure" }`, `reporter: CI ? [["github"], ["html", { open: "never" }]] :
  "list"`, `globalSetup: "./global-setup.ts"`, and a `webServer` array:
  - `api` — `bun ../api/src/index.ts`, env below, `url: http://api.brand.localhost:3007/ready`;
  - `ai` — `bun ../ai/src/index.ts`, `AI_MODEL=mock:echo`, `AI_SERVICE_TOKEN`,
    `url: http://ai.brand.localhost:3008/ready`;
  - `www`, `app`, `auth`, `account` — `next start --port <port> --hostname <name>.brand.localhost`
    run in each app's directory (the apps' own `start` scripts set no hostname, and `www`'s no
    port), `url: http://<name>.brand.localhost:<port>/api/health`;
  - every entry `reuseExistingServer: !process.env.CI`, `timeout: 120_000`.
- **Shared env** (one object in `e2e.env.ts`): `NODE_ENV=production`,
  `API_URL=http://api.brand.localhost:3007`, `API_SERVICE_TOKEN` and `AI_SERVICE_TOKEN` (fixed
  ≥ 32-char test values), `AI_SERVICE_URL=http://ai.brand.localhost:3008`, `COOKIE_DOMAIN=.brand.localhost`,
  `AUTH_URL`, `APP_URL`, `ACCOUNT_URL`, `SITE_DOMAIN=brand.localhost`; api only:
  `DATABASE_URL=sqlite://<tmp>/api.db`, `MAIL_PROVIDER=file`, `MAIL_DIR=<tmp>/mail`,
  `BILLING_PROVIDER=mock`, `SUPERADMIN_EMAILS=admin@e2e.test`, `API_RATE_LIMIT=10000`, and raised
  per-user limiters if the env exposes them (otherwise the suite uses a unique email per test so the
  per-email limiters never trip). `<tmp>` = `apps/e2e/.tmp` (git-ignored).
- `global-setup.ts`: deletes and recreates `<tmp>` before the servers start (Playwright runs
  `globalSetup` before `webServer`).
- `fixtures/mail.ts`: `latestMail(to, subject: RegExp, { after? })` polls `<tmp>/mail` every 100 ms
  for up to 5 s, returns the newest matching message; `linkIn(mail, pattern)` returns the first URL
  matching.
- `fixtures/accounts.ts`: `uniqueEmail(prefix)` (`<prefix>-<run id>-<n>@e2e.test`),
  `signUp(page, email, name?)`, `verify(page, email)`, `signUpVerified(page, email)`,
  `signIn(page, email)`, `createWorkspace(page, name)`.
- Selectors by role, label and visible text only; no test ids are added to app code.

### Journeys (`apps/e2e/tests/`)

1. `auth.spec.ts` — sign-up on `auth/signup` lands signed in; `account` shows the email as
   unverified; the mailed verify link verifies it; `app` sends a user without a workspace to
   `/workspaces/new`; creating "Acme" lands on `/notes`; sign-out from `app`'s user menu lands on
   `auth/login?signedout=1` and `account` then redirects to sign-in; signing in again honours `next`.
2. `magic-link.spec.ts` — "Email me a sign-in link" on `/login`; loading the mailed `/magic` link does
   not sign in; **Continue** does.
3. `notes.spec.ts` — create a note, see it listed, delete it; a viewer's create is refused with the
   api's message.
4. `invitations.spec.ts` — the owner invites `b@…` from `account/workspace`; B signs up, verifies,
   opens the mailed `/invitations/<token>` link, **Accept** → B sees the workspace in the switcher;
   a third verified user opening the same link sees the address-mismatch refusal.
5. `billing.spec.ts` — on Free, `/chat` shows the upsell; the owner switches to Pro with the mock
   form on `account/payments`; `/chat` loads and a message gets the `mock:echo` reply.
6. `admin.spec.ts` — `admin@e2e.test` signs up and verifies, opens **Admin**, finds a user,
   impersonates with a reason → `app` shows the banner; `account/security` change-password is refused
   with `Not available while impersonating`; the banner's **Stop impersonating** returns to the
   admin's user page and the audit shows started and stopped; a normal user opening `/admin` sees the
   404 page.
7. `www.spec.ts` — the home page shows the header, footer and pricing tiers; the waitlist form accepts
   an email, also with JavaScript disabled; `/terms` and `/privacy` render.
8. `chrome.spec.ts` — every app under test answers `/api/health`; each home page has the site nav and
   the skip link; responses carry a `content-security-policy` header without `'unsafe-eval'`.

### CI

- `scripts/ci-plan.ts`: a new output `e2e` (`true`/`false`): true when the affected set (after the
  existing `workspace:*` closure) includes any of `@repo/api`, `@repo/ai`, `@repo/www`, `@repo/app`,
  `@repo/auth`, `@repo/account`, `@repo/e2e`; root files run everything as today; docs-only skips.
  Planner test cases for: an app change → true, `apps/docs` only → false, a shared package used by
  `app` → true, docs-only → false.
- `.github/workflows/ci.yml`: job `e2e` (needs `changes`, `if: needs.changes.outputs.e2e == 'true'`,
  `ubuntu-latest`, `timeout-minutes: 20`): checkout; Bun at the pinned version; `bun install
  --frozen-lockfile`; assert `getent hosts app.brand.localhost` resolves to loopback, else append
  the eight hosts to `/etc/hosts`; cache `~/.cache/ms-playwright` keyed on the Playwright version;
  `bunx playwright install --with-deps chromium`; build `www`, `app`, `auth`, `account`;
  `bun --filter @repo/e2e test:ci`; on failure upload `apps/e2e/playwright-report` and
  `apps/e2e/test-results`. The final `ci` job requires `e2e` to be `success` or `skipped`.

## Error handling

- No fixed sleeps: web-first assertions and the mail poller only.
- One retry in CI; a test that passes on retry shows as flaky in the report.
- Every run starts from an empty database and mail directory.
- A server that fails to start fails the run within `webServer.timeout` with its output in the log.

## Tests of the harness itself

- `mail.test.ts` (api) for the provider; `ci-plan.test.ts` for the planner output; `apps/e2e`

## Deviations

Rulings made during execution, where the shipped behaviour differs from the design above:

- **The `.tmp` reset is not `globalSetup`.** Playwright 1.63 starts the `webServer`s before running
  `globalSetup`, so wiping `apps/e2e/.tmp` there would race a running api's open SQLite file. The
  reset (`global-setup.ts`'s body) instead runs as the first half of the api's `webServer` command —
  `bun global-setup.ts && bun src/index.ts` — so it executes only when the harness starts its own api,
  and strictly before that api opens the database. A reused api (`reuseExistingServer: !CI`, i.e.
  every local run unless `CI=1`) gets no reset and keeps its `log` mailer from whenever it was
  started — a dev server reused this way cannot serve the mail journeys, since `fixtures/mail.ts`
  reads `MAIL_DIR`, not the console.
- **The no-JS waitlist test submits with Enter, not a click.** With `javaScriptEnabled: false`,
  Playwright's click waits on a `requestAnimationFrame`-based actionability check that a scriptless
  page never satisfies, so `www.spec.ts`'s "without JavaScript" case fills the field and presses
  Enter, which submits the plain `<form>` natively.
- **`chrome.spec.ts` reads `account`'s CSP off its own `/api/health`, not its home page.** An
  anonymous visit to `account`'s home page redirects to `auth`, whose policy is not `account`'s; the
  health route is served by the same proxy and carries the same header, so it is read there for
  `account` only, while every other app under test is read off its home page.
- **Journey 3's "a viewer's create is refused with the api's message" lives in
  `invitations.spec.ts`, not `notes.spec.ts`, and asserts an absent form rather than a refusal.**
  `notes.spec.ts` only covers the owner's create/list/delete; a viewer account only exists once an
  invitation is accepted, so that check sits in `invitations.spec.ts`. `notes-view.tsx` never
  renders the add-note form below the `member` role, so the viewer never sees it to submit and get
  refused — the test asserts the title field and "Add note" button have zero count, a deterministic
  DOM check rather than one conditional on a refusal response. The api's actual `FORBIDDEN` refusal
  of a viewer's write is covered by `apps/api`'s own tests.
- **Journey 4's final assertion checks the `/notes` heading of the joined workspace, not the
  switcher.** After accepting, `invitations.spec.ts` asserts the invitee lands on `/notes` and sees
  the joined workspace's heading ("Invite Co"), rather than opening the workspace switcher UI to
  confirm the new workspace is listed there.
- **Two real bugs surfaced by the journeys, fixed as part of this phase, not pre-existing design
  flaws: `safeNextUrl` on `.localhost` in production, and a root-`loading.tsx` wedge found in
  three apps.**
  1. `safeNextUrl` (`packages/session/src/origin.ts`) refused `http:` post-login targets in
     production when `COOKIE_DOMAIN` is itself a `.localhost` domain (Compose's "production-like"
     stack, and this suite's own e2e harness — both run `NODE_ENV=production` on
     `.brand.localhost`, which has no real TLS available). It now accepts both `http:` and `https:`
     whenever the cookie domain ends in `.localhost`, regardless of `production`, matching the
     exception `@repo/sites` already makes for it. The session cookie's own `secure` flag has no
     such exception — it works over `http:` on `*.localhost` only because Chromium and Firefox
     treat `*.localhost` as a secure context.
  2. A root `src/app/loading.tsx` in `apps/app` and `apps/auth` (and, once checked, `apps/account`
     too — previously assumed safe since it sits below a route group) made Next 16.2's client
     router leave a revalidating server action's transition uncommitted forever: the response
     lands, but the button spins until a reload. No app ships a root `loading.tsx` now;
     `apps/{app,auth,account}/src/app/root-loading.test.ts` and `scripts/ci-plan.test.ts` keep it
     that way. See CLAUDE.md's **Status pages** entry for the full explanation.
- **`actions/upload-artifact@v5`** (not `v4`, the commonly-documented version at design time) uploads
  the Playwright report and test results whenever the job was not cancelled (`if: ${{ !cancelled()
  }}`), not only `if: failure()`: a test that failed, then passed on the job's own retry, still
  needs its trace uploaded, and `!cancelled()` also covers that case.
