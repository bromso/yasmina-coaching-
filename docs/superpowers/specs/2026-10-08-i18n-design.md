# Internationalisation (i18n) — design

Sub-project G, the last of the Phase 7 feature-parity work (A two-factor → B file storage →
C background jobs → D realtime → E product analytics → F content → G i18n). Approved in chat section
by section on 2026-10-08.

## Intent

A user can use the product in their own language: the signed-in surface (`auth`, `app`, `account`),
the emails it sends and the messages the API returns all speak the user's language, chosen once and
remembered across every subdomain and device. The starter ships English plus a Swedish demo locale
that proves the whole path; adding a language is a folder of messages and a line of config.

Decided with the owner:

- **Scope: foundation + signed-in core.** The shared layer, a switcher, `lang`; fully translated:
  `auth`, `app`, `account`, the `@repo/ui` pieces they render, transactional emails and the API's
  user-facing messages. The static apps (`www`, `docs`, `help`, `jobs`, `blog`) get the plumbing and
  the switcher but ship English copy.
- **Locale choice: cookie + profile, no URL change.** No `[locale]` segment anywhere.
- **Library: `next-intl` without its routing**, and its framework-free core `use-intl/core` in
  `apps/api` and `@repo/email`.

## 1. Architecture

**`packages/i18n` (`@repo/i18n`)**

- `LOCALES = ["en", "sv"]`, `DEFAULT_LOCALE = "en"`, `LOCALE_COOKIE = "locale"`,
  `type Locale = (typeof LOCALES)[number]`, `isLocale(value)`.
- `negotiateLocale(acceptLanguage: string | null): Locale` — honours quality weights, falls back
  from a region (`sv-SE` → `sv`), unknown or missing → `en`.
- `localeCookie(locale, { domain, secure })` — one year, `SameSite=Lax`, `Path=/`, on
  `COOKIE_DOMAIN`, so one choice holds on every subdomain (like the consent cookie).
- Catalogs: `messages/<locale>/<namespace>.json` for `common`, `ui`, `auth`, `app`, `account`,
  `email`, `api`. English is the source; key types are derived from it (a misspelled key is a type
  error). `messagesFor(locale, namespaces)` merges with English as the fallback, so a missing
  translation never shows a raw key at runtime.

**Resolution, per request** — the signed-in user's saved preference (`users.locale`, migration
`0017_user_locale`), else the `locale` cookie, else `Accept-Language`, else `en`.

**Next apps** — `src/i18n/request.ts` (`getRequestConfig`, no routing) per app; the root layout
renders `<html lang={locale}>` and `NextIntlClientProvider` with only the namespaces the app's client
components need. `auth`, `app` and `account` (already per-request) resolve as above. The static apps
build in English (their `request.ts` returns `en`; their pages stay static) and render the switcher.

**API and emails** — `@repo/session` sends `x-locale` (the resolved locale) on every call to
`apps/api`; the api validates it (`isLocale`, else `en`). The api translates its user-facing error
messages with `use-intl/core`'s `createTranslator` over the `api` namespace; logs, audit rows and
telemetry stay English. Emails render in the recipient's saved locale; the one mail that can reach
an address with no account — an invitation — uses the inviter's request `x-locale`. `auth.signUp`
(and account creation by magic link or OAuth) stores the request's locale as the new user's
preference. `auth.me` returns `user.locale`; `account.setLocale({ locale })` (⚑) updates it.

**Formatting** — the signed-in apps format dates and numbers with the user's locale (next-intl's
`useFormatter`/`getFormatter`). The blog and docs keep their English UTC dates (their pages stay
byte-identical static).

## 2. Switcher, coverage, keys

**Switcher** — `@repo/ui/components/locale-switcher`: each language in its own name ("English",
"Svenska"), in every app's header.

- `auth`, `app`, `account`: a plain `<form>` posting to a `setLocale` server action (sets the cookie,
  saves to the profile when signed in, refreshes) — works without JavaScript.
- Static apps: a small client component writing the cookie (honoured by the signed-in apps); hidden
  without JavaScript.
- `account`'s Personal info page gains a **Language** card using the same action.

**Translated (en + sv)**

- `auth`: every page and form — sign-in, sign-up, verify, reset, magic link, two-step verification
  and recovery codes — with their validation and error messages. The superadmin `/admin` pages stay
  English (internal tooling).
- `app`: notes, chat, workspace onboarding, the invitation landing page.
- `account`: every settings page, Payments and Workspace included.
- `@repo/ui`: what those apps render — `UserMenu`, `CookieConsent`, form feedback, status pages, the
  impersonation banner, site header and footer labels, theme toggle and sign-in link labels. Blocks
  keep taking text as props; their default strings move to the `ui` namespace.
- `@repo/email`: every template, in the recipient's language.
- `apps/api`: every user-facing message the apps display (validation, limits, permissions, seats,
  two-step verification, invitations, uploads, billing).

**Keys** — nested by page or feature (`auth.signIn.title`,
`account.security.twoFactor.turnOn`); ICU for plurals and selects
(`{count, plural, one {# member} other {# members}}`); rich text (links in sentences) through
`t.rich`, never HTML in messages.

## 3. Testing, delivery, docs

**Delivery — two PRs, never stacked:**

- **G1**: `@repo/i18n`, the cookie and negotiation; migration `0017`, `account.setLocale`,
  `auth.me`'s locale; `x-locale` through `@repo/session`; api messages and emails in both
  languages; the switcher; `auth` fully translated.
- **G2** (after G1 merges): `app`, `account` (with the Language card), the remaining `@repo/ui`
  strings, the static apps' switcher.

**Testing**

- Catalog parity: every shipped locale has exactly English's keys, and every message parses as ICU.
- Units: `negotiateLocale` (q-weights, `sv-SE` → `sv`, unknown → `en`), the cookie attributes,
  `isLocale`.
- api (SQLite and Postgres): a refused sign-in answers in Swedish with `x-locale: sv`; an invalid
  `x-locale` falls back to English; `setLocale` stores the choice; sign-up stores the request's
  locale; verification, reset, magic-link and invitation mails render in the recipient's language
  (template tests per locale).
- A hard-coded-string guard: a `scripts/` test flags literal user-facing JSX text in the translated
  apps' `src/` outside the catalogs, with an allow-list (brand name, the admin pages, code samples).
- e2e: choose Svenska on `/login` → the page and its errors are Swedish; sign up → the verification
  mail is Swedish; the saved preference wins over a different cookie after signing in elsewhere; the
  switcher's form works with JavaScript disabled.

**Operations** — no new environment variables (the cookie uses `COOKIE_DOMAIN`). Adding a language:
add it to `LOCALES` and a `messages/<locale>/` folder; the parity test lists every missing key.

**Docs** — CLAUDE.md (an **i18n.** paragraph, `@repo/i18n` in Packages, "Adding a new subdomain app"
gains `i18n/request.ts`, the provider and `lang`); a new `docs/guides/i18n.md` (adding a language,
adding and using keys, plurals and rich text, email and API messages, the guard's allow-list);
READMEs for `packages/i18n`, `packages/session`, `apps/api`, `packages/email`; ROADMAP (tick G —
Phase 7 complete).

## Out of scope

Right-to-left locales (the layer permits them; none ships), translated URLs or slugs, per-locale blog
or docs content, machine translation, translating the superadmin pages, locale-specific currency for
billing (prices stay USD).
