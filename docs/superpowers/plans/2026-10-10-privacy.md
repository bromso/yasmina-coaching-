# Data & privacy (Phase 8 A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace `apps/account`'s `/data-privacy` mockup with a real data export, the consent
setting, and self-service account deletion with a 7-day grace period and a purge job.

**Architecture:** `apps/api` owns the data: migration `0019_privacy`, `account.export.*`,
`account.delete` / `cancelDeletion`, the `privacy.export` job and two schedules (`privacy.purge`,
`privacy.export.prune`). `@repo/email` gets three templates. `apps/account` gets the page, a
download route and the grace-period banner (also in `apps/app`); `apps/auth`'s `/login` shows the
`deleted=1` notice.

**Tech Stack:** Bun 1.4.2, oRPC, `Bun.sql` (SQLite + Postgres), the jobs queue and `Storage` seam,
React Email, Next 16.2, next-intl, `bun test`, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-10-privacy-design.md`

## Global Constraints

- Branch `feat/privacy` from `main` (76e7b29 + spec e31c79a); never stacked.
- Biome zero diagnostics; Conventional Commits ≤ 100-char headers, one type per header, each ending
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- No new dependency or environment variable. A schema change is a new migration listed in
  `apps/api/src/migrations/index.ts`.
- Database behaviour holds on SQLite and Postgres. **Foreign keys are not a safety net:** most
  `user_id` columns have no `REFERENCES` (sessions, tokens, identities, recovery codes, analytics,
  notes), and SQLite does not enforce the ones that exist (no `PRAGMA foreign_keys`). The purge
  deletes or unlinks every table explicitly.
- Every user-facing api message goes through `apiMessage` with an `api` catalog key in en + sv;
  constants pinned in `apps/api/src/i18n.test.ts`. UI strings in `account` / `app` / `auth`
  namespaces, en + sv; the i18n guards stay green with empty allow-lists.
- Values: grace period `DELETION_GRACE_MS = 7 * 24 * 60 * 60 * 1000`; export lifetime 7 days;
  one export request per 24 h; re-auth window `REAUTH_WINDOW_MS` (existing, 10 min);
  schedules `privacy.purge` `25 * * * *`, `privacy.export.prune` `40 3 * * *`;
  export key `exports/<userId>/<22-char random>.json`.
- Implementers never run the Playwright e2e suite (a 10-minute no-progress watchdog); the
  controller runs `bun run ci` and e2e. Work in short steps; long commands in the background.

## Review Focus

1. A user who is the only owner of a workspace with other members can neither schedule deletion
   nor be purged later (re-check at purge time), and no workspace ever ends up without an owner.
2. The export never contains a secret: no password hash, TOTP secret, recovery code hash, session
   token hash or one-time token.
3. Another user's export id answers `NOT_FOUND`, and an impersonating admin can neither request nor
   download an export.
4. After the purge, no row in any table still links to the deleted user id except shared notes
   (author shown as "Deleted user") — sessions, tokens, identities, memberships, recovery codes,
   exports, analytics all gone or nulled.
5. A purge whose subscription cancel fails deletes nothing for that user and records a failure.

Tests: Tasks 4, 3, 3, 4, 4.

**Files:**

- Test: `apps/api/src/privacy.test.ts`

**Interfaces:**
- `account.delete({ email: string })` → `{ deletionScheduledAt: string }`. Order: impersonation →
  `FORBIDDEN`; `email` ≠ account email (case-insensitive) → `BAD_REQUEST` `deleteEmailMismatch`;
  session older than `REAUTH_WINDOW_MS` → `FORBIDDEN` `data.reason: TWO_FACTOR_REAUTH_REASON` with
  `deleteReauth`; sole owner of a workspace with other members → `CONFLICT` `deleteSoleOwner` with
  `{names}`; else `scheduleDeletion(now + DELETION_GRACE_MS)`, `users.revokeSessions(id, now)`
  (all sessions), enqueue `accountDeletionScheduled` (user's locale, link `${AUTH_URL}/login`).
- `account.cancelDeletion()` → `{}`; impersonation → `FORBIDDEN`; clears the date (no-op if none).
- api keys (en / sv): `deleteEmailMismatch` "Type your account's email address to confirm." /
  "Skriv kontots e-postadress för att bekräfta."; `deleteReauth` "Sign in again to delete your
  account." / "Logga in igen för att radera ditt konto."; `deleteSoleOwner` "Transfer ownership or
  delete these workspaces first: {names}" / "Överlåt ägarskapet eller radera de här arbetsytorna
  först: {names}".
- `privacyPurgeJob` (schedule `25 * * * *`, payload `{}`): for each id from `dueForDeletion(now)`,
  in `db.transaction`: `lockForSession`-style lock and re-read the date (skip if cleared or future);
  re-check sole ownership of shared workspaces (skip + `recordFailure`); cancel each sole-member
  workspace's live subscription with the provider **before** the transaction (as `workspaces.delete`
  does — reuse its helper; a failure skips the user and records it) then delete those workspaces in
  the transaction (reuse the workspace-delete query path so its logo is queued for deletion too);
  read name/email/locale; `users.purge`; enqueue `accountDeleted` to the read address and
  `storage.delete` for the returned keys (in the transaction); audit `user.deleted`.
