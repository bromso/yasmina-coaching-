# Passkeys Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Users add passkeys on the account Security page and sign in with one on `auth` — no password, no two-step code — on any subdomain; nobody can lock themselves out.

**Architecture:** `apps/api` owns WebAuthn through `@simplewebauthn/server`: a `passkeys` table, challenges in the `tokens` table, registration behind the reauth rule, a sign-in that issues a session like `auth.signIn` without the code step. `apps/auth` and `apps/account` use `@simplewebauthn/browser` in small client components wired to server actions over `@repo/session`. A software authenticator in the api's test helpers drives real ceremonies in tests; Playwright's CDP virtual authenticator drives the e2e journey.

**Tech Stack:** Bun 1.4, oRPC, `Bun.sql` (SQLite + Postgres), `@simplewebauthn/server` + `@simplewebauthn/browser` (catalog), Next 16, next-intl, React Email, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-17-passkeys-design.md`

## Global Constraints

- Migration `0024_passkeys` (forward-only; listed in `migrations/index.ts` and `migrate.test.ts`). Token purpose `passkey_challenge`, 5 minutes, hashed, single-use, carries the ceremony (`register` | `authenticate`) and, for `register`, the user id.
- RP: `PASSKEY_RP_ID` (default: `COOKIE_DOMAIN` without a leading dot, else `brand.localhost`), `PASSKEY_RP_NAME` (default `BRAND_NAME`); expected origins = `AUTH_URL` and `ACCOUNT_URL` origins. Env validated in `apps/api/src/env.ts`.
- Options: `residentKey: "required"`, `userVerification: "required"`, `attestationType: "none"`; `excludeCredentials` = the user's existing passkeys (`{ id, transports }`) on registration. Verify with the library's default `requireUserVerification: true` (a passkey stands in for both factors, so possession alone is not enough; a security key with no PIN is refused).
- `@simplewebauthn/*` v13 (13.3.0 checked in Context7, 2026-10-16). API facts the code relies on:
  - `generateRegistrationOptions({ rpName, rpID, userName, userID, attestationType, excludeCredentials, authenticatorSelection })`. `userID` must be a `Uint8Array` (a string throws). Use `isoUint8Array.fromUTF8String(String(user.id))` from `@simplewebauthn/server/helpers`; the sign-in check decodes `response.response.userHandle` the same way.
  - `verifyRegistrationResponse({ response, expectedChallenge, expectedOrigin: string[], expectedRPID })`. It throws on structural, origin, RP ID and challenge mismatches and returns `verified: false` only when the attestation itself fails. On success, persist `registrationInfo.credential`: `{ id, publicKey: Uint8Array, counter, transports? }`. Store `publicKey` as base64url through `isoBase64URL.fromBuffer`.
  - `generateAuthenticationOptions({ rpID, userVerification })` with no `allowCredentials` (discoverable).
  - `verifyAuthenticationResponse({ response, expectedChallenge, expectedOrigin, expectedRPID, credential })` returns `authenticationInfo.newCounter`.
  - The challenge is stored hashed, so pass `expectedChallenge` as the function form, `(c) => tokenHash(c) === row.token_hash`. Never store the raw challenge.
  - Counter: the library throws "Response counter value X was lower than expected Y" *before* we know the assertion is genuine, so a forged response could trip it. Pass the stored credential with `counter: 0` (which disables the library's own check). After `verified: true`, the api checks it itself: when stored or new is non-zero, the new value must be greater than the stored one, else refuse and `recordFailure`. A cloned-authenticator event is then recorded only for a signature that really verified.
  - Browser: `startRegistration({ optionsJSON })` and `startAuthentication({ optionsJSON, useBrowserAutofill? })`. Autofill needs an `<input autocomplete="… webauthn">` with `webauthn` last (it throws otherwise). Use `browserSupportsWebAuthnAutofill()` before trying it.
- Passkey sign-in never returns a two-factor challenge; limiter `passkey:<x-api-client-id>` 10 per 15 min (FailureLimiter-style: refund on success) plus the existing api-wide sign-in cap.
- Registration rule = two-step setup's: password on an account with one (`UNAUTHORIZED`, `data.reason: "password"`), else session younger than `REAUTH_WINDOW_MS` (`FORBIDDEN`, `data.reason: "reauth"`); `FORBIDDEN` "Not available while impersonating" for register/rename/delete.
- Last-way-in rule: deleting a passkey is `CONFLICT` when the account has no password, no identity, and this is its last passkey.
- Every user-facing api message through `apiMessage` with a contract constant + en/sv catalog keys; every UI string translated (en + sv) in auth/account; the i18n guards stay green.
- Commit trailer exactly `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; Conventional Commits ≤ 100 chars; Biome clean, zero warnings. Implementers never run Playwright or `bun run ci`.

## Review Focus

1. A passkey registered for one user used to sign in as another (credential_id lookup, user handle mismatch) → sign-in resolves the user from the stored credential only; a mismatched `userHandle` is refused (Task 2 test).
2. Replay: the same assertion or challenge used twice → single-use challenge consumed atomically; counter rule (Task 2 test).
3. A wrong origin (a sibling subdomain not in the expected list, or http on prod) → refused (Task 2 test).
4. Lockout: a passwordless, provider-less user deleting the last passkey → CONFLICT; admin removal of all passkeys for such a user still allowed (magic link remains) (Task 3 test).
5. A user with 2FA on signing in by passkey getting a code prompt, or a password sign-in for that user skipping 2FA → passkey skips, password still challenges (Task 2 test).
