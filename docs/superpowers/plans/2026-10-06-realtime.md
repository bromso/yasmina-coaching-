# Realtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Live updates from `apps/api` to signed-in pages over Server-Sent Events relayed through
each app's own origin, with one working example: live notes and presence on `apps/app`'s `/notes`.

**Architecture:** `apps/api/src/realtime/` holds the `Broadcaster` seam (`memory` for SQLite,
`postgres` via `NOTIFY` + Bun's `sql.listen`), the presence registry and the SSE stream handler
mounted on `Bun.serve` at `/events/workspaces/:workspaceId`. `notes.create` / `notes.delete`
publish after commit. `@repo/session/events` exports `createEventsRoute()`, which `apps/app`
mounts at `/api/events`; the `/notes` page subscribes with `EventSource` through a pure reducer.

**Tech Stack:** Bun 1.4.2 (`Bun.serve` streaming responses, `SQL.listen`, `bun test`), oRPC 1.15
contract types, Zod 4, Next 16.2 route handlers, React 19, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-06-realtime-design.md`

## Global Constraints

- Code style: Biome, double quotes, no semicolons, 2-space indent, 100-char lines; `bunx biome ci .`
  clean with zero warnings.
- Conventional Commits, header ≤ 100 chars, one type per header; every commit message ends with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- No new npm dependency.
- Browsers never call `apps/api`; the production CSP is not changed.
- Channel name: `workspace:<id>`. Postgres `NOTIFY` channel: `realtime`; payload limit 8000 bytes.
- Events: `note.created { note }`, `note.deleted { id }`,
  `presence { replicaId, members: { userId, name, avatarUrl }[] }`, `resync {}`.
- Stream: `Content-Type: text/event-stream`, `Cache-Control: no-store`, `X-Accel-Buffering: no`;
  first line `retry: 3000`; `id:` per event (monotonic per process); `: ping` comment every 25 s;
  presence re-published every 25 s; a replica unseen for 60 s is dropped from the client merge.
- Limits: 5 open streams per session (the 6th → 429); `REALTIME_MAX_STREAMS` default 1000 per
  process (→ 503). Membership and session re-checked every 60 s.
- Env: `REALTIME_BUS` (`memory` | `postgres`, default by dialect), `REALTIME_MAX_STREAMS`.
- Relay client id: `events:<ip hash>` (like `files:`).
- Presence never includes email.

## Review Focus

1. **A reconnect after the tab slept or a proxy cut the stream** — the client gets `resync` and
   `presence` on reconnect and refreshes, so the list is correct even though nothing is replayed.
   (Task 2 sends them on every connect; Task 4's reducer handles `resync`.)
2. **A member removed while their stream is open** — the stream closes at the next re-check and
   delivers nothing after; their presence disappears for the others. (Task 2)
3. **The user's own action** — creating a note via the server action both revalidates the page and
   delivers `note.created`; the note must appear once, not twice. (Task 4 reducer test)
4. **An older page of notes (`?cursor=`)** — a new note must not be inserted into an older page;
   live inserts apply only on the first page; deletes apply anywhere. (Task 4 reducer test)
5. **A 6th tab** — the api answers 429, `EventSource` stops retrying, the page keeps working without
   live updates and shows no error loop. (Task 2 limit test; Task 4 handles `onerror` with
   `readyState === CLOSED` by showing nothing alarming)

```ts
// @repo/api-contract realtime.ts
export const PresenceMemberSchema = z.object({ userId: z.number().int().positive(), name: z.string(), avatarUrl: z.string().nullable() })
export const RealtimeEventSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("note.created"), note: NoteSchema }),
  z.object({ type: z.literal("note.deleted"), id: z.number().int().positive() }),
  z.object({ type: z.literal("presence"), replicaId: z.string(), members: z.array(PresenceMemberSchema) }),
  z.object({ type: z.literal("resync") }),
])
export type RealtimeEvent = z.infer<typeof RealtimeEventSchema>
export const workspaceChannel = (workspaceId: number) => `workspace:${workspaceId}`
export const NOTIFY_PAYLOAD_LIMIT = 8000
// apps/api broadcaster.ts
export type Broadcaster = {
  kind: "memory" | "postgres"
  publish(channel: string, event: RealtimeEvent): Promise<void>
  subscribe(channel: string, onEvent: (event: RealtimeEvent) => void): () => void
  close(): Promise<void>
}
export function memoryBroadcaster(): Broadcaster
export function postgresBroadcaster(sql: SQL, log: Log): Promise<Broadcaster> // resolves after LISTEN is acknowledged
export function createBroadcaster(opts: { bus: "memory" | "postgres"; databaseUrl: string; log: Log }): Promise<Broadcaster>
```

The Postgres broadcaster uses its own `new SQL(databaseUrl)` (a `LISTEN` holds a connection);
`publish` runs `SELECT pg_notify('realtime', $json)` where `$json` is
`JSON.stringify({ channel, event })`; a serialized payload over `NOTIFY_PAYLOAD_LIMIT` bytes
(`Buffer.byteLength`) throws `realtime payload too large` before any SQL. The listener parses each
payload, validates `event` with `RealtimeEventSchema` (drop and log invalid ones) and fans out to
local subscribers of `channel`. A subscriber that throws is logged and does not stop the others.
`memoryBroadcaster` does the same fan-out without the database. Check the exact `SQL.listen`
signature in `node_modules/.bun/bun-types@1.4.2/.../sql.d.ts` (around line 988) before writing.

- Produces:

```ts
// after-commit.ts
export function publishAfterCommit(ctx: { broadcaster: Broadcaster; recordFailure: (m: string, e: unknown) => void },
  channel: string, event: RealtimeEvent): void // fire-and-forget; logs failures; never throws
// presence.ts
export type PresenceRegistry = {
  join(workspaceId: number, member: PresenceMember, connectionId: string): boolean // true if the user is new
  leave(workspaceId: number, userId: number, connectionId: string): boolean        // true if the user left
  members(workspaceId: number): PresenceMember[]
  workspaces(): number[]
}
export function createPresence(): PresenceRegistry
// stream.ts
export function createStreamHandler(deps: { db: Db; broadcaster: Broadcaster; presence: PresenceRegistry;
  replicaId: string; maxStreams: number; maxPerSession?: number; pingMs?: number; recheckMs?: number;
  fileUrl: (key: string | null) => string | null; log: Log; recordFailure: (m: string, e: unknown) => void }):
  { handle(req: Request): Promise<Response>; closeAll(): void; openCount(): number }
```

Today `notes.create` / `notes.delete` write without a transaction, so `publishAfterCommit` runs
after the write returns; document in its JSDoc that a caller inside `db.transaction` must call it
after the transaction resolves (never inside the callback).

Stream behaviour (all from the spec): authenticate the bearer through `protect` (mount
`"/events/workspaces/:workspaceId": { GET: protect((req) => streams.handle(req)) }`), then read
`x-session-token` → live non-expired session → user; parse the id; membership required — a missing
or invalid session answers 401, a non-member or unknown workspace 404 (same body shape as other api
errors). Count streams per session id; the 6th → 429 `{ message: "Too many open streams" }`;
`openCount() >= maxStreams` → 503. Respond with a `ReadableStream`: write `retry: 3000\n\n`, then
`presence` (after joining) and `resync`; subscribe to the channel and write each event as
`id: <n>\nevent: message\ndata: <json>\n\n`; every `pingMs` (25 000) write `: ping\n\n` and re-publish
this replica's presence snapshot; every `recheckMs` (60 000) re-read session and membership and
close if either is gone. On close (client abort via `req.signal`, recheck failure, `closeAll`):
unsubscribe, clear timers, `presence.leave`, and when the user left publish a new snapshot.
`replicaId` is `crypto.randomUUID()` per process. `onShutdown` calls `streams.closeAll()`.

**Interfaces — Produces:**

```ts
// lib/realtime.ts
export type LiveState = { notes: Note[]; firstPage: boolean; presence: Record<string, { members: PresenceMember[]; seenAt: number }> }
export function applyRealtimeEvent(state: LiveState, event: RealtimeEvent, now: number): LiveState | "resync"
export function presentMembers(state: LiveState, now: number): PresenceMember[] // merged, de-duplicated by userId, replicas unseen for 60 s dropped
```

Rules: `note.created` → prepend only when `firstPage` and the id is not already in the list (the
user's own create arrives twice: revalidation and event); `note.deleted` → remove by id anywhere;
`presence` → store by `replicaId` with `seenAt = now`; `resync` → return `"resync"` (the component
calls `router.refresh()`). `LiveNotes` receives the server-rendered notes and re-seeds its state
when they change (after `router.refresh()` or a revalidating action), opens
`new EventSource("/api/events")` in an effect, parses `MessageEvent.data` with
`RealtimeEventSchema.safeParse` (ignore invalid), and closes it on unmount. Connection status:
show "Reconnecting…" (`role="status"`) when the source has been in `CONNECTING` for more than 5 s;
when `readyState` is `CLOSED` (e.g. 429) show nothing — the page still works. `HereNow` renders the
merged members as an avatar stack (`useImageFallback` from `@repo/ui/components/image-fallback`,
initials fallback, `title` = name) with an accessible label `"<n> people here"` /
`"1 person here"`; hidden when empty. The notes list markup stays the same (the existing
`NoteList` is reused inside `LiveNotes`); without JavaScript the page is unchanged.
