# Internationalisation (i18n)

The starter ships English plus a Swedish demo locale that proves the whole path: the signed-in
surface (today, `apps/auth`, `apps/app` and `apps/account`), the emails `apps/api` sends, and
the api's own user-facing messages all speak the user's chosen language, remembered across every
subdomain and device. `packages/i18n` (`@repo/i18n`) is the shared layer every other piece reads;
see its `README.md` for the package itself, `packages/session/README.md` for how a Next app
resolves and sets the locale, `apps/api/README.md`'s **Locale** section for the api side, and
`packages/email/README.md` for emails. This guide is about *using* all of that day to day.

## Adding an app to i18n

A **signed-in app** (today `apps/auth`, `apps/app`, `apps/account`) follows the same pattern,
each piece copied from an existing app:

1. `src/i18n/request.ts` (`next-intl`'s `getRequestConfig`, no routing, no `[locale]` segment),
   resolving the locale from `getAuth().getLocale()`. The layout that calls it starts with
   `await connection()` (outside any `try`) and its `catch` opens with
   `unstable_rethrow(error)` (from `next/navigation`, imported first) — so resolution never runs
   while a build prerenders a route, and a missing `API_URL` at build time never logs "locale
   resolution failed" at all (it used to, once per prerendered route, before this ordering).
2. `next-intl` (`catalog:`) and `withNextIntl` around `next.config.mjs`; `<html lang={locale}>` in
   the root layout; `NextIntlClientProvider messages={messagesFor(locale, [...])}` with only the
   namespaces its own client components read (`ui` strings reach `@repo/ui` as props, computed
   server-side — never shipped to the browser as a namespace of their own).
3. The header's `LocaleSwitcher`, wired to a `setLocale` server action — see **The switcher**
   below.
4. Its own namespace, `packages/i18n/messages/<locale>/<name>.json` (see **Adding a language**
   below for the file shape), and a `zodMessage(t)` in `src/lib/i18n.ts` for its forms — see
   **Zod messages** below.
5. Its own guard test, `src/i18n-guard.test.ts` over `@repo/i18n-guard`'s `scanApp`, plus
   `@repo/i18n-guard` (`workspace:*`) as a `devDependency` — see **The guard and its allow-list**
   below.

A settings-style page that lets the signed-in user pick their own language (`apps/account`'s
Personal info) also gets a **Language card** — see below.

A **static app** (`docs`, `help`, `jobs`) needs none of the above: it stays English and adds only
`StaticLocaleSwitcher` to its header — see **The switcher** below. It gets no namespace, no guard
test and no `next-intl` dependency. `www` (Swedish by default, English by cookie, rendered per
request) and `blog` (Swedish at `/`, English under `/en`, fully static, one root layout per
language for `<html lang>`, its words in `apps/blog/src/content/ui.ts`, a header language link
that opens the page's translation and writes the shared `locale` cookie) are bilingual without
`next-intl` — see `apps/www/README.md` and `apps/blog/README.md`.

## Adding a language

1. Add the code to `LOCALES` and its own-language name to `LOCALE_NAMES`, both in
   `packages/i18n/src/locales.ts`:
   ```ts
   export const LOCALES = ["en", "sv", "da"] as const
   export const LOCALE_NAMES: Record<Locale, string> = { en: "English", sv: "Svenska", da: "Dansk" }
   ```
2. Add `packages/i18n/messages/da/` with the seven namespace files (`common.json`, `ui.json`,
   `auth.json`, `app.json`, `account.json`, `email.json`, `api.json`) — copy `en/`'s and translate the values; the *keys* must
   match exactly.
3. Register the catalogs in `packages/i18n/src/catalog.ts`: import the seven JSON files and add
   the locale to `ALL_LOCALE_MESSAGES` (its type, `Record<Locale, Messages>`, fails the typecheck
   until you do; `messagesFor` and `translatorFor` read nothing else):
   ```ts
   import daApi from "../messages/da/api.json"
   // …the other six
   const DA = { common: daCommon, ui: daUi, auth: daAuth, app: daApp, account: daAccount, email: daEmail, api: daApi }
   export const ALL_LOCALE_MESSAGES: Record<Locale, Messages> = { en: EN, sv: SV, da: DA }
   ```
4. Run `cd packages/i18n && bun test`. The catalog-parity test (`src/messages.test.ts`, "catalog
   parity") fails per namespace, listing exactly the keys the new locale is missing — fill those
   in and re-run until it's clean. The same file's ICU-validity test (`every message string in
   every locale compiles as valid ICU`) catches a typo'd plural or an unbalanced brace in the new
   translations the same way.
5. Nothing else changes: `messagesFor` merges English under any locale missing a key, so a
   half-finished translation shows English rather than a raw key, and every consumer
   (`translatorFor`, `next-intl`'s `useTranslations`) already iterates `LOCALES`.

A locale never needs new code to parse its messages — only new JSON, its seven imports in
`catalog.ts` and, for a demo-quality rollout, enough translated keys to pass step 4.

## Adding a key and using it

Pick a namespace by *who renders it*, not by app: `common` (shared strings any namespace can
reuse — there's barely a convention here yet, since only `ui`, `auth`, `email` and `api` carry
real content so far), `ui` (what `@repo/ui` components render, as props — see **`@repo/ui`
stays prop-driven** below), `auth`/`app`/`account` (each app's own pages and forms), `email`
(templates), `api` (the api's user-facing messages). Nest by page or feature:
`auth.signIn.title`, `account.security.twoFactor.turnOn`.

1. Add the key to **every** locale's file for that namespace (English first) —
   `packages/i18n/messages/<locale>/<namespace>.json`. The catalog-parity test fails loudly if you
   forget one.
2. **Server component** (a page, a layout, `generateMetadata`):
   ```tsx
   import { getTranslations } from "next-intl/server"

   export async function generateMetadata() {
     const t = await getTranslations("auth.meta")
     return { description: t("description") }
   }

   export default async function Page() {
     const t = await getTranslations("auth")
     return <h1>{t("signIn.title")}</h1>
   }
   ```
3. **Client component** (needs `"use client"` and the namespace in the provider — see
   `apps/auth/src/app/layout.tsx`'s `NextIntlClientProvider messages={messagesFor(locale,
   ["auth"])}`, which ships only `auth` to the browser; `ui` strings reach `@repo/ui` as props,
   computed server-side):
   ```tsx
   "use client"
   import { useTranslations } from "next-intl"

   export function LoginForm() {
     const t = useTranslations("auth")
     return <button>{t("login.submit")}</button>
   }
   ```
4. **Outside React** (`apps/api`'s error messages, `@repo/email`'s templates, an action core under
   `bun test`): `translatorFor(locale, namespace)` from `@repo/i18n/translate` — the same ICU
   engine (`use-intl/core`), no React, no Next request context:
   ```ts
   import { translatorFor } from "@repo/i18n/translate"
   const t = translatorFor(locale, "auth")
   t("login.title")
   ```

## Plurals, selects and rich text

ICU, inline in the catalog JSON — never a second format, never HTML in a message.

**Plural** (`ui.userMenu.trigger`, with an `=0` exact case ahead of the plural rules):
```json
"trigger": "{pending, plural, =0 {Account menu for {name}} one {Account menu for {name}, # pending invitation} other {Account menu for {name}, # pending invitations}}"
```
```ts
t("userMenu.trigger", { name: "Ada", pending: 2 })
```

**Select** (Swedish's `email.invitation.body`, picking the role's own name; `other` falls back to
the raw value rather than a missing-key marker, so an unanticipated role still renders something):
```json
"body": "{inviter} bjöd in dig att gå med i {workspace} som {role, select, viewer {läsare} member {medlem} admin {administratör} owner {ägare} other {{role}}}. Länken är giltig i {days} dagar."
```

**Rich text** — `t.rich`, never raw HTML in a message, so a translator cannot inject markup and a
link's destination stays in code, not in a string a translation could break:
```json
"terms": "By clicking continue, you agree to our <terms>Terms of Service</terms> and <privacy>Privacy Policy</privacy>."
```
```tsx
t.rich("terms", {
  terms: (chunks) => <a href={`${legalBaseUrl}/terms`}>{chunks}</a>,
  privacy: (chunks) => <a href={`${legalBaseUrl}/privacy`}>{chunks}</a>,
})
```

## API messages

Every user-facing error or notice the apps display comes from `apiMessage(context, key, values?)`
in `apps/api/src/i18n.ts` — never a literal string in a handler. `context.locale` is set once per
request from `x-locale` (see `apps/api/README.md`'s **Locale** section); `apiMessage` looks up one
translator per locale, built at module load, not per call.

**The en-equals-constant rule.** `@repo/api-contract` declares a default message for every error a
procedure can throw (so a typed client sees that text even without reading the English catalog).
`apps/api/src/i18n.test.ts` pins every catalog key that has a named contract constant
(`AUTH_ERRORS.UNAUTHORIZED`, `WORKSPACE_ERRORS.NOT_FOUND`, …) to equal that constant when read in
English, and a separate coverage test unions every key the suite checks against
`Object.keys(messagesFor("en", ["api"]).api)` — so the catalog and the contract can never drift
apart, and a new key added without a matching test fails the gate. Follow the same rule for a new
procedure's error: add the English string to the contract as today, add the same string to
`packages/i18n/messages/en/api.json` under a new key, translate it in `sv/api.json`, throw it
through `apiMessage(context, key)`, and add it to the `i18n.test.ts` coverage list.

Admin-only messages (`admin.*`, the superadmin middleware's own refusals) stay English on purpose
— internal tooling, out of the guard's and the catalog's scope.

## Email messages and byte-identity

`@repo/email`'s templates read `packages/i18n/messages/<locale>/email.json` through
`translatorFor(locale, "email")`; `emails.<name>(props, locale = "en")` is the one entry point —
see `packages/email/README.md`'s **Locale** section for the subject-vs-`<name>Subject` split and
why a handful of templates keep an oddly-split JSX child (`@react-email/render`'s hydration
comment placement, pinned byte-for-byte against a committed English snapshot). The practical rule
when editing a template: never merge two adjacent JSX text/expression children into one string
without re-running `src/index.test.tsx`'s byte-identity test — if it fails, the split was load
bearing.

## Zod messages

A form action maps a Zod issue to a translated message **by its `code`** (and, for a custom
refine, `params.key`) — never by matching the issue's English `message` text, which would break
the moment anyone rewords it. `apps/auth/src/lib/i18n.ts`'s `zodMessage(t)` is the pattern:
```ts
export function zodMessage(t: AuthT) {
  return (issue: ZodLikeIssue) => {
    if (issue.code === "custom") {
      const key = issue.params?.key
      return typeof key === "string" ? t(`validation.${key}`) : t("validation.invalid")
    }
    if (issue.code === "too_small") return t("validation.tooShort", { min: Number(issue.minimum) })
    // …
  }
}
```
`fieldErrors(issues, zodMessage(t))` (`@repo/ui/components/form-feedback`) renders the result;
omit the second argument and `fieldErrors` behaves exactly as it did before translation existed —
nothing about its untranslated callers changes. A custom Zod `refine`/`check` that wants a specific
message in every locale passes `params: { key: "..." }` rather than relying on its English
`message` being read by a mapper (see `@repo/api-contract`'s password-reuse refine).

## The switcher

`@repo/ui/components/locale-switcher` (`LocaleSwitcher`) is every header's switcher: a language
menu. Its trigger shows the current language's flag and name (its accessible name is
"<label>: <name>", e.g. "Språk: Svenska"); it opens a list of every language — each a button
with its flag and its name in its own language (`LOCALE_NAMES`, with `lang`), the current one
marked with `aria-current` and a check — and activating one applies it at once. That activation
is an explicit choice, so WCAG 3.2.2 holds where an auto-submitting `<select>` would not (arrow
keys fire its `change` on every step). Once hydrated it is `@repo/ui`'s Radix `DropdownMenu`
(Enter/Space/ArrowDown open it, arrows move, Escape closes it and returns focus, Tab closes it and
moves on, a click outside closes it; the entrance animation is off under reduced motion).
Server-rendered, and so without JavaScript, it is a `<details>` disclosure whose languages are
submit buttons `name="locale"` inside the `<form action>`, so a signed-in app's switch needs no
script.

The flags live in one place, `LOCALE_FLAGS` in `@repo/i18n/locales` (`circle-flags:gb` for
English, the spelling the site uses, and `circle-flags:se`); an option's own `flag` overrides it.
They are bundled offline by `bun icons:bundle` (from `@iconify-json/circle-flags`, a root
devDependency like `@iconify-json/lucide`), which scans `packages/i18n/src` too and strips each
flag's id-bearing mask so server and client markup agree — so they render server-side, with no
network fetch and no CSP change. A new locale is one entry in `LOCALE_NAMES` and `LOCALE_FLAGS`,
then `bun icons:bundle`. The flags are decorative (`aria-hidden`); the name carries the meaning.

`@repo/ui` itself never imports `next-intl` — the component takes `label`/`options` as plain
props, so it works the same in a translated and an untranslated app. Three things use a
language control:

- **A signed-in app's header switcher** posts to a `setLocale` server action (`action` prop) —
  the pattern below.
- **A static app's header switcher** is `StaticLocaleSwitcher`
  (`@repo/ui/components/static-locale-switcher`), which wraps `LocaleSwitcher` with `onChange`
  instead of `action` — there is no form (and so no no-JavaScript path), because a static page has no per-request render to post
  to. Until hydrated it renders an invisible, `aria-hidden`, `inert` placeholder of the same size
  (nothing is safe to read before that, and the header must not shift), then reads the
  `locale` cookie client-side; when a language is chosen it writes that cookie itself (`writeLocaleCookie`, the same
  `document.cookie = …` pattern `CookieConsent` already uses) and shows a visible, polite-live-
  region "Saved — signed-in pages will use it." note, which stays until a reload. The page itself never changes language. Pass
  it the app's existing build-time `cookieDomain` prop so the written cookie reaches every
  subdomain, not just this one — building a static app without `COOKIE_DOMAIN` set writes a
  host-only cookie instead (see `apps/e2e/README.md`'s **Run** section for where this bites).
- **Personal info's Language card** (`apps/account`'s `LanguageForm`) — a settings field, not a
  header control, so it keeps `LocaleSelect` (`@repo/ui/components/locale-select`): a labelled
  native `<select>` plus a **Save language** button, nothing applied on the select's `change`,
  with `selectProps` for its field error and `pending` — see below.

The server action pattern (`apps/app/src/app/actions.ts`'s `setLocale`, the one a new signed-in
app copies): validate with `isLocale`, call `getAuth().setLocale(locale)` (saves the profile when
signed in, then the cookie), `revalidatePath("/", "layout")` on success so the whole tree
re-renders in the new language, then redirect back to the page the request came from
(`localeReturnPath` — checked against this app's own origin, same principle as `safeNextUrl`'s
subdomain check, though it is its own small function, not a call to it) with a `?locale_error=1`
flag on failure.

## The Language card

A page that lets the signed-in user change their own language in place, rather than via the
header's redirect-and-back, adds a **Language card** — `apps/account`'s Personal info is the
example (`components/language-form.tsx`, `setLanguage` in `app/(account)/personal-info/actions.ts`
over `setLocaleCore` in `lib/actions.ts`). It is an ordinary `useActionState` form like every other
settings card, not the header's redirect pattern: `setLocaleCore` validates with `isLocale`
(a field error on refusal), calls `getAuth().setLocale(locale)`, and on success calls the page's
own `revalidate()` (`revalidatePath("/", "layout")`) and returns its confirmation message in the
*new* locale, since the whole tree — the header included — re-renders before the response is read.
Its `LocaleSelect` is labelled "Language" / "Språk" and saved by its own button
(`account.language.submit`, "Save language" / "Spara språk"); the header's menu trigger is a
button named "Language: <name>", so the two controls coexist on one page without an
accessible-name collision; a test or an e2e journey finds the card by its own submit button.

## The guard and its allow-list

`packages/i18n-guard` (`@repo/i18n-guard`) is the hard-coded-string guard every translated app
runs as its own `src/i18n-guard.test.ts` (a workspace package rather than a file under `scripts/`,
because it needs `typescript` and CI's planner job runs `bun test scripts` before `bun install`).
Its `scanApp({ srcDir, label, allowlistPath, isExcluded })` parses every `.tsx` file under an
app's `src/` with the TypeScript compiler (`ts.createSourceFile`), outside admin pages, tests and
`global-error.tsx`, and walks the JSX. It flags:

- a `JsxText` node containing a letter — on one line or wrapped across several, and the words
  around an expression (`<p>{name} signed in</p>` flags `signed in`);
- a string literal or template literal written directly as a JSX child — `{"Sign in"}`,
  `` {`Sign in`} ``, either branch of a conditional (`{ok ? "Saved" : "Failed"}`) and the operands
  of `&&` / `||` / `??`, through parentheses;
- the literal value, plain or in braces, of a user-facing attribute: `placeholder`, `aria-label`,
  `alt`, `title`, `label`, `aria-description`.

`t("…")`, any other expression (`{value}`) and every other attribute (`className="…"`) pass. JSX
text and plain attribute values are decoded first, so a decorative entity (`&nbsp;`, `&middot;`,
…) is not text while an unknown or misspelled one (`&nbps;`) still is, and a file with a syntax
error throws naming the file rather than being walked as the partial tree TypeScript recovers.
`packages/i18n-guard/README.md` has the full list and its self-tests plant one probe per shape.

Each of `apps/auth`, `apps/app` and `apps/account` has its own `src/i18n-guard.test.ts`, ~30 lines
over `scanApp` naming its own `srcDir`, `label` and `isExcluded` (tests, `global-error.tsx`, and
anything else the app's own guard test chooses to skip):
```ts
test("apps/<name>'s translated surface has no hard-coded, user-facing JSX text", () => {
  const violations = scanApp({
    srcDir: import.meta.dir,
    label: "apps/<name>/src",
    allowlistPath: join(import.meta.dir, "..", "i18n-guard.allowlist.json"),
    isExcluded,
  })
  if (violations.length > 0) {
    throw new Error(describeViolations(violations, "apps/<name>/i18n-guard.allowlist.json"))
  }
  expect(violations).toEqual([])
})
```
The app adds `@repo/i18n-guard` (`workspace:*`) to its own `devDependencies`.

**Blind spots.** It sees only what is written inside the JSX: a string built or held in a
variable, a constant or a helper's return value outside it and then rendered (`const msg = "Hi"`,
`<p>{msg}</p>`) passes, as does a string handed to a component under a prop name not in the list
(`<Card heading="Hi" />`) and anything a `.ts` file renders. Treat it as a floor, not a guarantee —
translate through `t(...)` by convention and let the guard catch what slips through.

A genuine false positive — the brand name, a code sample inside a `<pre>` — gets an entry in that
app's own `i18n-guard.allowlist.json` (empty in all three today):
```json
{ "file": "apps/auth/src/views/example-view.tsx", "text": "Acme", "reason": "..." }
```
An entry matches by `file` and by `text` (a substring of the flagged text), never by line number,
which would drift every time someone edits the file above it. Every entry needs a `reason`, and
`scanApp` itself throws when an entry names a file outside the app, a file `isExcluded` already
skips, carries no reason, or no longer matches anything (stale) — so a fixed false positive (or a
deleted file) is caught rather than left as dead weight, and each app's own test over this stays a
single call rather than re-implementing the check.

## Known limits

- **Scope.** `apps/auth`, `apps/app` and `apps/account` (every page, Personal info's **Language**
  card included) are translated, and `www` and `blog` are bilingual their own way (see above). The
  other static apps (`docs`, `help`, `jobs`) stay English by design and get only the plumbing: `StaticLocaleSwitcher` in the header, writing the
  shared cookie, and nothing else — no namespace, no guard test, no `next-intl` dependency. Every
  `@repo/ui` string the three translated apps render reaches it as a prop from the `ui` namespace:
  the header's nav label and its mobile menu (`mobileLabels`: the hamburger, the sheet's title and
  close button), the footer's nav label, the cross-app links and footer group titles
  (`relabelNav` / `relabelFooter` from `@repo/sites`, by id: `ui.sites.<id>`,
  `ui.footerGroups.<id>`) and the account sidebar's sheet. The defaults stay English, which is
  what the static apps render; the superadmin's **Admin** link stays English like the admin pages.
- **Routes with no `x-locale`.** `createFileRoute`, `createEventsRoute` and `@repo/telemetry`'s
  server route build their own api clients and send no `x-locale` — on purpose, not as a gap: each
  answers with a bodyless status or a `204`, so nothing they return is ever shown to a person, and
  there is nothing to translate. Every other anonymous caller, `apps/www`'s contact and booking
  actions included, resolves and sends it from a real signal (the `locale` cookie or `Accept-Language`,
  never the English fallback) — see `packages/session/README.md`'s **Locale** section.
- **The locale cookie is `Secure` over plain http in production mode.** Same choice, same reason,
  as the `session` cookie it sits next to (`packages/session/src/cookie.ts`): fine on `*.localhost`
  (Chromium and Firefox treat it as a secure context regardless of scheme, which is what every dev
  and e2e run uses), a real problem for a plain-http staging environment on a non-`.localhost`
  domain, where neither cookie would be sent at all. Terminate TLS before staging, the same answer
  as for the session cookie.
- **A static app's switcher only shares its cookie across subdomains when built with
  `COOKIE_DOMAIN` set.** `StaticLocaleSwitcher` passes the app's own build-time `cookieDomain`
  straight to `writeLocaleCookie`; a static app built without `COOKIE_DOMAIN` writes a host-only
  cookie, so the choice never reaches the signed-in apps on their own subdomains. `next dev` falls
  back to `.brand.localhost`; `next build` runs in production mode and has no such fallback, so
  the e2e script and CI job set `COOKIE_DOMAIN=.brand.localhost` explicitly. This is the same
  build-time trade-off `CookieConsent` already makes for the consent cookie.
