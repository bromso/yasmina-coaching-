# Operations

Phase 9 B: structured logs, a request id that follows one browser request through `apps/api` into
the jobs it causes, a token-protected Prometheus `/metrics` on the api and its worker (B1), and
nightly backups with a tested restore and incident runbooks (B2). This guide covers all of it.

## Logs

Every server process — `apps/api`, its worker, `apps/ai`, and the server-side code of `apps/app`,
`apps/auth`, `apps/account`, `apps/www`, `apps/help` and `apps/jobs` — logs through `@repo/log`
(`packages/log/README.md`), a dependency-free package safe to import from Bun and Node alike. Each
service builds one process-wide logger named after itself:

```ts
import { createLogger } from "@repo/log"

const logger = createLogger({ service: "api" }) // "worker", "ai", "app", "auth", … elsewhere
```

One JSON object per line, in call order:

```json
{ "time": "2026-10-15T12:00:00.000Z", "level": "info", "service": "api", "message": "request", "requestId": "q1Z3k9…", "method": "POST", "route": "/rpc/notes/create", "status": 200, "ms": 42.3 }
```

- **Format.** `json` by default when `NODE_ENV=production`, `pretty` otherwise (one readable
  line, e.g. `2026-10-15T12:00:00.000Z WARN  [api] careful (q1Z3k9…) n=2`). `LOG_FORMAT` (`json` |
  `pretty`) overrides either default.
- **Level.** `LOG_LEVEL` (`debug` | `info` | `warn` | `error`, default `info`); a line below the
  threshold is dropped before anything is formatted. An invalid value falls back to `info` and
  logs one `warn` line naming the bad value — it never throws and never crashes the process.
- **Envelope.** `time`, `level`, `service`, `message` (and `requestId` when one is in scope)
  always come from the logger itself: a field with one of those names is written as
  `field.<key>` instead, so a stray `level: "info"` can never hide an error line from a level
  filter.
- **Redaction.** Every field passed to `debug`/`info`/`warn`/`error`/`child` is walked at any
  depth (plain objects, arrays and `Map`s; capped at 8 levels, deeper values become `"[depth]"`)
  before it is written. A key containing `password`, `token`, `secret`, `authorization`,
  `cookie`, `apikey` / `api_key` / `api-key`, `dsn`, `credential` or `private_key` — case-insensitive,
  matched anywhere in the key, so `sessionToken`, `api_secret`, `X-Session-Token`, `SENTRY_DSN` and
  a nested `headers.Authorization` are all caught — or the bare key `auth` becomes `"[redacted]"`.
  A key ending in `email` is masked instead of dropped (`maskEmail`: `ada@example.com` →
  `a***@example.com`), as is an address under `to`, `from` or `address`, so an email stays
  identifiable without being a raw PII value in a log sink. A `URL` value is written without its
  username, password or the values of sensitive query parameters (`?token=`). A logger call never
  throws: an unserialisable field (a circular reference) logs a fallback line
  (`logError: "unserialisable fields"`) rather than losing the line or crashing.
- **Errors.** An `Error` (typically `fields.error`) is serialised as `{ name, message, stack }`
  plus its own string and number properties (`code`, `errno`, Postgres's `detail`) and its `cause`,
  recursively (5 links at most), so Bun's `TypeError: fetch failed` keeps the real reason —
  `cause: { message: "connect ECONNREFUSED", code: "ECONNREFUSED" }`. The pretty format prints the
  chain on the error's line (`error=Error: fetch failed <- Error: connect ECONNREFUSED [ECONNREFUSED]`).
- **The log mailer.** With `MAIL_PROVIDER=log` (the dev default) each email is one `info` line
  `mail` — masked `to`, `subject`, and the whole text body as `text` — written by whichever
  process runs the jobs. Its purpose is to show the one-time links, so it never belongs in
  production (the api warns at startup).
- **`apps/ai`'s usage line.** One `info` line per model call with `message: "ai.usage"` and the
  entry's fields (`route`, `model`, token counts, `steps`, `ms`, `outcome`). Before these logs it
  was a bare JSON line with `event: "ai.usage"` — a filter on `event` must move to `message`.
- **`child(fields)`** returns a logger that merges `fields` into every line it writes afterwards —
  used for a job's own fields (`job`, `jobId`) layered on the process logger.
- **The api's internal callback.** `apps/api`'s hundreds of existing call sites still call a
  `log(message, error)` callback; it's now `legacyLog(logger)` (`apps/api/src/request-context.ts`)
  over the same structured logger, so none of those call sites changed.

## Request ids, end to end

A request id is 16 random bytes, base64url-encoded — 22 characters,
`^[A-Za-z0-9_-]{22}$` — generated by `newRequestId()`. An *incoming* id is accepted only if it
matches the looser `^[A-Za-z0-9_-]{8,64}$` (`validRequestId`); anything else is treated as absent
and a new one is generated. One id follows a browser's request through every hop it causes:

1. **The Next apps' proxy.** `createSecurityProxy()` (`packages/ui/src/lib/security-proxy.ts`,
   each app's `src/proxy.ts`) keeps a well-formed incoming `x-request-id` or generates one, sets
   it on the request forwarded to the Next server *and* on the response — so the id is stable for
   the whole request and visible to the browser.
2. **`@repo/session`'s clients and the few app-owned ones.** `createAuth`'s client, `anonymousApi`,
   the `*FromRequest` helpers (`getUserFromRequest`, `getMeFromRequest`,
   `resolveWorkspaceFromRequest`), `createTelemetryRoute`, `createAnalyticsRoute`,
   `createFileRoute` and `createEventsRoute` (all in `@repo/session` / `@repo/telemetry`) forward
   the request's id as `x-request-id` on their own call to `apps/api` or `apps/ai`. The few
   app-owned clients that build their own request — `apps/www`'s contact and booking actions, `apps/help`'s
   contact action, `apps/jobs`'s apply action and `apps/app`'s `/api/chat` proxy to `apps/ai` — do
   the same.

   The Next servers' own log lines carry the id only where it is already at hand: `@repo/session`'s
   error lines (`auth.me failed`, `workspaces.list failed`, `files: api call failed`,
   `events: api call failed`) add it as a `requestId` field from the header they forward. There is
   no Next-wide request context (no `withRequestContext` around a page, action or route), so a line
   an app's own action or page writes has no `requestId` unless it adds one itself — follow such a
   request by its api lines instead, which always carry it.
3. **`apps/api` and `apps/ai`.** Both share `@repo/service-kit`'s `withRequest` wrapper around
   every handler. It accepts a caller's `x-request-id` **only when that caller already passed the
   service-bearer guard** — an anonymous or malformed request can never plant an id that then
   shows up in operator logs as if it were trusted; otherwise it generates a fresh one. Either
   way, the whole handler runs inside `withRequestContext({ requestId })`
   (`@repo/log/context`, over `node:async_hooks`'s `AsyncLocalStorage`, so the id survives `await`
   and timers), the id is echoed as the `x-request-id` response header, and every log line the
   handler writes — directly or through anything it calls — carries it.
4. **Jobs.** Migration `0022_jobs_request_id` adds a nullable `jobs.request_id`. `enqueue` stores
   `currentRequestId()` at the moment of enqueue (`null` for a schedule's own tick, which enqueues
   outside any request). The worker runs each job inside
   `withRequestContext({ requestId: row.request_id ?? newRequestId() })`, so a job's log lines —
   a `mail.send` triggered by a sign-up, say — join the request that caused it, and a job with no
   request id (a nightly schedule) still gets one of its own for the run.

**Access logging.** `withRequest` writes one `info` line per api/ai request: `method`, `route`
(a bounded label — a procedure path such as `/rpc/notes/create` or `openapi:<segment>`, never a
raw URL, id or query string; see **Metrics** below for how `route` stays bounded), `status`,
`ms`, and `clientId` when the caller sent one. `/health`, `/ready` and `/metrics` are never
access-logged (and never rate-limited).

**Timeouts.** `/ready` (and the dedicated worker's `/health`) gives its database ping
`READY_TIMEOUT_MS` (default 2 000 ms) and answers `503` "Not ready (timed out)" past it — a paused
Postgres keeps its socket open, so without the bound the probe would hang instead of failing.
Every other logged api/ai request has a server-side deadline, `REQUEST_TIMEOUT_MS` (default
30 000 ms): with no response by then it answers `503` "The request took too long. It may still
complete — check before retrying." and logs a `request timed out` warning carrying its request id;
the handler finishes in the background and its result is discarded — nothing can cancel a pending
query, so a mutation (`notes.create`, `jobs.apply`, `workspaces.create`, an avatar replace, …) may
still commit after the caller was told it failed. Treat a 503 past the deadline as an unknown
outcome, not a clean failure: check before blindly retrying a non-idempotent write. The api's event
streams are exempt, and a chat stream already under way is not cut. On `apps/ai`, the deadline also
does not abort the provider call behind `summarize`: a slow model call keeps running past the 503
and its tokens are still billed once it finishes — see `apps/ai/README.md`.

**Checking it.** `apps/e2e/tests/request-id.spec.ts` checks what a browser can actually see: a
page response from `www /`, `auth /login` and `app /notes` (signed in) carries a
22-character `x-request-id`, and two loads of the same page get different ids. To follow one
request by hand: open the page, read `x-request-id` off the network response, then `grep` the
api's logs for that id — every line it caused (the oRPC call, any job it enqueued) carries it.

## Metrics

`GET /metrics` on `apps/api` (a `Bun.serve` route, outside oRPC) and on the dedicated worker
(`apps/api/src/worker.ts`'s own health server); `apps/ai` exposes no `/metrics`. Both are built on
`@repo/service-kit`'s hand-written registry (`createRegistry`, Prometheus text exposition format
0.0.4, `content-type: text/plain; version=0.0.4; charset=utf-8`) and its `metricsRoute`:

- `METRICS_TOKEN` unset → **404** (off by default; a deployment that never set a token is never
  silently open).
- A missing or wrong bearer token → **401** (compared in constant time).
- A matching token → the full exposition.

Labels are always bounded: `route` is a procedure path or REST segment the contract actually
declares (`apiRouteOf`, `apps/api/src/request-context.ts`) — a raw id, an unknown path or a query
string all fold to `"other"`, so a scraper can never create an unbounded number of label series
from a caller making up paths. A job name a running process does not define (newer code than the
worker's build) folds to `"other"` the same way.

### What the api exposes

| Metric | Type | Labels | Notes |
|---|---|---|---|
| `http_requests_total` | counter | `route`, `method`, `status_class` | `status_class` is `2xx`…`5xx` (anything outside 100–599 folds to `5xx`) |
| `http_request_duration_seconds` | histogram | `route`, `method` | buckets 0.005…10 s (`DEFAULT_BUCKETS`) |
| `rate_limit_refusals_total` | counter | `limiter` | the tripped cap's key, with any per-app suffix collapsed (`capLimiterLabel`) so the label set stays fixed |
| `realtime_streams_open` | gauge | — | read from the live stream count on scrape |
| `db_ping_seconds` | gauge | — | a database round trip timed on each scrape |
| `process_resident_memory_bytes` | gauge | — | `process.memoryUsage().rss` |
| `process_uptime_seconds` | gauge | — | `process.uptime()` |
| `build_info` | gauge | `version`, `commit` | always `1`; `commit` from `GIT_COMMIT` (`"unknown"` unset) |

When the same process also runs the worker (`JOBS_WORKER` not `false`), it additionally exposes
the job metrics below on its own `/metrics` — so an api replica and a dedicated worker never
double-count the queue between them. `jobs_queue` is counted from the shared `jobs` table, so
several api replicas running the worker each report the same database-wide number: aggregate it
with `max()`, never `sum()` (`max(jobs_queue) by (status)`). The other job metrics are per process
and do sum.

| Metric | Type | Labels | Notes |
|---|---|---|---|
| `jobs_queue` | gauge | `status` (`queued`/`running`/`dead`) | counted from the `jobs` table on scrape |
| `job_runs_total` | counter | `name`, `outcome` (`succeeded`/`retried`/`dead`) | |
| `job_duration_seconds` | histogram | `name` | buckets 0.005…10 s plus 30 s, 60 s |
| `scheduler_lag_seconds` | gauge | — | how late the scheduler's last minute tick fired |

### What the dedicated worker exposes

The same job metrics table above, plus `process_resident_memory_bytes`, `process_uptime_seconds`
and `build_info{version,commit}` — nothing api-specific (no HTTP metrics; the worker serves only
`/health` and `/metrics`).

A scrape-time collector (anything reading the database) that throws or takes longer than 2 s is
skipped for that one metric rather than failing the whole scrape.

### Scrape config

```yaml
scrape_configs:
  - job_name: boilerplate-api
    scheme: https
    metrics_path: /metrics
    authorization:
      credentials: "${METRICS_TOKEN}"
    static_configs:
      - targets: ["api.brand.example.com"]

  - job_name: boilerplate-api-worker
    scheme: https
    metrics_path: /metrics
    authorization:
      credentials: "${METRICS_TOKEN}"
    static_configs:
      - targets: ["api-worker.internal.brand.example.com"]
```

(Prometheus's `authorization.credentials` sends `Authorization: Bearer <credentials>`. Any
Prometheus-compatible scraper that can send a static bearer token works the same way.)

### Example alerts

```yaml
groups:
  - name: boilerplate-bun
    rules:
      - alert: HighServerErrorRate
        expr: |
          sum(rate(http_requests_total{status_class="5xx"}[5m]))
          / sum(rate(http_requests_total[5m])) > 0.05
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: "5xx rate above 5% for 5 minutes"

      - alert: HighRequestLatency
        expr: |
          histogram_quantile(0.95,
            sum(rate(http_request_duration_seconds_bucket[5m])) by (le, route)
          ) > 1
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: "p95 latency above 1s on {{ $labels.route }}"

      - alert: DeadJobsRising
        expr: increase(job_runs_total{outcome="dead"}[15m]) > 0
        for: 0m
        labels: { severity: warning }
        annotations:
          summary: "A job died in the last 15 minutes — check /admin's Background jobs card"

      - alert: JobQueueBacklog
        # max(), not sum(): every replica running the worker reports the same table-wide count.
        expr: max(jobs_queue{status="queued"}) > 500
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: "500+ jobs queued for 10 minutes — worker may be stalled or undersized"

      - alert: ScrapeOrReadyFailing
        expr: up{job=~"boilerplate-api.*"} == 0
        for: 2m
        labels: { severity: critical }
        annotations:
          summary: "/metrics (or the target) has been unreachable for 2 minutes"
```

## Backups and runbooks

### Turning backups on

`apps/api/src/backup/` dumps the whole database to a single gzipped JSON-lines file; one code path
serves both engines, and a backup taken on one restores on the other (see **Cross-engine restore**
below). It is off by default — `BACKUP_ENABLED=true` (`apps/api/.env.example`, the root
`.env.example`) turns on the nightly `backup.run` schedule (`0 2 * * *` UTC; the scheduler checks
it on every tick, but a running process's env is fixed, so turning it on or off is a restart).
Each run:

1. Dumps the database to a local temp file, then uploads it to the storage seam (whichever
   `STORAGE_PROVIDER` the api already uses) at `backups/<YYYY-MM-DD>/<engine>-<HHMMSS>.jsonl.gz`
   (UTC; `BACKUP_KEY_PATTERN` in `apps/api/src/backup/format.ts`). `storage.sweep` never lists
   `backups/` — it only ever deletes avatars, logos and expired exports — so a backup is never at
   risk from the sweep.
2. Deletes its own objects under `backups/` older than `BACKUP_RETENTION_DAYS` (default 14, 1–365)
   by the date in the key itself, never by the storage provider's own metadata; a stray key under
   `backups/` that isn't a backup (an upload that landed there by mistake) is left alone. That
   includes a backup the CLI wrote to storage (same key pattern): keep one you mean to hold on to
   past the retention — a pre-upgrade backup, say — with `backup -- --out <file>` instead. A prune
   failure is recorded and the job still succeeds; the next night prunes again.
3. On success, logs `backup written <key> (<bytes> bytes)` and sets the gauge `backup_last_success_timestamp_seconds` (read on scrape from the
   `jobs` table's last succeeded `backup.run` row — see the **restoring from a backup** runbook
   below for what that means for alerting). On failure it calls `recordFailure` (a log line plus a
   telemetry `server` row) before the usual job retry/backoff.

Uploading reads the whole compressed file into memory first (`Storage.put` takes bytes, not a
stream), so a very large database's backup briefly costs that many bytes of RAM on whichever
process runs the job (the api, or the dedicated worker) — worth knowing before enabling this on a
memory-constrained box with a multi-gigabyte database.

### What is — and isn't — in a backup

The format (`apps/api/src/backup/format.ts`) is gzipped UTF-8 JSON lines: a header
(`format`, `version`, `engine`, `createdAt`, the applied `migrations` in order, and each table's
last-handed-out id so a restore never reuses one), then per table a `{ table, columns }` line
followed by one JSON array per row.

- **`jobs` is left out.** A queued `mail.send`, `storage.delete` or anything else still pending
  would re-run after a restore — re-sending mail, re-deleting an object the restore just put back
  — so the backup never carries it. A restore into an empty database starts with an empty queue;
  anything the old database had queued is gone.
- **`schema_migrations` is left out too** — the header's `migrations` list already says exactly
  which ones were applied, and restore uses that to decide what to re-run.
- **The uploads bucket is not copied.** A backup is the database only: `avatar_key`, `logo_key`
  and the export/CV keys it stores are references into whatever `STORAGE_PROVIDER` holds, and this
  guide does not back that up. Rely on your storage provider's own versioning or replication (S3
  versioning, R2's, a SeaweedFS volume replica, …) for the bucket itself. The two must be restored
  to the same point together — a database restored to yesterday with a bucket still at today has
  rows pointing at objects that were deleted since, and the reverse has objects nothing references
  yet. See **the restore drill** below for the order that keeps them in step.

### The restore drill

Both CLIs load the same env the running api does (`loadEnv`, `apps/api/src/env.ts` — `DATABASE_URL`,
`STORAGE_PROVIDER` and friends) and never print a database URL or credential. `bun run --filter`
runs them in `apps/api`, so a relative path (`./backup.jsonl.gz` below) means
`apps/api/backup.jsonl.gz`, not one in your shell's directory — both log the absolute path they
used. `--out` writes through `<file>.partial` and renames it into place only once the dump is
complete, so a failed dump never clobbers a good backup already there. A backup the CLI takes does
not move `backup_last_success_timestamp_seconds` (only the nightly job does).

```bash
# Local file, either engine:
bun run --filter @repo/api backup -- --out ./backup.jsonl.gz
bun run --filter @repo/api restore ./backup.jsonl.gz [-- --force]

# The storage seam instead of a local file (the default for backup; restore takes a key too):
bun run --filter @repo/api backup                      # prints the key it wrote
bun run --filter @repo/api restore backups/2026-10-15/sqlite-020000.jsonl.gz [-- --force]
```

In the Docker image the same two entrypoints are `bun dist/backup-cli.js` / `bun
dist/restore-cli.js` (no `bun run --filter`, since the image has no workspace).

**Before you restore:**

1. **Stop every process that writes to the target database** — the api and any dedicated worker
   (`src/worker.ts`). A restore that runs beside them either refuses (the target isn't empty) or,
   with `--force`, deletes rows a live process is reading or writing mid-request.
2. **Pause `storage.sweep`** (`30 3 * * *`): set `STORAGE_SWEEP_ENABLED=false` for every process
   that runs the job worker (the api unless `JOBS_WORKER=false`, and the dedicated `api-worker`)
   before you start them again, and keep it off until the bucket is restored to the same point as
   the database (see **what isn't in a backup** above) — otherwise the sweep can delete an object
   the restored database still references, or one a not-yet-restored bucket is about to need. The
   flag pauses only the sweep; mail and every other job keep running. (Stopping the worker
   altogether does the same, with everything else stopped too.)
3. Restore the bucket to the matching point first (your storage provider's own tooling), *then*
   restore the database, *then* start the api and worker(s) again.

**On SQLite:**

```bash
rm .data/api.db*                                   # the fresh, empty target (or a new path)
bun run --filter @repo/api restore backups/2026-10-15/sqlite-020000.jsonl.gz
```

A target with any rows in any table refuses with `RestoreTargetNotEmpty`, naming the occupied
tables, and exits 1 — restore into a database with none, or re-run with `--force` to delete those
rows (children-first) before inserting. A target with more migrations applied than the backup
lists is refused even with `--force`: this code cannot undo a migration, so restore into a fresh
database (or one at or behind the backup's migration list) instead.

**With Docker Compose** (the stack in `docker-compose.yml`, SQLite on the `api-data` volume at
`/data/api.db`): the image has no workspace, so the restore runs `dist/restore-cli.js` in a one-off
container from the api's own image, with the api's environment and volume (`docker compose run
api …` gives it both; `--no-deps` starts nothing else, so SeaweedFS keeps running only if it
already is — it must, to restore from a storage key).

```bash
docker compose stop api api-worker                 # every writer (api-worker only if you run it)

# Move the old database aside (kept until you are sure), leaving /data/api.db absent:
docker compose run --rm --no-deps api \
  sh -c 'mkdir -p /data/before-restore && mv /data/api.db* /data/before-restore/'

# From a storage key (the bucket the api's STORAGE_PROVIDER points at):
docker compose run --rm --no-deps api \
  bun dist/restore-cli.js backups/2026-10-15/sqlite-020000.jsonl.gz

# …or from a file on the host, mounted read-only into the one-off container:
docker compose run --rm --no-deps -v "$PWD/backup.jsonl.gz:/restore/backup.jsonl.gz:ro" api \
  bun dist/restore-cli.js /restore/backup.jsonl.gz

# Start again with the sweep paused until the bucket matches (step 2 above):
STORAGE_SWEEP_ENABLED=false docker compose up -d api   # add --profile worker to start api-worker
```

The image's working directory is `/app`, so give the CLI an absolute path (as above). `--force`
goes after the key or path, as with the bare CLI. Once the bucket is back in step, run `docker
compose up -d api` again without `STORAGE_SWEEP_ENABLED=false` (or with it unset in `.env`) to
turn the sweep back on, and delete `/data/before-restore` when you no longer need it. Against
Postgres instead, skip the `mv` and point the one-off container at a fresh database: `docker
compose run --rm --no-deps -e DATABASE_URL=postgres://… api bun dist/restore-cli.js <key|path>`.

**On Postgres:** the same two commands, pointed at a fresh database or schema via `DATABASE_URL`
(create one with `createdb` or `CREATE DATABASE`, rather than reusing the live one). Restore resets
every table's `id` sequence to at least the backup's own counter and at least the restored rows'
`MAX(id)` — `pg_get_serial_sequence` per table — so the first insert after a restore never collides,
and an id handed out before the backup (to a row deleted before it was taken) is never handed out
again.

**Cross-engine restore:** a SQLite backup restores into Postgres and a Postgres backup into SQLite
(both directions are tested in `apps/api/src/backup/backup.test.ts` when `TEST_DATABASE_URL` is
set) — the format and the restore logic don't care which engine produced the dump. One difference:
`REAL` is single precision on Postgres, so a telemetry vital's value narrows going SQLite → Postgres. Useful for migrating engines, not
only for disaster recovery.

**After restoring:** turn `storage.sweep` back on (`STORAGE_SWEEP_ENABLED` unset or `true`, then
restart) only once the bucket is back in step (see above), and
check `backup_last_success_timestamp_seconds` on the next scrape to confirm the schedule is running
again if `BACKUP_ENABLED` is on.

### Runbooks

Each: the symptom, the exact log line or metric to check, the fix.

**1. The api will not start.**
Symptom: the container exits immediately (`restart: on-failure:3` in `docker-compose.yml` burns
through its retries, or a bare process exits 1 at once).
Look for: `cannot start: <reason>` (`apps/api/src/index.ts`'s `cannotStart`, one line, `error`
level) — the reason is `loadEnv`'s own message, e.g. `AUTH_URL is not set`, `MAIL_PROVIDER=smtp
needs SMTP_URL`, `STORAGE_PROVIDER=s3 needs S3_BUCKET, S3_REGION, …`,
`TWO_FACTOR_ENCRYPTION_KEY must not be the development key`, or a migration failure.
Fix: set (or fix) exactly the variable the message names — `loadEnv` always says which one — and
restart; nothing else about the process is wrong.

**2. A dead-job backlog.**
Symptom: jobs stop completing; mail, storage deletes or the prunes fall behind.
Look for: `max(jobs_queue{status="dead"}) > 0` (or the `JobQueueBacklog` / `DeadJobsRising` alerts
in **Example alerts** above), or `apps/auth`'s `/admin` **Background jobs** card (queued / running
/ dead counts, the 20 most recent dead jobs with their `last_error`).
Fix: read the dead job's `last_error` on the card for the real cause (a bad mail provider, a
storage credential, …) and fix that first. Then **Retry** it (back to `queued`, `attempts` 0,
`run_at` now — a `CONFLICT` means a newer copy already holds its dedupe key, so nothing is lost) or
**Discard** it if it should never run again. A whole backlog of the same job name usually means the
underlying dependency (mail provider, storage, database) is down — fix that, then retry in bulk is
not built; retry them one at a time from the card, or re-enqueue by hand if there are many.

**3. The realtime stream cap.**
Symptom: `/notes` or any live page stops updating; its `EventSource` gets a `503` and shows
"Reconnecting…" that never clears (or, on a fresh connect, the page just never goes live).
Look for: a `503` from `GET /events/workspaces/:workspaceId`, or `realtime_streams_open` near
`REALTIME_MAX_STREAMS` (default 1000) on `/metrics`.
Fix: raise `REALTIME_MAX_STREAMS` if the process has headroom (memory, file descriptors) for more
open streams, or run more api replicas (each process has its own cap, so spreading load across
replicas raises the effective total) — there's also a per-session (5) and per-user (10) cap that
`503`s the same way before the process-wide one does; that's a client reconnecting too many tabs or
sessions, not a capacity problem, and lowering those is not the fix for a real backlog.

**4. Mail failing.**
Symptom: sign-up verification, password reset or any other mail never arrives.
Look for: no `mail sent <template> to <masked address>` line (`apps/api/src/jobs/builtin/mail.ts`)
for the expected send, and instead a dead `mail.send` job on the **Background jobs** card with a
`last_error` naming the provider's failure (an SMTP connection refused, a bad Resend key, …).
Fix: check the provider's own env first — `MAIL_PROVIDER`, and whichever of `SMTP_URL` /
`RESEND_API_KEY` / `MAIL_DIR` it needs (see the env table in `CLAUDE.md`'s **Email** section) —
against the provider's own status or credentials, then **Retry** the dead job once the provider is
reachable again; the job's payload still holds the original template, address and props, so retrying
it sends the original mail, not a copy.

**5. Storage 403s.**
Symptom: avatars or workspace logos stop loading (`404` from the apps' `/files/<key>` route, which
reads the same as a missing file), or `storage.sweep` keeps dying.
Look for: `recordFailure("storage read forbidden", …)` (`apps/api/src/storage/s3.ts`'s
`onForbidden`, wired in `index.ts` / `worker.ts`) — logged on *every* 403, not just the first,
since one on every object means credentials or the bucket policy, not a missing file.
Fix: check the IAM policy's `s3:ListBucket` grant and the access key pair — see
`docs/guides/storage.md`'s IAM policy note (a bucket without `s3:ListBucket` answers 403, not 404,
for a genuinely missing key; wrong credentials answer 403 for every key). Correct the policy or the
credentials; no restart is needed once they're fixed.

**6. SQLite `database is locked`.**
Symptom: a write fails outright with that message, rather than queuing behind the busy timeout as a
single-writer SQLite file normally does.
Look for: the error text itself (it surfaces as a thrown error on whatever request or job hit it,
not a dedicated log line); separately, `db: a statement waited 30000 ms behind an open SQLite
transaction …` (`gateTimeoutMessage`, `apps/api/src/db.ts`) is a different, related symptom — a
transaction inside this process held the gate too long — and `SQLite pragmas failed` at startup
means `busy_timeout` / WAL never engaged in the first place, which is what makes the plain
`database is locked` error possible at all.
Fix: this is what happens when more than one process opens the same SQLite file without WAL mode
engaged, or when a process outside this codebase (a backup tool, a shell `sqlite3` session) opens
the file with its own locking. Confirm `createDb`'s pragmas actually ran (no `SQLite pragmas
failed` line at startup); if they did and this still happens with more than one api/worker process
on one file, move to Postgres (`DATABASE_URL=postgres://…`) — SQLite's single-writer-per-file model
is correct for exactly one process, documented as such throughout this repo, and is not a
configuration you can scale your way out of on SQLite itself.

**7. Restoring from a backup.**
Symptom: data loss or corruption serious enough that a restore, not a fix, is the answer.
Look for: `backup_last_success_timestamp_seconds` on `/metrics` to confirm there is a recent backup
to restore from (compare it to `BACKUP_RETENTION_DAYS` old) — but note that this gauge is read from
the `jobs` table's last *succeeded* `backup.run` row, and `jobs.prune` deletes succeeded rows after
7 days: the metric can quietly disappear a week after the last success even though nothing is
newer wrong, which is exactly the gap an alert should catch (a missing/stale gauge, not just a low
value). Add one alongside the five in **Example alerts** above:

```yaml
      - alert: BackupStale
        # 2 days: one missed nightly run (0 2 * * *) is tolerated, two are not. Match the threshold
        # to your own schedule; absent() catches a gauge jobs.prune has already removed.
        expr: |
          absent(backup_last_success_timestamp_seconds)
          or (time() - max(backup_last_success_timestamp_seconds)) > 86400 * 2
        for: 1h
        labels: { severity: critical }
        annotations:
          summary: "No successful backup.run in over 2 days"
```

Only add it once `BACKUP_ENABLED` is on: if it was never turned on, there's nothing to restore from
— the gauge is never exposed in the first place, and `absent()` would fire forever.
Fix: follow **the restore drill** above in full, including stopping the api, every worker, and
restoring the bucket to the same point before the database.

**8. Suspending a compromised or abusive account.**
Symptom: an account needs to stop signing in right now — abuse, fraud, a compromised credential —
without deleting anything or waiting on the account-deletion grace period.
Do: on `apps/auth`'s `/admin/users/<id>`, the **Suspension** card's form (superadmin only; refused
for yourself, another superadmin, or an impersonation session, same as the other admin cards) —
give a reason (3–200 characters, internal only, kept in the audit log and never shown to the user)
and, optionally, an end date (strictly future, at most 365 days out; blank suspends indefinitely).
The write ends every session the account holds and stamps `sessions_revoked_at` in the same
transaction, so an open tab or an outstanding two-step challenge cannot outlive it, and mails the
account (`accountSuspended`: the end date if any, a support line, never the reason). Every sign-in
path — password, magic link, a sign-in or connect provider callback, a passkey, a two-step code —
then answers "This account is suspended. Contact support." once its own credential check passes;
`/admin/users?suspended=true` and each row's "Suspended" badge are how to find every account an
active suspension currently blocks — both show only suspensions in force, so an expired one drops
out of them the moment its end date passes. **Lift suspension** on the same card (same reason
field) reverses it and mails `accountUnsuspended`. A suspension whose end date already passed needs
no action to stop blocking sign-in — `isSuspended` reads it as expired on the next attempt — but
its record stays on the user's own page (Status "Expired") until an admin clears it with **Lift
suspension**, which the card offers whenever a record exists, expired or not. To suspend an
account again after an expired suspension, lift the expired record first; the card then shows the
**Suspend account** form.
Fix: n/a — this is the intended control, not a failure. Workspaces, memberships, billing and
invitations are untouched; see CLAUDE.md's **Suspension** paragraph and `apps/api/README.md`'s
**Suspension** section for the full rule.

## Audit log retention and export

`audit_log` (migration `0011_admin`) is append-only in every writer (apart from the privacy purge
nulling user ids), and since Phase 10 C, bounded:
nightly `audit.prune` (`45 3 * * *`) deletes a whole row once it passes `AUDIT_RETENTION_DAYS`
(default 365 days) and strips the `ip`/`user_agent` of every younger row once it passes
`AUDIT_PII_RETENTION_DAYS` (default 90 days). Each run has a time budget (48 s of its 60 s
timeout): a backlog bigger than one run can clear — the first nights after an upgrade with years of
history — stops there, logs `audit pruned (partial: time budget reached, the next run continues)`
with its counts and finishes as a success, and the following nights carry on until it is drained;
it never retries or dies for being large. A superadmin can pull a period of it out as a CSV or
JSON Lines file from `/admin/audit` before that happens. See CLAUDE.md's **Audit retention and
export** paragraph and `apps/api/README.md`'s section of the same name for the mechanism (the
job, the batching, the export procedure's cap and columns); this guide covers the bounds'
reasoning, how to justify a longer period, what a restore brings back, the overlap with backups,
the tamper-evidence gap, and what to do with an export once it exists.

**Workspace activity (Phase 12 A).** A workspace's own admins and owners see a 90-day window of
its administrative actions (membership, roles, invitations, API keys, webhooks, plan) on
`/workspace`'s Activity card — a *view* over the same `audit_log` rows, not a separate retention
period. The rows themselves are deleted on the schedule above, under `AUDIT_RETENTION_DAYS`: once
`audit.prune` removes a row, it drops out of the Activity card too, at the latest the same night
(sooner, since the card's own window is 90 days). See CLAUDE.md's **Activity log.** paragraph and
`apps/api/README.md`'s **Activity log** section.

### Why these bounds

The defaults and the 180–1095-day range (`AUDIT_RETENTION_MIN_DAYS`/`AUDIT_RETENTION_DEFAULT_MAX_DAYS`
in `apps/api/src/env.ts`) come from a specific legal basis, checked 2026-10-18 — not legal advice;
the operator remains the controller and should have counsel confirm this for their own
jurisdiction and facts:

- **An IP address a site operator stores is personal data** where the operator has legal means to
  identify the person — CJEU C-582/14 *Breyer*, 19 Oct 2016, para. 49. Storing it for security purposes, as `audit_log.ip` does, can rest on the
  legitimate-interest basis, but that is subject to the balancing test the judgment also sets out
  (paras. 60–64) — it is not a blank cheque to keep it forever.
- **GDPR Art. 5(1)(c)** (data minimisation), **5(1)(e)** (storage limitation — keep personal data
  no longer than necessary for the purpose), **5(1)(f)** and **Art. 32** (security — an audit trail
  is itself a security measure, so keeping one is defensible, but not without limit), and **5(2)**
  (accountability — be able to show why the period chosen is the right one).
- **CNIL Délibération n° 2021-122** (14 Oct 2021, the French data protection authority's
  recommendation on security logging): keep logs **six months to one year** in the general case;
  **up to three years** may be justified specifically for internal control, with documented
  procedures explaining why; a longer period still needs either a specific legal obligation or a
  documented Data Protection Impact Assessment — "the limitation period of offences alone" is
  explicitly called out as *not* sufficient justification on its own; users must be told that
  logging happens, what it records and for how long (see the **Audit logs** section this phase
  added to `apps/www`'s `/privacy` template); access to the logs themselves should stay restricted
  to strict need (superadmin only, here); and logs should ideally be timestamped and signed at
  creation — this codebase does the first and not the second (see **The tamper-evidence gap**
  below).
- **OWASP's Logging Cheat Sheet** adds: record and monitor access to the logs themselves, detect
  tampering, and consider masking or redacting data before extracting or sharing it — the export's
  CSV-injection guard (below) is the one piece of that this implementation takes on directly; the
  rest (monitoring access to `/admin/audit` itself, redacting before a third party sees an export)
  is an operational practice this guide can recommend but not enforce in code.

`AUDIT_RETENTION_DAYS`'s default (365) and its unjustified ceiling (1095 = 3 years) map directly
onto CNIL's "general case" and "internal control" figures; `AUDIT_PII_RETENTION_DAYS`'s default
(90) strips the two columns most clearly identifying (`ip`, `user_agent`) well inside even the
general-case window, while the row itself — `action`, `target_type`/`target_id`, `reason`,
`metadata` — survives longer for the internal-control purpose those columns were never needed for.

### Justifying a period longer than 1095 days

Set `AUDIT_RETENTION_JUSTIFIED=true` and `AUDIT_RETENTION_DAYS` to the value you need, up to 3650
(10 years). The api logs one warning at startup, every time this flag is on, asking the operator to
document the legal obligation or DPIA that justifies it — it does not ask what that justification
is, and does not refuse to start without one; writing it down is on the operator, in whatever
record of processing or DPIA register already covers this system. `AUDIT_PII_RETENTION_DAYS` still
has no equivalent escape hatch: its only requirement is "strictly less than `AUDIT_RETENTION_DAYS`",
however large that is. There is no automatic expiry on the justification itself — revisit it
whenever the underlying obligation does, the same as any other DPIA.

### The backup overlap

`backup.run` (see **Backups and runbooks** above) dumps the whole database, `audit_log` included,
and keeps its own objects under `backups/` for `BACKUP_RETENTION_DAYS` (default 14) before deleting
them itself. A row `audit.prune` deleted last night is still sitting in last week's backup. That
means the **effective** retention of an audit row — the longest it can possibly be recovered from
anywhere this system controls — is `AUDIT_RETENTION_DAYS` plus up to `BACKUP_RETENTION_DAYS`, not
`AUDIT_RETENTION_DAYS` alone. Account for that sum, not just the configured row retention, when
documenting the justification above or answering a data-subject or regulator's question about how
long a given entry could have existed somewhere.

### What a restore brings back

Restoring an older backup (see **the restore drill** above) writes back whatever `audit_log` rows
were in it at that point — including rows `audit.prune` has since stripped or deleted on the live
database, since a restore replaces the table wholesale. Nothing about the restore itself re-applies
retention: those rows sit there, un-pruned, until the next scheduled `audit.prune` run reaches them
again on its own ordinary cutoffs. This is expected, not a bug to route around — a restore is meant
to bring the database back to a point in time, audit trail included, and the nightly job then
carries on as if that point in time had been running the whole while. If a restore is being done
specifically to investigate an incident, consider that the very rows under investigation may be
exactly the ones a routine `audit.prune` run would otherwise strip or delete in the hours after the
restore completes — export anything load-bearing before the next 03:45 UTC tick.

### The tamper-evidence gap

Deleted means deleted: there is no archive step before `audit.prune` removes a row, by design (see
the spec's "No archive before deletion" decision, `docs/superpowers/specs/2026-10-18-audit-retention-design.md`).
**Tamper evidence is not provided.** Rows are not signed or hash-chained at write time, so someone
with direct write access to the database could alter or delete a row with no built-in way to
detect it, and nothing in this codebase meets CNIL's "signed at creation" recommendation. This is a
known, accepted gap — a hash chain is its own later sub-project. What an operator can do today,
neither built into the codebase:

1. **Database-level protections** — restrict direct write access to the `audit_log` table (a
   read-only database role for anyone but the api's own connection, row-level security, or a
   trigger that refuses `UPDATE`/`DELETE` from anything but the api's own connection) are an
   operator's own infrastructure decision, outside this repo.
2. **Keep periodic exports in write-once storage.** Because the export is a plain file (CSV or JSON
   Lines, `admin.audit.export`), an operator can pull a period of it on a schedule (outside this
   codebase — the export is a synchronous download, not a background job, by design; see the
   spec's **Export** decision and its out-of-scope "background exports") and land each file in
   storage a later write cannot silently overwrite — S3 Object Lock in compliance mode, a
   WORM-configured bucket, or a SIEM (Splunk, Datadog, an ELK stack). That gives *after-the-fact
   tamper detection* for the periods exported (compare a stored file with the live table); it is
   not a signature made when each row is written, and it does not satisfy CNIL's "signed at
   creation". **Any such copy is personal data under the same rules as the table**: before it goes
   into long-term storage, remove (or mask) the `ip` and `user_agent` columns, or keep the copy no
   longer than `AUDIT_PII_RETENTION_DAYS` (90 days by default); and keep the rest of each row no
   longer than `AUDIT_RETENTION_DAYS`. A store that keeps network details or rows longer than that
   silently contradicts the configured retention and the `/privacy` **Audit logs** section — if you
   really need the longer period, update that section to state it and where the copy is kept. The
   10-per-hour `audit-export:<adminId>` limiter and the 100 000-row cap (`CONFLICT` past it, never
   a truncated file) both still apply — script a loop over date ranges, not one call for a
   multi-year backlog.

### Handling an export file as personal data

The exported file is personal data in its own right — it carries `actor_email`,
`impersonated_email`, `ip`, `user_agent` and a free-text `reason` column, the same data the live
table holds, just outside the database. Treat a downloaded `audit-<from>-<to>.csv`/`.jsonl` the way
you would any other export containing it:

- It inherits none of `audit_log`'s own access control once it leaves `/admin/audit` — anyone who
  can read the file can read everything in it, including an admin's own stated reason for acting on
  someone's account. Store it only where the same strict-need access rule CNIL recommends for the
  live log still applies.
- Delete or further-restrict a copy once its own purpose (an audit engagement, a SIEM ingest, a
  legal hold) ends; an export left on a laptop or in a shared drive indefinitely defeats the point
  of bounding the live table's retention in the first place.
- The CSV variant is already guarded against formula injection (OWASP's CSV Injection guidance: a
  leading `'` on any cell starting `=`, `+`, `-`, `@`, a tab or a CR) before it reaches whatever
  spreadsheet application opens it, but that guard is about the file executing something unintended
  on open — it does nothing to the data's sensitivity once opened.
- `audit.exported` (the audit row the export itself writes, naming the admin, the range, the format
  and the row count — never the file's contents) is how to see who pulled what, and when, after the
  fact; that row is as durable as the rest of `audit_log`, so it outlives most exports' own
  retention and is the first place to look when auditing the auditors.
